# 3. Update and Delete Operations with Confirmation

## 1. Introduction

The **Update** and **Delete** operations complete the CRUD lifecycle. Updating modifies existing database records using pre-populated forms, while Deleting permanently removes records. To prevent catastrophic data loss, deletions must always include an explicit confirmation screen and require an HTTP POST submission.

---

## 2. Why Do We Need It?

- **Update:** Users make mistakes or data changes over time. Pre-populating existing data into forms enables quick edits.
- **Safe Deletion:** Accidentally clicking "Delete" should never immediately erase data. Confirmation screens prompt users: *"Are you sure you want to delete this item?"*, guarding against accidental clicks.

---

## 3. How It Works

- **Update View:** Fetches existing object via `get_object_or_404`. Initializes `form = ModelForm(request.POST or None, instance=obj)`. If valid, calling `form.save()` executes an SQL `UPDATE`.
- **Delete View:**
  - GET: Displays a confirmation page with a form asking for confirmation.
  - POST: Executes `obj.delete()` and redirects to the list view.

---

## 4. Syntax

```python
# File: books/views.py
from django.shortcuts import render, redirect, get_object_or_404
from django.contrib import messages
from .models import Book
from .forms import BookForm

# UPDATE VIEW
def book_update(request, pk):
    book = get_object_or_404(Book, pk=pk)
    if request.method == "POST":
        form = BookForm(request.POST, instance=book) # Binds existing instance!
        if form.is_valid():
            form.save() # Executes SQL UPDATE
            messages.success(request, f"'{book.title}' updated successfully.")
            return redirect('books:detail', pk=book.pk)
    else:
        form = BookForm(instance=book) # Pre-populates inputs with current values
    return render(request, 'books/book_form.html', {'form': form, 'book': book})

# DELETE VIEW
def book_delete(request, pk):
    book = get_object_or_404(Book, pk=pk)
    if request.method == "POST":
        book_title = book.title
        book.delete() # Executes SQL DELETE
        messages.success(request, f"Book '{book_title}' was permanently deleted.")
        return redirect('books:list')
    # GET: Render confirmation template
    return render(request, 'books/book_confirm_delete.html', {'book': book})
```

## 5. Practical Examples

### Safe Delete Confirmation Template
```html
<!-- books/templates/books/book_confirm_delete.html -->
{% extends 'base.html' %}

{% block content %}
<div class="card danger-zone">
    <h2>Confirm Deletion</h2>
    <p>Are you sure you want to permanently delete <strong>"{{ book.title }}"</strong>?</p>
    <p class="warning-text">This action cannot be undone.</p>

    <form method="POST">
        {% csrf_token %}
        <button type="submit" class="btn btn-danger">Yes, Delete Permanently</button>
        <a href="{{ book.get_absolute_url }}" class="btn btn-secondary">Cancel</a>
    </form>
</div>
{% endblock %}
```

---

## 6. Code Explanation

- `instance=book`: Crucial argument! Without `instance=book`, `form.save()` would insert an entirely new duplicate row into the database instead of updating the existing one.
- `book.delete()`: Executes the SQL `DELETE FROM books_book WHERE id = :pk`.
- The delete confirmation template uses a `<form method="POST">` with `{% csrf_token %}` to prevent CSRF exploits.

---

## 7. Expected Output

When a user confirms deletion:
- Database deletes the row.
- Browser redirects to `/books/`.
- Django flash message appears: `"Book 'Fluent Python' was permanently deleted."`.

---

## 8. Real-World Use Case

Editing user billing addresses, changing product prices, and deleting expired job listings or archived employee profiles.

---

## 9. Common Mistakes

1. **Executing deletion on GET:**
   ```python
   # DANGEROUS SECURITY FLAW:
   def delete_item(request, pk):
       Book.objects.filter(pk=pk).delete() # Executes on GET! Crawlers will destroy your database!
   ```
2. Forgetting `instance=obj` in the update view POST handler.

---

## 10. Best Practices

- Always require an HTTP POST confirmation for all delete actions.
- Always use flash messages (`django.contrib.messages`) to provide clear feedback upon updates and deletions.
- Provide a clear "Cancel" button linking back to safety on delete confirmation screens.

## 12. Interview Questions

**Q1: What is "Soft Deletion" in Django models and when would you use it?**  
*Answer:* Soft deletion is a pattern where records are not physically removed from the SQL database via `DELETE`. Instead, the model has an `is_deleted = models.BooleanField(default=False)` or `deleted_at = models.DateTimeField(null=True)` column. When a user deletes an item, the view marks `is_deleted = True`. Custom managers then filter out deleted items (`filter(is_deleted=False)`). This preserves historical audit logs, foreign key relationships, and allows accidental deletions to be restored.

**Q2: What happens if you omit `instance=obj` in an update view?**  
*Answer:* If you omit `instance=obj`, the `ModelForm` is unbound to any existing database entity. When the user submits their edits and `form.save()` is called, Django interprets it as a creation request and executes an SQL `INSERT`, creating a duplicate row rather than updating the original record.

---

## 13. Summary

- Update views bind the existing entity via `instance=obj`.
- Delete operations require an explicit POST confirmation screen.
- Flash messages communicate successful state changes.
