# 4. Search, Filtering, and Pagination

## 1. Introduction

When tables scale to thousands or millions of records, returning all rows on a single page exhausts server memory and creates unusable web pages. Professional CRUD applications implement **Search**, **Dynamic Filtering**, and **Pagination** to break datasets into fast, browsable chunks.

---

## 2. Why Do We Need It?

- **Performance:** Loading 50 records takes 5ms; loading 50,000 records takes 5,000ms.
- **Usability:** Users need to search items by keyword, filter by categories, and navigate across numbered pages (`Previous [1] 2 3 [Next]`).
- **Memory Conservation:** Django's `Paginator` uses SQL `LIMIT` and `OFFSET` to pull only the requested page into memory.

---

## 3. How It Works

1. **Search & Filter:** Inspect `request.GET.get('q')` and apply `.filter(Q(...) | Q(...))`.
2. **Pagination:** Wrap the filtered QuerySet inside Django's `Paginator(queryset, per_page)`.
3. Extract the requested page number from `request.GET.get('page')`.
4. Call `paginator.get_page(page_number)` to safely handle invalid or out-of-range pages.

---

## 4. Syntax

```python
# File: books/views.py
from django.shortcuts import render
from django.core.paginator import Paginator
from django.db.models import Q
from .models import Book

def book_list(request):
    queryset = Book.objects.all().order_by('-created_at')

    # 1. Search Query
    query = request.GET.get('q')
    if query:
        queryset = queryset.filter(
            Q(title__icontains=query) | Q(author__icontains=query)
        )

    # 2. Category Filter
    category = request.GET.get('category')
    if category:
        queryset = queryset.filter(category__iexact=category)

    # 3. Pagination (10 items per page)
    paginator = Paginator(queryset, 10)
    page_number = request.GET.get('page')
    page_obj = paginator.get_page(page_number)

    return render(request, 'books/book_list.html', {
        'page_obj': page_obj,
        'query': query,
    })
```

## 5. Practical Examples

### Reusable Pagination Controls in HTML Template
```html
<!-- Rendering the list of items -->
{% for book in page_obj %}
    <div class="book-card">
        <h3>{{ book.title }}</h3>
        <p>By {{ book.author }} - ${{ book.price }}</p>
    </div>
{% empty %}
    <p>No books found matching your search criteria.</p>
{% endfor %}

<!-- Pagination Navigation Bar -->
<div class="pagination">
    {% if page_obj.has_previous %}
        <a href="?page=1{% if query %}&q={{ query }}{% endif %}">&laquo; First</a>
        <a href="?page={{ page_obj.previous_page_number }}{% if query %}&q={{ query }}{% endif %}">Previous</a>
    {% endif %}

    <span class="current-page">
        Page {{ page_obj.number }} of {{ page_obj.paginator.num_pages }}
    </span>

    {% if page_obj.has_next %}
        <a href="?page={{ page_obj.next_page_number }}{% if query %}&q={{ query }}{% endif %}">Next</a>
        <a href="?page={{ page_obj.paginator.num_pages }}{% if query %}&q={{ query }}{% endif %}">Last &raquo;</a>
    {% endif %}
</div>
```

---

## 6. Code Explanation

- `Paginator(queryset, 10)`: Splits the QuerySet into 10-item chunks.
- `paginator.get_page(page_number)`: Returns a `Page` object. If `page_number` is not an integer, it gracefully falls back to page 1; if `page_number` exceeds the maximum, it falls back to the last page!
- `page_obj.has_previous` / `page_obj.has_next`: Booleans indicating if adjacent pages exist.
- `{% if query %}&q={{ query }}{% endif %}`: Preserves the active search query when clicking to page 2 or 3!

---

## 7. Expected Output

Querying `http://127.0.0.1:8000/books/?q=python&page=2`:
- Server executes: `WHERE title LIKE '%python%' LIMIT 10 OFFSET 10;`.
- Displays 10 search results matching "python".
- Displays: `Page 2 of 6`.

---

## 8. Real-World Use Case

Every modern web catalog: Google search results, Amazon product browsing, GitHub issue trackers, and corporate employee directories.

---

## 9. Common Mistakes

1. **Losing search filters when clicking pagination links:** Clicking `?page=2` without appending `&q={{ query }}` drops the search term and resets to the entire unfiltered database!
2. Using `paginator.page()` instead of `paginator.get_page()`. `page()` raises `PageNotAnInteger` or `EmptyPage` on bad input, whereas `get_page()` handles exceptions automatically.

---

## 10. Best Practices

- Always use `paginator.get_page()` for resilient error handling.
- Preserve search and filter query parameters in pagination anchor tags.
- Ensure the QuerySet has an explicit ordering (`order_by()`) to prevent pagination inconsistencies.

## 12. Interview Questions

**Q1: Why does Django require an ordered QuerySet when using `Paginator`?**  
*Answer:* Without an explicit `ORDER BY` clause, relational database engines do not guarantee deterministic row ordering between successive queries. If a table has no consistent sort order, rows can randomly shift between pages, causing duplicate items to appear on multiple pages or some items to be skipped entirely when paginating.

**Q2: What is the difference between `page_obj.number` and `page_obj.paginator.num_pages`?**  
*Answer:* `page_obj.number` is the 1-based index of the currently active page (e.g. Page 2). `page_obj.paginator.num_pages` is the total count of all pages available in the dataset (e.g. 15 total pages).

---

## 13. Summary

- `Paginator` slices QuerySets into manageable pages.
- `get_page()` provides error-resilient page resolution.
- Dynamic filtering uses `Q` objects and GET query parameters.
