# 1. Python Prerequisites and Virtual Environments

## 1. Introduction

Before building Django applications, you need a properly isolated development environment. A **virtual environment** is a self-contained directory tree that contains a specific Python interpreter and an isolated set of installed third-party libraries.

---

## 2. Why Do We Need It?

Without virtual environments, all packages installed via `pip` are placed into a single global system directory. This causes critical conflicts:
- Project A may require Django 4.2 LTS, while Project B requires Django 5.1.
- Installing updates for one project can break other existing projects.
- Deployment becomes error-prone because there is no clean record of which dependencies are strictly necessary.
Virtual environments completely isolate project dependencies.

---

## 3. How It Works

When a virtual environment is created:
1. Python creates a new folder (e.g. `venv/`) containing copies or symlinks of the Python executable.
2. Inside `venv/Scripts` (Windows) or `venv/bin` (macOS/Linux), activation scripts alter your shell's `PATH` environment variable.
3. When activated, invoking `python` or `pip` directs commands to the local environment rather than the system-wide installation.

---

## 4. Syntax

```bash
# Check Python version (requires 3.10+)
python --version

# Create virtual environment
python -m venv venv
```

---

## 5. Practical Examples

### Creating and Verifying Virtual Environment
```bash
# 1. Create a workspace directory
mkdir my_django_project
cd my_django_project

# 2. Create the virtual environment named 'venv'
python -m venv venv

# 3. Check created files
# On Windows: dir venv
# On Mac/Linux: ls -l venv
```

---

## 6. Code Explanation

- `python -m venv venv`: Runs Python's built-in `venv` module. The second `venv` is the name of the folder created.
- Inside `venv`:
  - `Include/`: C header files for compiled extensions.
  - `Lib/site-packages/`: Where pip installs all isolated packages.
  - `Scripts/` (or `bin/`): Contains the Python interpreter and activation scripts.
  - `pyvenv.cfg`: Configuration file referencing the base Python installation.

---

## 7. Expected Output

Directory listing after creation:
```text
venv/
├── Include/
├── Lib/
│   └── site-packages/
├── Scripts/ (or bin/)
└── pyvenv.cfg
```

---

## 8. Real-World Use Case

Every professional software consultancy and enterprise development team mandates virtual environments (or Docker containers) so code can be reproduced reliably on continuous integration (CI) runners and staging servers.

---

## 9. Common Mistakes

1. **Committing `venv/` to Git repository:** The virtual environment folder contains OS-specific binaries and must ALWAYS be excluded via `.gitignore`.
2. Forgetting to verify the Python version before creating `venv`.

---

## 10. Best Practices

- Always name your virtual environment standard names like `venv` or `.venv`.
- Always ensure `.gitignore` contains `venv/` and `.env`.

## 12. Interview Questions

**Q1: Why do we isolate dependencies using virtual environments in Django projects?**  
*Answer:* Virtual environments prevent dependency version conflicts between different projects and keep system Python packages clean. They also enable generating precise `requirements.txt` manifests.

**Q2: How does `pip install` know where to install packages when a virtual environment is active?**  
*Answer:* Activation points the environment's `sys.prefix` and shell `PATH` to the `venv/` directory, causing `pip` to install packages inside `venv/Lib/site-packages` instead of the global system directory.

---

## 13. Summary

- Virtual environments isolate third-party packages per project.
- Created using `python -m venv venv`.
- Must never be tracked in version control.
