# 4. Handling Form Submission and cleaned_data

## 1. Introduction

When an HTTP request is submitted, form processing follows a distinct lifecycle: receiving raw input from `request.POST`, validating constraints, converting values into Python types, and extracting the sanitized values from **`form.cleaned_data`**.

---

## 2. Why Do We Need It?

All data sent from browsers over HTTP arrives as raw strings. If a user submits an age field with `"25"`, Python treats it as a string. Database operations, calculations, and domain logic require validated, type-safe Python objects (`int`, `date`, `Decimal`). `cleaned_data` guarantees that data is sanitized, validated, and type-cast.

---

## 3. How It Works

### The Form Submission Lifecycle:
1. Client submits form via POST.
2. View initializes form with submitted payload: `form = FormClass(request.POST)`.
3. View calls `form.is_valid()`.
4. Django runs field-level validation, cleans values, and populates `form.cleaned_data`.
5. If valid, the view accesses `form.cleaned_data['key']` to execute business logic.
6. The view returns a redirect (PRG pattern).
7. If invalid, the view re-renders the template with `form`, preserving user input and displaying error messages.

---

## 4. Syntax

```python
# File: accounts/views.py
from django.shortcuts import render, redirect
from .forms import ProfileForm

def edit_profile(request):
    if request.method == "POST":
        form = ProfileForm(request.POST)
        if form.is_valid():
            # Accessing cleaned and coerced data
            age = form.cleaned_data['age']        # Python int
            birthday = form.cleaned_data['birthday'] # datetime.date object
            bio = form.cleaned_data['bio']        # Sanitized string
            
            # Save or process data...
            return redirect('accounts:profile')
    else:
        form = ProfileForm()

    return render(request, 'accounts/edit.html', {'form': form})
```

## 5. Practical Examples

### Handling Multiple Submit Actions in One Form
```python
# File: orders/views.py
from django.shortcuts import render, redirect
from .forms import OrderForm

def order_processing_view(request):
    if request.method == "POST":
        form = OrderForm(request.POST)
        if form.is_valid():
            data = form.cleaned_data
            
            # Check which button was clicked
            if 'save_draft' in request.POST:
                # Save as draft
                return redirect('orders:drafts')
            elif 'submit_payment' in request.POST:
                # Process transaction
                return redirect('orders:checkout')
    else:
        form = OrderForm()

    return render(request, 'orders/order_form.html', {'form': form})
```

---

## 6. Code Explanation

- `form = OrderForm(request.POST)`: Binds POST data to the form.
- `form.is_valid()`: Triggers full clean routines across all fields.
- `form.cleaned_data`: A dictionary accessible only after `is_valid()` returns `True`.
- `'save_draft' in request.POST`: Inspects which submit button was pressed by examining button `name` attributes.

---

## 7. Expected Output

If the user inputs invalid data (e.g., negative age or invalid email):
- `form.is_valid()` returns `False`.
- The template re-renders with:
  ```html
  <ul class="errorlist"><li>Enter a valid email address.</li></ul>
  ```
- The user's other valid inputs remain populated in the inputs so they don't have to re-type them!

---

## 8. Real-World Use Case

Processing registration forms, payment checkouts, and profile updates across banking, healthcare, and SaaS apps where input errors must be reported immediately without losing user entries.

---

## 9. Common Mistakes

1. **Reading raw `request.POST` instead of `form.cleaned_data`:**
   ```python
   # INCORRECT (Bypasses all validation and type coercion):
   age = int(request.POST.get('age')) # Dangerous! What if user typed 'twenty'? Crashes with ValueError!
   # CORRECT:
   age = form.cleaned_data['age'] # Guaranteed to be a valid int
   ```

---

## 10. Best Practices

- Never use raw `request.POST` directly for business logic; always use `form.cleaned_data`.
- Always redirect after successful POST submissions.

## 12. Interview Questions

**Q1: What happens under the hood when `form.is_valid()` is called?**  
*Answer:* `form.is_valid()` calls `form.errors`. If errors haven't been computed yet, `form.full_clean()` is executed, which:
1. Cleans each field individually via `field.clean()`.
2. Executes custom field cleaners: `clean_<fieldname>()`.
3. Executes form-wide cross-field validation: `form.clean()`.
4. Populates `form.cleaned_data` with valid fields and `form.errors` with validation errors.
It returns `True` if `form.errors` is empty.

**Q2: What is the difference between `request.POST.get('age')` and `form.cleaned_data.get('age')`?**  
*Answer:* `request.POST.get('age')` returns the raw, unvalidated string sent by the HTTP client (e.g. `"-5"` or `"abc"`). `form.cleaned_data.get('age')` returns a validated, sanitized, and type-cast Python integer (or raises validation errors if invalid).

---

## 13. Summary

- Forms convert raw HTTP strings into typed Python objects.
- `form.is_valid()` executes all cleaning and validation checks.
- Validated results are safely accessed via `form.cleaned_data`.
