# 4. Asynchronous Tasks with Celery and Email

## 1. Introduction

Web requests should be answered within milliseconds. Time-consuming operations—such as sending SMTP emails, generating PDF reports, processing video uploads, or syncing third-party APIs—must not block the HTTP request-response cycle. **Celery** is an asynchronous task queue and job scheduler that runs heavy background jobs outside the web server.

---

## 2. Why Do We Need It?

- Sending an email via external SMTP servers (e.g., SendGrid, SES, Gmail) takes 1.5 to 4 seconds.
- If a user signs up and the view sends an email synchronously, the browser spinner spins for 4 seconds. If the SMTP server times out, the entire registration fails!
- With Celery, the view dispatches a task to a message broker in 5ms and returns `201 Created` immediately. A background worker picks up the job and sends the email independently.

---

## 3. How It Works

```text
[ Django View ] ---> (Pushes Task) ---> [ Message Broker (Redis) ]
                                                    |
                                                    v (Pulls Task)
                                         [ Celery Worker Process ]
                                                    |
                                                    v
                                        [ Sends Email / PDF / API ]
```
1. **Producer:** Django creates a task payload (JSON) and pushes it to Redis.
2. **Broker (Redis):** Holds queued tasks until worker processes consume them.
3. **Consumer (Worker):** Standalone Celery Python process executing the task.
4. **Celery Beat:** Scheduler for cron-like recurring periodic tasks.

---

## 4. Syntax

```python
# File: myproject/celery.py
import os
from celery import Celery

os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'myproject.settings')

app = Celery('myproject')
# Read config from Django settings with CELERY_ prefix
app.config_from_object('django.conf:settings', namespace='CELERY')
# Autodiscover tasks in all installed apps (tasks.py)
app.autodiscover_tasks()
```

## 5. Practical Examples

### 1. Defining and Calling a Celery Task
```python
# File: accounts/tasks.py
from celery import shared_task
from django.core.mail import send_mail
from django.conf import settings

@shared_task(bind=True, max_retries=3)
def send_welcome_email_task(self, user_id, user_email, user_name):
    try:
        subject = f"Welcome to our platform, {user_name}!"
        message = "Thank you for joining our community. We are thrilled to have you!"
        send_mail(
            subject,
            message,
            settings.DEFAULT_FROM_EMAIL,
            [user_email],
            fail_silently=False,
        )
        return f"Email sent successfully to {user_email}"
    except Exception as exc:
        # Retry in 60 seconds if SMTP server fails
        raise self.retry(exc=exc, countdown=60)
```

### 2. Calling Task from Django View
```python
# File: accounts/views.py
from django.shortcuts import render, redirect
from .tasks import send_welcome_email_task

def register(request):
    if request.method == 'POST':
        # ... process user registration ...
        user = form.save()
        
        # Dispatch asynchronous task! Returns immediately!
        send_welcome_email_task.delay(user.id, user.email, user.first_name)
        
        return redirect('registration_success')
```

---

## 6. Code Explanation

- `@shared_task`: Decorator allowing reusable tasks without hardcoding the Celery app instance.
- `.delay(*args, **kwargs)`: Shortcut for `.apply_async()`. Serializes arguments to JSON and queues the job into Redis immediately.
- `bind=True`: Gives access to `self`, allowing error handling and `self.retry(countdown=60)`.
- **Golden Rule:** Never pass complete Django model instances to Celery tasks (e.g., pass `user.id`, NOT `user`). Model instances can become stale or cause serialization errors. Always query the model inside the task.

## 8. Real-World Use Case

**Automated Daily Invoicing and Report Generation:**
Celery Beat triggers a daily midnight task that aggregates orders, compiles PDF invoices via WeasyPrint, and emails them to billing contacts without any manual administrative intervention.

---

## 9. Common Mistakes

1. **Passing Model Instances:** Passing `send_email(user)` instead of `send_email(user.id)`. Celery serializes task arguments to JSON; complex model instances fail or contain stale database state by the time the worker executes.
2. **Missing `app.autodiscover_tasks()`:** Forgetting to configure `__init__.py` with Celery app export causes tasks to never register.
3. **No Retries:** Failing to handle external network flakiness with `max_retries` and `countdown`.

---

## 10. Best Practices

- Always pass primitive types (IDs, strings, integers) to tasks.
- Keep tasks **idempotent** (running the task twice should produce the exact same outcome without duplicate side effects).
- Use distinct queues for high-priority tasks (instant transactional emails) vs low-priority tasks (nightly backups).

## 12. Interview Questions

**Q1: What does idempotence mean in the context of asynchronous task queues?**
*Answer:* An idempotent task can be executed multiple times with the same input without changing the result beyond the initial execution. Because network glitches or worker restarts can cause tasks to be delivered or retried more than once ("at-least-once delivery"), tasks must check state before executing (e.g., check `if order.is_paid: return` before processing a payment).

**Q2: How does Celery handle task failures and exceptions?**
*Answer:* By default, unhandled exceptions mark the task state as `FAILURE`. Using `bind=True`, a task can catch expected exceptions and call `self.retry(exc=e, countdown=delay, max_retries=3)`. Unhandled exceptions can also be captured by error monitoring tools like Sentry.

---

## 13. Summary

- Celery decouples slow, resource-heavy operations from the synchronous HTTP request-response cycle.
- Uses Redis or RabbitMQ as the message broker.
- Always pass primitive arguments (`id`) instead of model instances.
- Celery Beat provides cron-like scheduling for recurring periodic tasks.
