# 5. Logging and Error Monitoring

## 1. Introduction

In production, `DEBUG = False`. When an unexpected error occurs, users see a generic `500 Server Error` page. Without structured **Logging** and **Error Monitoring**, developers have no visibility into what broke, who was affected, or how to reproduce the bug.

---

## 2. Why Do We Need It?

- Print statements (`print()`) vanish into standard output and do not provide timestamps, log levels, file names, or stack traces.
- Centralized logging records security events, performance anomalies, and payment failures to permanent files.
- Real-time exception tracking platforms (like Sentry) alert developers instantly via Slack or email when unhandled exceptions occur in production.

---

## 3. How It Works

Django's logging framework uses Python's built-in `logging` module configured via a dictionary (`LOGGING`) in `settings.py`:
1. **Loggers:** Entry points where code sends messages (`logger.info()`, `logger.error()`).
2. **Handlers:** Destinations for log messages (Console, Rotating File, Email, Syslog).
3. **Formatters:** Define the output text format (e.g., `[%(asctime)s] %(levelname)s %(message)s`).
4. **Filters:** Conditional control over which records pass from logger to handler (e.g., `RequireDebugFalse`).

---

## 4. Syntax

```python
# File: settings.py
LOGGING = {
    'version': 1,
    'disable_existing_loggers': False,
    'formatters': {
        'verbose': {
            'format': '[{asctime}] {levelname} [{name}:{lineno}] {message}',
            'style': '{',
        },
    },
    'handlers': {
        'console': {
            'class': 'logging.StreamHandler',
            'formatter': 'verbose',
        },
        'file': {
            'class': 'logging.handlers.RotatingFileHandler',
            'filename': BASE_DIR / 'logs/django.log',
            'maxBytes': 1024 * 1024 * 5,  # 5 MB
            'backupCount': 5,
            'formatter': 'verbose',
        },
    },
    'loggers': {
        'django': {
            'handlers': ['console', 'file'],
            'level': 'INFO',
            'propagate': True,
        },
    },
}
```

---

## 5. Practical Examples

### 1. Using Loggers in Views and Services
```python
# File: payments/services.py
import logging

# Create logger named after current module
logger = logging.getLogger(__name__)

def process_stripe_charge(user, amount_cents):
    logger.info(f"Initiating charge of ${amount_cents / 100:.2f} for user_id={user.id}")
    try:
        # Call Stripe API
        charge = stripe.Charge.create(...)
        logger.info(f"Payment successful: charge_id={charge.id} for user_id={user.id}")
        return charge
    except stripe.error.CardError as e:
        logger.warning(f"Card declined for user_id={user.id}: {e.user_message}")
        raise
    except Exception as e:
        # logger.exception automatically captures full traceback!
        logger.exception(f"Unexpected payment failure for user_id={user.id}")
        raise
```

### 2. Sentry Production Integration
```python
# File: settings.py
import sentry_sdk

sentry_sdk.init(
    dsn=os.environ.get("SENTRY_DSN"),
    traces_sample_rate=1.0,
    profiles_sample_rate=1.0,
)
```

---

## 6. Code Explanation

- `logging.getLogger(__name__)`: Idiomatic way to instantiate loggers. Names the logger after the current module hierarchy (e.g., `payments.services`).
- `logger.exception()`: Must be called inside an `except` block. Automatically attaches the entire stack trace to the log message.
- `RotatingFileHandler`: Prevents log files from growing infinitely and consuming disk space. Rotates files when they hit `maxBytes` (keeps 5 backup archives).
- Log levels: `DEBUG` < `INFO` < `WARNING` < `ERROR` < `CRITICAL`.

## 8. Real-World Use Case

**PCI-DSS and Security Compliance Audit Trails:**
Logging every failed login attempt, password reset, and administrative privilege change with IP address and timestamp. Enables forensic investigation in case of suspected security breaches.

---

## 9. Common Mistakes

1. **Logging Sensitive Data (PII):** Never log credit card numbers, passwords, CVVs, or auth tokens.
2. **Using `print()` in Production:** `print()` does not write to rotating logs, lacks log levels, and hurts I/O performance.
3. **Neglecting Log Rotation:** Writing to a single unbounded log file eventually exhausts production disk space, crashing the server.

---

## 10. Best Practices

- Use `logger.exception()` in `except` blocks instead of `logger.error(str(e))` to retain full tracebacks.
- Store log files in a dedicated directory ignored by Git (`logs/`).
- Use structured JSON logging in containerized environments (Docker/Kubernetes).
- Integrate Sentry or Datadog for real-time alerting on `ERROR` and `CRITICAL` events.

## 12. Interview Questions

**Q1: What are the four core components of Python's logging module and how do they interact?**
*Answer:* The four components are:
1. **Loggers:** The entry points exposed to application code (`logger.info`).
2. **Handlers:** Direct log records to specific destinations (console, disk files, syslog, sockets).
3. **Filters:** Provide fine-grained control to filter or alter records before they reach handlers.
4. **Formatters:** Specify the exact string layout and metadata of the final log message.
A logger receives a message, evaluates its level, passes it through filters, and dispatches it to attached handlers, which format and output it.

**Q2: Why should you never use `print()` statements for debugging or tracking in production Django applications?**
*Answer:* `print()` lacks log severity levels, timestamps, source location (file/line), and configuration flexibility. It writes directly to standard output, cannot be silenced or redirected without code changes, offers no file rotation (risking disk exhaustion), and cannot integrate with modern monitoring tools like Sentry or Datadog.

---

## 13. Summary

- Replace `print()` with Python's standard `logging` module.
- Configure `LOGGING` dictConfig in `settings.py` with handlers, formatters, and loggers.
- Use `RotatingFileHandler` to avoid unbounded disk consumption.
- Connect Sentry for automatic real-time error notifications in production.
