# 2. Database Optimization and Solving N+1 Queries

## 1. Introduction

The **N+1 Queries Problem** is the single most common performance killer in database-driven web applications. It occurs when an ORM executes 1 query to retrieve a list of $N$ parent records, and then executes $N$ additional individual queries to fetch related child records inside a template or loop. Django solves this with `select_related()` and `prefetch_related()`.

---

## 2. Why Do We Need It?

Imagine displaying 50 blog posts with their author names:
- **Without optimization:** 1 query for posts + 50 queries for authors = **51 database roundtrips**.
- At 10ms per roundtrip, the page takes over 500ms just waiting on database latency!
- **With `select_related('author')`:** **1 single SQL JOIN query** fetches all 50 posts and authors simultaneously in ~15ms.

---

## 3. How It Works

| Method | Relationship Type | SQL Mechanism |
|---|---|---|
| `select_related(*fields)` | `ForeignKey`, `OneToOneField` (Single-valued) | Executes SQL `INNER JOIN` or `LEFT OUTER JOIN` in a **single query**. |
| `prefetch_related(*lookups)` | `ManyToManyField`, Reverse `ForeignKey` (Multi-valued) | Executes **separate queries** (1 for parents, 1 per related model) and joins in Python memory. |
| `only(*fields)` / `defer(*fields)` | Model column selection | Restricts `SELECT` columns to reduce network bandwidth and memory footprint. |

---

## 4. Syntax

```python
# 1. Single-valued relationship (ForeignKey / OneToOne)
books = Book.objects.select_related('author', 'publisher').all()

# 2. Multi-valued relationship (ManyToManyField / reverse FK)
authors = Author.objects.prefetch_related('books', 'awards').all()

# 3. Custom Prefetch with filtering
from django.db.models import Prefetch
active_books = Prefetch('books', queryset=Book.objects.filter(is_active=True))
authors = Author.objects.prefetch_related(active_books).all()
```

## 5. Practical Examples

### Diagnosing and Fixing N+1 in Django
```python
# Problematic View (Triggers N+1 Queries)
def bad_employee_list(request):
    employees = Employee.objects.all()  # 1 Query
    # In template: {% for e in employees %}{{ e.department.name }}{% endfor %}
    # Each e.department executes 1 additional query! Total: 1 + N queries
    return render(request, 'employees/list.html', {'employees': employees})

# Optimized View (Eliminates N+1)
def good_employee_list(request):
    employees = Employee.objects.select_related('department').prefetch_related('skills').all()
    # Exactly 2 queries:
    # 1. SELECT employee JOIN department
    # 2. SELECT skills WHERE employee_id IN (...)
    return render(request, 'employees/list.html', {'employees': employees})
```

---

## 6. Code Explanation

- `select_related('department')`: Performs an SQL `JOIN` on the `departments` table. The `employee.department` attributes are populated immediately during initial retrieval.
- `prefetch_related('skills')`: Runs a second query: `SELECT * FROM skills INNER JOIN employee_skills WHERE employee_id IN (1, 2, 3...)` and joins the Python objects in memory.
- `django-debug-toolbar`: Shows SQL count in your browser; look for duplicate identical queries with different IDs.

## 8. Real-World Use Case

**E-Commerce Product Catalog:**
Displaying 24 product cards on a home page where each product has a brand (`ForeignKey`), category (`ForeignKey`), and tags (`ManyToManyField`). `select_related('brand', 'category').prefetch_related('tags')` reduces database queries from ~75 queries down to exactly 2 queries.

---

## 9. Common Mistakes

1. **Using `select_related()` on ManyToMany:** `select_related` only works on single-valued relationships. Calling it on ManyToMany raises a `FieldError`.
2. **Calling `.all()` or `.filter()` in Templates:** Writing `{% for tag in product.tags.all %}` works with `prefetch_related`, but adding a filter like `product.tags.filter(active=True)` bypasses the prefetch cache and hits the database again!
3. **Over-Prefetching:** Fetching large unused relations consumes excessive application memory.

---

## 10. Best Practices

- Always install `django-debug-toolbar` or `django-silk` in local development to audit query counts.
- Use `select_related()` for `ForeignKey` and `OneToOneField`.
- Use `prefetch_related()` for `ManyToManyField` and reverse `ForeignKey`.
- Combine with `.only('id', 'name', 'price')` when dealing with wide tables containing text or BLOB columns.

## 12. Interview Questions

**Q1: How does `prefetch_related` work internally under the hood?**
*Answer:* `prefetch_related` executes two separate queries: first, it fetches the parent objects (`SELECT * FROM parent WHERE ...`). Next, it extracts all parent primary keys and executes a single query with an `IN` clause: `SELECT * FROM child WHERE parent_id IN (pk1, pk2, pk3, ...)`. Finally, Django matches the child records to their respective parent instances in Python memory.

**Q2: What is the difference between `defer()` and `only()`?**
*Answer:* `only(*fields)` instructs Django to load only the specified columns in the initial SQL query, deferring all other columns until explicitly accessed. `defer(*fields)` does the opposite: it loads all columns except the specified deferred columns (useful for heavy fields like `TextField` or JSON). Accessing a deferred field later triggers an individual SQL query.

---

## 13. Summary

- N+1 queries degrade performance by executing individual database queries inside loops.
- `select_related()` uses SQL `JOIN` for `ForeignKey` and `OneToOneField`.
- `prefetch_related()` uses multi-query batching with `IN` clauses for `ManyToManyField` and reverse relations.
- Audit queries with `django-debug-toolbar` and verify with `assertNumQueries()`.
