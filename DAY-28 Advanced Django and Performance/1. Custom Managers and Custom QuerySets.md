# 1. Custom Managers and Custom QuerySets

## 1. Introduction

Every Django model comes equipped with a default manager named `objects` (`models.Manager`). While `objects.all()` and `objects.filter()` provide standard ORM access, enterprise applications often encapsulate complex business queries and domain rules directly inside **Custom Model Managers** and **Custom QuerySets**.

---

## 2. Why Do We Need It?

Without custom managers:
- Business query logic (e.g., active accounts, published articles, high-priority tickets) is duplicated across views, forms, and API serializers (violating DRY).
- Complex multi-clause filters make views cluttered and hard to test.
- Soft-delete patterns require filtering `is_deleted=False` in every single view manually.

---

## 3. How It Works

1. **Custom QuerySet:** Subclass `models.QuerySet` to define chainable query methods (e.g., `Article.objects.published().by_author(user)`).
2. **`as_manager()`:** Django provides `CustomQuerySet.as_manager()` to automatically expose chainable QuerySet methods directly on the model manager.
3. **Custom Manager:** Subclass `models.Manager` to alter the base queryset returned by overriding `get_queryset()`, or to add table-level creation helpers (like `create_user()` in `UserManager`).

---

## 4. Syntax

```python
# File: blog/models.py
from django.db import models

class ArticleQuerySet(models.QuerySet):
    def published(self):
        return self.filter(status='published')
    
    def featured(self):
        return self.filter(is_featured=True)

class Article(models.Model):
    STATUS_CHOICES = [('draft', 'Draft'), ('published', 'Published')]
    title = models.CharField(max_length=200)
    status = models.CharField(max_length=20, choices=STATUS_CHOICES, default='draft')
    is_featured = models.BooleanField(default=False)
    
    # Attach custom manager built from QuerySet
    objects = ArticleQuerySet.as_manager()
```

## 5. Practical Examples

### Soft-Delete Pattern with Custom Manager
```python
# File: core/models.py
from django.db import models
from django.utils import timezone

class SoftDeleteQuerySet(models.QuerySet):
    def delete(self):
        # Soft delete: update deleted_at instead of SQL DELETE
        return self.update(deleted_at=timezone.now())
    
    def hard_delete(self):
        # Permanent SQL DELETE
        return super().delete()

class ActiveManager(models.Manager):
    def get_queryset(self):
        # Filter out soft-deleted records by default
        return SoftDeleteQuerySet(self.model, using=self._db).filter(deleted_at__isnull=True)

class SoftDeleteModel(models.Model):
    deleted_at = models.DateTimeField(null=True, blank=True)
    
    objects = ActiveManager()          # Default: hides soft-deleted records
    all_objects = models.Manager()      # Fallback: access all records including deleted

    class Meta:
        abstract = True

    def delete(self, using=None, keep_parents=False):
        self.deleted_at = timezone.now()
        self.save()
```

---

## 6. Code Explanation

- `ArticleQuerySet.as_manager()`: Creates an instance of `Manager` that proxies all custom methods from `ArticleQuerySet`, allowing seamless chaining such as `Article.objects.published().featured()`.
- `ActiveManager.get_queryset()`: Overrides the base queryset. Whenever `SoftDeleteModel.objects.all()` is called, Django silently adds `WHERE deleted_at IS NULL`.
- `all_objects`: Always keep a secondary unadulterated `models.Manager()` for administrative queries or data auditing.

## 8. Real-World Use Case

**SaaS Multi-Tenancy / Soft-Delete:**
In compliance-heavy domains (banking, healthcare, HR), records must never be physically purged from the database. Custom soft-delete managers ensure developers cannot accidentally display deleted records to end-users while retaining audit trails for legal discovery.

---

## 9. Common Mistakes

1. **Renaming Default Manager Without Care:** Overriding `objects` with a filtered manager can cause issues with Django Admin or dumpdata. Always provide an unrestricted manager or set `base_manager_name`.
2. **Missing Chaining:** Defining methods on `models.Manager` instead of `models.QuerySet` prevents chaining (`Article.objects.published().featured()` fails if defined on Manager alone).
3. **Circular Dependencies:** Importing views or serializers inside custom managers.

---

## 10. Best Practices

- Define domain query logic in `models.QuerySet` and expose via `.as_manager()`.
- Keep manager methods focused strictly on database queries; avoid side effects like sending emails.
- Name query methods with clear verbs or states: `active()`, `pending()`, `overdue()`.

## 12. Interview Questions

**Q1: Why should you prefer `QuerySet.as_manager()` over subclassing `models.Manager`?**
*Answer:* When you add methods to a custom `Manager`, they are only available on the top-level manager (e.g., `Article.objects.published()`). However, you cannot chain them with other query operations (e.g., `Article.objects.filter(year=2026).published()` would raise an `AttributeError`). By defining methods on a custom `QuerySet` and calling `as_manager()`, Django copies the methods to both the manager and returned querysets, enabling full chaining.

**Q2: What happens if your custom manager filters out records in `get_queryset()` when executing foreign key lookups?**
*Answer:* In Django, reverse relations and foreign key lookups use the default manager of the related model unless `base_manager_name` is explicitly configured. If your default manager filters records, related objects may appear missing or raise `ObjectDoesNotExist`. To avoid this, set `Meta.base_manager_name = 'all_objects'`.

---

## 13. Summary

- Custom Managers and QuerySets encapsulate database queries into reusable domain methods.
- Define query logic in `models.QuerySet` and use `.as_manager()` for full chainability.
- Soft delete patterns rely on overriding `get_queryset()` to exclude deleted records.
