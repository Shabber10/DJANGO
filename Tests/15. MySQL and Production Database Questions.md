## Section A: Multiple-Choice Questions

#### Q1. Why is MySQL character set `utf8mb4` mandatory instead of standard MySQL `utf8`?
- [ ] **A**. Standard `utf8` is 50% slower.
- [ ] **B**. MySQL's legacy `utf8` only supports 3 bytes per character, causing crashes when storing 4-byte Unicode characters like emojis.
- [ ] **C**. `utf8mb4` encrypts database tables automatically.
- [ ] **D**. `utf8` is deprecated in Python.

**Answer:** B. MySQL's legacy `utf8` only supports 3 bytes per character, causing crashes when storing 4-byte Unicode characters like emojis.  
*Explanation:* Legacy MySQL `utf8` implemented a flawed 3-byte encoding. `utf8mb4` implements genuine UTF-8 supporting all 4-byte characters (emojis, complex symbols, non-Latin scripts).

#### Q2. What is the purpose of `CONN_MAX_AGE` in Django's database settings?
- [ ] **A**. Deletes rows older than a specified number of seconds.
- [ ] **B**. Enables persistent database connections, reusing TCP sockets across multiple HTTP requests instead of reconnecting on every request.
- [ ] **C**. Configures MySQL query cache size.
- [ ] **D**. Sets the user login session expiration.

**Answer:** B. Enables persistent database connections, reusing TCP sockets across multiple HTTP requests instead of reconnecting on every request.  
*Explanation:* Opening database connections incurs network and TLS latency. `CONN_MAX_AGE = 600` keeps connections alive for 10 minutes, significantly improving throughput.

#### Q3. What happens if an unhandled exception is raised inside a `with transaction.atomic():` block?
- [ ] **A**. Django commits changes made up to the point of the error.
- [ ] **B**. Django rolls back all database operations executed inside that atomic block.
- [ ] **C**. The database server restarts.
- [ ] **D**. The application pauses until an administrator confirms the change.

**Answer:** B. Django rolls back all database operations executed inside that atomic block.  
*Explanation:* `transaction.atomic()` provides an all-or-nothing guarantee. Uncaught exceptions automatically trigger an SQL `ROLLBACK`.

#### Q4. Which ORM method executes an SQL `SELECT ... FOR UPDATE` row-level lock?
- [ ] **A**. `.lock_rows()`
- [ ] **B**. `.select_for_update()`
- [ ] **C**. `.acquire_lock()`
- [ ] **D**. `.pessimistic_lock()`

**Answer:** B. `.select_for_update()`  
*Explanation:* `.select_for_update()` locks selected rows until the current transaction commits or rolls back, preventing concurrent processes from modifying them.

#### Q5. Which flag must always be passed to `mysqldump` when backing up production InnoDB tables without blocking active web traffic?
- [ ] **A**. `--force`
- [ ] **B**. `--single-transaction`
- [ ] **C**. `--lock-all-tables`
- [ ] **D**. `--no-data`

**Answer:** B. `--single-transaction`  
*Explanation:* `--single-transaction` executes the dump inside an isolated snapshot transaction without placing table-level read locks, allowing uninterrupted live read and write traffic.

## Section B: Conceptual and Scenario-Based Questions

#### Scenario 1: Preventing Deadlocks and Concurrency Glitches
**Question:** Explain how a deadlock occurs in MySQL when two concurrent transactions attempt to lock the same resources in reverse order, and detail two architectural strategies to avoid deadlocks.

**Model Answer:**
- **Deadlock Mechanism:**
  - Transaction 1 locks Employee Row A, then attempts to lock Employee Row B.
  - Transaction 2 locks Employee Row B, then attempts to lock Employee Row A.
  - Both transactions block waiting on each other indefinitely. MySQL detects the cycle and forcibly terminates one transaction with `Deadlock found when trying to get lock`.
- **Mitigation Strategies:**
  1. **Strict Ordering:** Always acquire row locks in a consistent, deterministic order across all application code (e.g., sort primary keys: `lock_accounts = Account.objects.filter(id__in=[id1, id2]).order_by('id').select_for_update()`).
  2. **Short Atomic Blocks:** Keep transactions brief; never make external network calls or perform heavy calculations inside transaction locks.

#### Exercise 1: Atomic Balance Transfer with Row-Level Locking
**Problem Statement:** Write a Python function `transfer_leave_days(sender_emp_id, receiver_emp_id, days)` that:
1. Wraps execution inside `transaction.atomic()`.
2. Locks both employee leave records using `select_for_update()`.
3. Validates sender has sufficient leave days.
4. Deducts from sender, credits receiver, and logs the transfer.

```python
# Write your solution code here
```

**Correct Code Solution:**
```python
from django.db import transaction
from django.core.exceptions import ValidationError
from apps.employees.models import Employee

def transfer_leave_days(sender_id, receiver_id, days):
    if days <= 0:
        raise ValidationError("Days transferred must be greater than zero.")
        
    with transaction.atomic():
        # Order by ID to prevent deadlocks:
        ids = sorted([sender_id, receiver_id])
        locked_employees = {
            emp.id: emp for emp in 
            Employee.objects.select_for_update().filter(id__in=ids)
        }
        
        sender = locked_employees.get(sender_id)
        receiver = locked_employees.get(receiver_id)

        if not sender or not receiver:
            raise ValidationError("One or both employees do not exist.")

        if sender.leave_balance < days:
            raise ValidationError(f"Insufficient leave balance. Available: {sender.leave_balance}")

        sender.leave_balance -= days
        receiver.leave_balance += days

        sender.save(update_fields=['leave_balance'])
        receiver.save(update_fields=['leave_balance'])

    return True
```

## Section D: Debugging Tasks

#### Task 1: Triggering Celery Tasks Inside Uncommitted Transactions
**Buggy Code Snippet:**
```python
def hire_employee_view(request):
    with transaction.atomic():
        emp = form.save()
        # Dispatching background task immediately:
        send_welcome_email_task.delay(emp.id)  # Celery worker raises ObjectDoesNotExist!
```

**Bug Explanation:**  
The Celery worker picks up the task immediately and queries the database *before* the outer transaction commits to disk. The worker cannot see the newly created employee and crashes.

**Fixed Code Solution:**
```python
# Use transaction.on_commit to trigger after successful commit:
def hire_employee_view(request):
    with transaction.atomic():
        emp = form.save()
        transaction.on_commit(lambda: send_welcome_email_task.delay(emp.id))
```
