## Section A: Multiple-Choice Questions

#### Q1. When does a standard Middleware function execute code on the response path?
- [ ] **A**. Before calling `response = self.get_response(request)`
- [ ] **B**. After calling `response = self.get_response(request)`
- [ ] **C**. Only inside `__init__()`
- [ ] **D**. Inside the view function

**Answer:** B. After calling `response = self.get_response(request)`  
*Explanation:* Code written before `response = self.get_response(request)` executes on the incoming request path. Code written after that line executes on the outgoing response path before sending data back to the client.

#### Q2. Why is middleware ordering in `settings.py` critical?
- [ ] **A**. Middleware order determines which database runs migrations first.
- [ ] **B**. Middleware executes from top-to-bottom on requests, and bottom-to-top on responses. Downstream middleware relies on upstream middleware (e.g., `AuthenticationMiddleware` requires `SessionMiddleware`).
- [ ] **C**. Middleware order has no effect in modern Django.
- [ ] **D**. Bottom-to-top ordering applies to both requests and responses.

**Answer:** B. Middleware executes from top-to-bottom on requests, and bottom-to-top on responses. Downstream middleware relies on upstream middleware.  
*Explanation:* `SessionMiddleware` populates `request.session`. `AuthenticationMiddleware` reads `request.session` to find the user ID and attach `request.user`. If `AuthenticationMiddleware` were placed above `SessionMiddleware`, it would crash.

#### Q3. Which signal is fired immediately after a model instance is saved to the database?
- [ ] **A**. `pre_save`
- [ ] **B**. `post_save`
- [ ] **C**. `post_commit`
- [ ] **D**. `model_saved`

**Answer:** B. `post_save`  
*Explanation:* `django.db.models.signals.post_save` is dispatched immediately after a model's `save()` method finishes executing. It passes `instance`, `created` (boolean indicating if a new row was inserted), and `using`.

#### Q4. Where should signal receiver connections be placed so they reliably register when Django starts?
- [ ] **A**. Inside `settings.py`
- [ ] **B**. Inside the application's `AppConfig.ready()` method
- [ ] **C**. Inside `models.py` at the very top
- [ ] **D**. Inside `urls.py`

**Answer:** B. Inside the application's `AppConfig.ready()` method  
*Explanation:* The recommended Django pattern is to define receivers in `signals.py` and import them inside `apps.py` within `AppConfig.ready()`, avoiding circular imports and guaranteeing registration during app initialization.

#### Q5. What happens if a signal receiver raises an unhandled exception during `post_save`?
- [ ] **A**. Django silently ignores the error.
- [ ] **B**. The exception propagates up and aborts the view execution, rolling back atomic transactions.
- [ ] **C**. The signal retries 3 times.
- [ ] **D**. Django logs a warning and continues.

**Answer:** B. The exception propagates up and aborts the view execution, rolling back atomic transactions.  
*Explanation:* Standard Django signals run synchronously in the same thread and execution context as the caller. Any unhandled exception halts execution.

## Section B: Conceptual and Scenario-Based Questions

#### Scenario 1: Request Execution Time Tracking Middleware
**Question:** Build a custom middleware `ExecutionTimeMiddleware` that measures the exact time taken to process an HTTP request, logs any requests taking longer than 500ms as warnings, and appends an `X-Page-Generation-Duration-ms` header to the HTTP response.

**Model Answer:**
```python
# File: apps/core/middleware.py
import time
import logging

logger = logging.getLogger(__name__)

class ExecutionTimeMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # 1. Incoming Request Path: Record start time
        start_time = time.perf_counter()

        # 2. Process downstream middleware and view
        response = self.get_response(request)

        # 3. Outgoing Response Path: Calculate elapsed duration
        duration_ms = (time.perf_counter() - start_time) * 1000.0

        if duration_ms > 500.0:
            logger.warning(
                f"Slow Request Detected: {request.method} {request.path} took {duration_ms:.2f}ms"
            )

        # Attach custom diagnostic header
        response['X-Page-Generation-Duration-ms'] = f"{duration_ms:.2f}"
        return response
```

#### Exercise 1: Automatic User Profile Creation via `post_save` Signal
**Problem Statement:** Write a signal receiver connected to `User` `post_save` that automatically creates an associated `Employee` profile record whenever a new `User` is registered with role `EMPLOYEE`.

```python
# Write your solution code here
```

**Correct Code Solution:**
```python
# File: apps/accounts/signals.py
from django.db.models.signals import post_save
from django.dispatch import receiver
from django.conf import settings
from apps.employees.models import Employee, Department

@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def create_employee_profile(sender, instance, created, **kwargs):
    if created and instance.role == 'EMPLOYEE':
        # Assign a default department if none exists
        default_dept, _ = Department.objects.get_or_create(
            code="GEN",
            defaults={'name': 'General Pool'}
        )
        Employee.objects.create(
            user=instance,
            department=default_dept,
            employee_id=f"EMP-{instance.id:04d}",
            designation="New Hire",
            salary=50000.00,
            hire_date=instance.date_joined.date()
        )
```

## Section D: Debugging Tasks

#### Task 1: Infinite Recursion Loop in `post_save` Signal
**Buggy Code Snippet:**
```python
@receiver(post_save, sender=Employee)
def update_employee_badge(sender, instance, created, **kwargs):
    if created:
        instance.employee_id = f"BADGE-{instance.id}"
        instance.save()  # Triggers RecursionError: maximum recursion depth exceeded!
```

**Bug Explanation:**  
Calling `instance.save()` inside a `post_save` receiver fires another `post_save` signal for the same instance, triggering an infinite recursive loop that crashes the server with `RecursionError`.

**Fixed Code Solution:**
```python
# Solution A: Use pre_save signal instead:
@receiver(pre_save, sender=Employee)
def set_badge_pre_save(sender, instance, **kwargs):
    if not instance.employee_id and instance.id:
        instance.employee_id = f"BADGE-{instance.id}"

# Solution B: Update database directly via QuerySet without triggering signals:
@receiver(post_save, sender=Employee)
def update_badge_post_save(sender, instance, created, **kwargs):
    if created and not instance.employee_id:
        Employee.objects.filter(pk=instance.pk).update(
            employee_id=f"BADGE-{instance.id}"
        )
```
