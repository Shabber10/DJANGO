## Section A: Multiple-Choice Questions

#### Q1. Which command displays the raw SQL statements that a migration will execute without applying them?
- [ ] **A**. `python manage.py showmigrations`
- [ ] **B**. `python manage.py sqlmigrate <app> <migration_number>`
- [ ] **C**. `python manage.py migrate --dry-run`
- [ ] **D**. `python manage.py viewsql <app>`

**Answer:** B. `python manage.py sqlmigrate <app> <migration_number>`  
*Explanation:* `sqlmigrate` outputs the exact database-specific SQL statements (e.g., MySQL or PostgreSQL syntax) that Django will execute when running that migration.

#### Q2. When should `select_related()` be used instead of `prefetch_related()`?
- [ ] **A**. For `ManyToManyField` relationships.
- [ ] **B**. For single-valued relationships (`ForeignKey` and `OneToOneField`).
- [ ] **C**. Only when using SQLite.
- [ ] **D**. Only when querying reverse relations.

**Answer:** B. For single-valued relationships (`ForeignKey` and `OneToOneField`).  
*Explanation:* `select_related()` executes a single SQL query using an `INNER JOIN` or `LEFT OUTER JOIN`. It only works on single-valued relationships. Multi-valued relationships (`ManyToManyField` and reverse `ForeignKey`) require `prefetch_related()`.

#### Q3. What is the effect of `on_delete=models.PROTECT` on a ForeignKey?
- [ ] **A**. Automatically cascades and deletes child rows.
- [ ] **B**. Sets the foreign key column to NULL.
- [ ] **C**. Prevents deletion of the referenced parent object by raising a `ProtectedError`.
- [ ] **D**. Reassigns child rows to the superuser.

**Answer:** C. Prevents deletion of the referenced parent object by raising a `ProtectedError`.  
*Explanation:* `PROTECT` ensures relational integrity by forbidding the deletion of a parent record as long as child records reference it.

#### Q4. Which `ModelAdmin` attribute specifies the columns displayed in the Django Admin list table?
- [ ] **A**. `fields`
- [ ] **B**. `list_display`
- [ ] **C**. `columns`
- [ ] **D**. `table_headers`

**Answer:** B. `list_display`  
*Explanation:* `list_display = ('name', 'code', 'created_at')` controls which fields or callable methods appear as columns on the admin changelist page.

#### Q5. How does `prefetch_related()` retrieve related objects under the hood?
- [ ] **A**. By running a single giant SQL JOIN.
- [ ] **B**. By executing separate queries with `IN (...)` clauses and joining the Python objects in memory.
- [ ] **C**. By creating temporary database views.
- [ ] **D**. By reading from a Redis cache.

**Answer:** B. By executing separate queries with `IN (...)` clauses and joining the Python objects in memory.  
*Explanation:* `prefetch_related` executes one query for the primary model, collects all related IDs, and runs a secondary query (`WHERE id IN (...)`) to fetch related records, assembling relationships in memory.

## Section B: Conceptual and Scenario-Based Questions

#### Scenario 1: Optimizing N+1 Queries in a Department Directory
**Question:** An HR directory displays 50 employees. Each card displays the employee's name, their department name, and all skills (`ManyToManyField`) they possess. Without optimization, this page triggers 101 queries. Write the optimized QuerySet and explain the query count reduction.

**Model Answer:**
```python
# Optimized QuerySet:
employees = (
    Employee.objects
    .select_related('user', 'department')
    .prefetch_related('skills')
    .all()
)
```
- **Query Count:** Exactly 2 SQL queries:
  1. `SELECT * FROM employee JOIN user JOIN department` (Fetches all 50 employees along with user and department data).
  2. `SELECT * FROM skills JOIN employee_skills WHERE employee_id IN (...)` (Fetches all skills for the 50 employees in one batch).
- Query count dropped from **101 queries to 2 queries**, reducing response time by 90%+.

#### Exercise 1: Custom ModelAdmin with Filters and Actions
**Problem Statement:** Register the `Employee` model in Django Admin with:
1. Columns: `employee_id`, full name, department, status, and hire date.
2. Filters: `status` and `department`.
3. Search: `employee_id`, `user__first_name`, and `user__last_name`.
4. Custom bulk action: Mark selected employees as `ACTIVE`.

```python
# Write your solution code here
```

**Correct Code Solution:**
```python
# File: apps/employees/admin.py
from django.contrib import admin
from .models import Employee

@admin.action(description="Mark selected employees as Active")
def make_active(modeladmin, request, queryset):
    updated = queryset.update(status='ACTIVE')
    modeladmin.message_user(request, f"{updated} employee(s) marked as active.")

@admin.register(Employee)
class EmployeeAdmin(admin.ModelAdmin):
    list_display = ('employee_id', 'get_full_name', 'department', 'status', 'hire_date')
    list_filter = ('status', 'department', 'hire_date')
    search_fields = ('employee_id', 'user__first_name', 'user__last_name', 'designation')
    actions = [make_active]

    @admin.display(description="Full Name", ordering='user__first_name')
    def get_full_name(self, obj):
        return obj.user.get_full_name()
```

## Section D: Debugging Tasks

#### Task 1: Reversing a Foreign Key Lookup
**Buggy Code Snippet:**
```python
# Department model has no explicit related_name on Employee foreign key:
dept = Department.objects.get(id=1)
# Trying to access employees:
emp_list = dept.employee_set()  # Raises TypeError: 'RelatedManager' object is not callable
```

**Bug Explanation:**  
`dept.employee_set` is a `RelatedManager`, not a function. You must call `.all()` or `.filter()` on it (`dept.employee_set.all()`), or configure `related_name='employees'` on the ForeignKey.

**Fixed Code Solution:**
```python
# Access via .all()
emp_list = dept.employee_set.all()

# Or define related_name on the model:
# department = models.ForeignKey(Department, on_delete=models.PROTECT, related_name='employees')
# Then access cleanly:
# emp_list = dept.employees.all()
```
