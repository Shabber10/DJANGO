## Section A: Multiple-Choice Questions

#### Q1. How does Django protect against SQL Injection vulnerabilities by default?
- [ ] **A**. It disables raw SQL queries completely.
- [ ] **B**. It compiles Python into C binary code.
- [ ] **C**. The ORM uses parameterized queries (prepared statements), ensuring parameters are quoted and escaped separately from SQL commands.
- [ ] **D**. It runs a regex filter on all HTTP strings.

**Answer:** C. The ORM uses parameterized queries (prepared statements), ensuring parameters are quoted and escaped separately from SQL commands.  
*Explanation:* Django ORM queries separate SQL command structure from user parameters. The database driver escapes input data, preventing SQL injection.

#### Q2. When is a Django view vulnerable to SQL Injection?
- [ ] **A**. When using `Employee.objects.filter(name=user_input)`
- [ ] **B**. When concatenating unvalidated strings directly into `raw()` or `extra()` SQL clauses (e.g. `raw(f"SELECT * FROM t WHERE id = {user_input}")`)
- [ ] **C**. When using `get_object_or_404()`
- [ ] **D**. When using `Q` objects

**Answer:** B. When concatenating unvalidated strings directly into `raw()` or `extra()` SQL clauses.  
*Explanation:* Using Python f-strings or string formatting inside `.raw()` bypasses parameterized query protection, introducing severe SQL injection vulnerabilities.

#### Q3. What is the purpose of Django's `XFrameOptionsMiddleware`?
- [ ] **A**. Prevents SQL Injection.
- [ ] **B**. Defends against Clickjacking attacks by emitting the `X-Frame-Options: DENY` HTTP header to prevent framing by malicious sites.
- [ ] **C**. Compresses PNG and JPEG images.
- [ ] **D**. Validates email domain DNS records.

**Answer:** B. Defends against Clickjacking attacks by emitting the `X-Frame-Options: DENY` HTTP header.  
*Explanation:* `XFrameOptionsMiddleware` instructs modern browsers not to allow the website to be embedded inside an `<iframe crossorigin>`, mitigating clickjacking.

#### Q4. Which template filter should NEVER be applied to untrusted user-submitted text?
- [ ] **A**. `|safe`
- [ ] **B**. `|escape`
- [ ] **C**. `|lower`
- [ ] **D**. `|truncatewords:20`

**Answer:** A. `|safe`  
*Explanation:* Django automatically HTML-escapes all template variables. Applying the `|safe` filter disables this auto-escaping, opening the application to Stored Cross-Site Scripting (XSS) if user input contains `<script>` tags.

#### Q5. What does the command `python manage.py check --deploy` do?
- [ ] **A**. Uploads your project to AWS or Heroku.
- [ ] **B**. Audits your active settings for critical security misconfigurations before production deployment.
- [ ] **C**. Installs missing packages from `requirements.txt`.
- [ ] **D**. Deletes all inactive user sessions.

**Answer:** B. Audits your active settings for critical security misconfigurations before production deployment.  
*Explanation:* `check --deploy` validates security flags like `SECURE_SSL_REDIRECT`, `CSRF_COOKIE_SECURE`, `SESSION_COOKIE_SECURE`, and `DEBUG = False`.

## Section B: Conceptual and Scenario-Based Questions

#### Scenario 1: Cross-Site Request Forgery (CSRF) Anatomy and Defense
**Question:** Explain the step-by-step mechanism of a Cross-Site Request Forgery (CSRF) attack on a bank fund transfer view, and detail how Django's CSRF token mechanism neutralizes the attack.

**Model Answer:**
1. **The Attack:**
   - User logs into `bank.com` and receives a valid session cookie.
   - Without logging out, the user visits malicious site `evil.com`.
   - `evil.com` executes a hidden JavaScript `POST` request to `https://bank.com/transfer/` with parameters `to_account=attacker&amount=1000`.
   - The browser automatically attaches the user's `bank.com` session cookies to the request. Without CSRF defense, the server executes the transfer.
2. **Django's Defense:**
   - Django uses the **Synchronizer Token Pattern**.
   - When rendering forms, Django embeds a cryptographically generated, random secret token in a hidden input (`{% csrf_token %}`) and sets a matching cookie.
   - When a POST request arrives, `CsrfViewMiddleware` verifies that the submitted form token matches the cookie token.
   - Because `evil.com` cannot read cross-origin cookies due to the browser's Same-Origin Policy (SOP), it cannot forge the hidden form token. Django rejects the request with HTTP 403 Forbidden.

## Section C: Practical Coding Exercises

#### Exercise 1: Secure Production Security Headers Configuration
**Problem Statement:** Write the production security settings block in `settings.py` that configures SSL redirection, secure cookies, HSTS for 1 year, and frame denial when `DEBUG = False`.

```python
# Write your solution code here
```

**Correct Code Solution:**
```python
# File: settings.py
if not DEBUG:
    # Force HTTPS
    SECURE_SSL_REDIRECT = True
    
    # Secure Cookies (Only transmitted over HTTPS)
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    
    # HTTP Strict Transport Security (HSTS)
    SECURE_HSTS_SECONDS = 31536000  # 1 Year
    SECURE_HSTS_INCLUDE_SUBDOMAINS = True
    SECURE_HSTS_PRELOAD = True
    
    # Browser defense headers
    SECURE_BROWSER_XSS_FILTER = True
    SECURE_CONTENT_TYPE_NOSNIFF = True
    X_FRAME_OPTIONS = 'DENY'
```

## Section D: Debugging Tasks

#### Task 1: Dangerous Raw SQL Injection
**Buggy Code Snippet:**
```python
def search_users(request):
    query = request.GET.get('q', '')
    # Vulnerable to SQL Injection:
    users = User.objects.raw(f"SELECT * FROM auth_user WHERE username = '{query}'")
    return render(request, 'users.html', {'users': users})
```

**Bug Explanation:**  
An attacker can pass `?q=' OR '1'='1` to dump all user records or execute destructive queries. String concatenation in `raw()` bypasses SQL parameterization.

**Fixed Code Solution:**
```python
# Fix A: Use standard ORM (Parameterized automatically)
users = User.objects.filter(username=query)

# Fix B: If raw SQL is required, pass parameters as a list/tuple:
users = User.objects.raw("SELECT * FROM auth_user WHERE username = %s", [query])
```
