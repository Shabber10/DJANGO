# 2. Defending Against CSRF, XSS, and SQL Injection

## 1. Introduction

The three most notorious web vulnerabilities are **Cross-Site Request Forgery (CSRF)**, **Cross-Site Scripting (XSS)**, and **SQL Injection (SQLi)**. Understanding how these attacks operate and how Django systematically neutralizes them is fundamental knowledge for any professional backend engineer.

---

## 2. Why Do We Need It?

- **CSRF:** Tricks an authenticated user's browser into executing unwanted actions (e.g., transferring funds or changing passwords) on a trusted site where they are logged in.
- **XSS:** Injects malicious JavaScript into web pages viewed by other users, allowing attackers to steal session tokens or log keystrokes.
- **SQLi:** Manipulates raw SQL query strings to read, modify, or drop database tables.

---

## 3. How It Works

### Django's Triple Defense:
1. **CSRF Protection:**
   - Every POST form requires `{% csrf_token %}`.
   - Django generates a secret token stored in a cookie (`csrftoken`).
   - `CsrfViewMiddleware` verifies that the submitted form token matches the cookie token.
2. **XSS Protection:**
   - DTL automatically escapes special HTML characters: `<` becomes `&lt;`, `>` becomes `&gt;`, `&` becomes `&amp;`, `"` becomes `&quot;`.
3. **SQLi Protection:**
   - ORM translates lookups into parameterized queries: `SELECT * FROM users WHERE name = %s;`, passing input as raw parameters that the SQL engine cannot execute as code.

---

## 4. Syntax

```html
<!-- CSRF Defense in Forms: -->
<form method="POST">
    {% csrf_token %}
    <input type="text" name="comment">
    <button type="submit">Submit</button>
</form>

<!-- XSS Defense in Templates (Automatic!): -->
<!-- If user submits: <script>alert('Hacked!')</script> -->
<!-- Django renders safe text: &lt;script&gt;alert('Hacked!')&lt;/script&gt; -->
<p>{{ comment.body }}</p>
```

```python
# SQL Injection Defense in Views:
# SAFE (Parameterized by ORM):
user = User.objects.filter(username=user_input)

# DANGEROUS / DO NOT DO THIS:
# user = User.objects.raw(f"SELECT * FROM auth_user WHERE username = '{user_input}'")
```

## 5. Practical Examples

### Handling CSRF in AJAX / Fetch API Calls
When sending POST requests from JavaScript:
```javascript
// Function to read CSRF cookie
function getCookie(name) {
    let cookieValue = null;
    if (document.cookie && document.cookie !== '') {
        const cookies = document.cookie.split(';');
        for (let i = 0; i < cookies.length; i++) {
            const cookie = cookies[i].trim();
            if (cookie.substring(0, name.length + 1) === (name + '=')) {
                cookieValue = decodeURIComponent(cookie.substring(name.length + 1));
                break;
            }
        }
    }
    return cookieValue;
}

// Attach header to fetch() call
fetch('/api/comments/', {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
        'X-CSRFToken': getCookie('csrftoken') // Validates CSRF in Django!
    },
    body: JSON.stringify({ text: "Great article!" })
});
```

---

## 6. Code Explanation

- `X-CSRFToken`: Django's `CsrfViewMiddleware` inspects both POST form bodies (`csrfmiddlewaretoken`) and the `X-CSRFToken` HTTP header, allowing JavaScript applications to communicate securely.
- HTML Escaping: Never use the `|safe` filter on user-submitted text!

---

## 7. Expected Output

If an external malicious site attempts to submit a POST form without a valid CSRF token:
```text
HTTP/1.1 403 Forbidden
Forbidden (403)
CSRF verification failed. Request aborted.
```

---

## 8. Real-World Use Case

Securing online banking transfer forms, preventing comment spam injection on social platforms, and protecting e-commerce checkout endpoints.

---

## 9. Common Mistakes

1. **Using `@csrf_exempt` carelessly:** Decorating views with `@csrf_exempt` disables CSRF protection entirely! Only use `@csrf_exempt` for external third-party webhooks (e.g. Stripe) that authenticate via cryptographic HMAC signatures.
2. Writing raw SQL with string interpolation (`f"SELECT ... {input}"`).

---

## 10. Best Practices

- Always include `{% csrf_token %}` inside POST forms.
- Never use the `|safe` filter on untrusted user-submitted text.
- Use parameterized queries if you must execute raw SQL (`raw("SELECT ... WHERE id = %s", [user_id])`).

## 12. Interview Questions

**Q1: How does Django's CSRF protection mechanism work under the hood?**  
*Answer:* Django uses a double-submit cookie pattern. When a user requests a page, Django sets a cryptographically random, masked token in a cookie (`csrftoken`) and injects the matching token into the form via `{% csrf_token %}`. When the form is submitted via POST, `CsrfViewMiddleware` compares the unmasked value of the submitted token against the unmasked value of the cookie. Because a malicious cross-origin site cannot read cookies from your domain due to the Same-Origin Policy, it cannot forge the matching token.

**Q2: How do you safely execute raw SQL queries in Django without risking SQL injection?**  
*Answer:* By using query parameterization (placeholders) rather than string formatting. Django's `.raw()` method and `cursor.execute()` accept parameters as a separate list:
```python
# SAFE:
cursor.execute("SELECT * FROM store_product WHERE price > %s", [min_price])
```
The database driver escapes the parameter as a literal value rather than executable code.

---

## 13. Summary

- CSRF is prevented via `{% csrf_token %}` and `CsrfViewMiddleware`.
- XSS is neutralized via automatic HTML escaping in templates.
- SQL injection is eliminated by ORM parameterized queries.
