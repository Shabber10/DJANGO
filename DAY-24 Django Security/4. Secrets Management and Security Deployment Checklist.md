# 4. Secrets Management and Security Deployment Checklist

## 1. Introduction

Deploying a Django application to production requires a rigorous security review. Exposing sensitive credentials or leaving development conveniences active can lead to immediate system compromise. Following a systematic **Deployment Security Checklist** ensures your application is hardened against attack.

---

## 2. Why Do We Need It?

- If `SECRET_KEY` is leaked, attackers can forge session cookies and impersonate any user, including superusers!
- Hardcoded database passwords in Git repositories are harvested by automated bots within minutes of being pushed.
- A checklist guarantees that all critical settings are audited before launch.

---

## 3. How It Works

### The Essential Production Security Checklist:
1. **`DEBUG = False`:** Never deploy with debug enabled.
2. **`SECRET_KEY` Isolation:** Loaded from environment variables, never hardcoded.
3. **`ALLOWED_HOSTS` Restriction:** Strict list of verified production domain names.
4. **Database Credentials:** Loaded via environment variables.
5. **HTTPS & Secure Cookies:** SSL redirect, Secure and HttpOnly cookies enabled.
6. **Admin URL Obfuscation:** Changing `/admin/` to a non-standard path.
7. **Static & Media Isolation:** Serving assets via WhiteNoise or S3, not Django.

---

## 4. Syntax

```python
# File: config/settings/production.py
import os
from pathlib import Path
from dotenv import load_dotenv

BASE_DIR = Path(__file__).resolve().parent.parent.parent
load_dotenv(BASE_DIR / '.env')

# 1. Debug MUST be False
DEBUG = False

# 2. Secret Key from Environment
SECRET_KEY = os.environ['SECRET_KEY']

# 3. Strict Allowed Hosts
ALLOWED_HOSTS = ['mycompany.com', 'www.mycompany.com']

# 4. HTTPS & Security Headers
SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SECURE_HSTS_SECONDS = 31536000
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True

# 5. Prevent MIME type sniffing
SECURE_CONTENT_TYPE_NOSNIFF = True

# 6. Clickjacking
X_FRAME_OPTIONS = 'DENY'
```

## 5. Practical Examples

### Generating a New Cryptographically Strong SECRET_KEY
In terminal:
```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
```
Output:
```text
django-insecure-8x(3j9@#k2!m0$v^b&*1q_p9z8y7x6w5v4u3t2s1r0q
```
Copy this generated secret directly into your production environment settings!

---

## 6. Code Explanation

- `get_random_secret_key()`: Django's official utility to generate a secure 50-character random string.
- `SECURE_CONTENT_TYPE_NOSNIFF = True`: Sets the `X-Content-Type-Options: nosniff` header, preventing browsers from incorrectly sniffing MIME types and executing malicious content disguised as text.

## 8. Real-World Use Case

Pre-deployment security reviews for banking platforms, healthcare patient portals, and SaaS applications before launching to public traffic.

---

## 9. Common Mistakes

1. **Pushing `.env` to GitHub:** Always verify `.gitignore` contains `.env` before running `git add .`!
2. Setting `ALLOWED_HOSTS = ['*']` in production (completely disables Host header validation).

---

## 10. Best Practices

- Use `python manage.py check --deploy` in CI/CD pipelines to block builds if security warnings exist.
- Rotate `SECRET_KEY` if ever compromised.
- Obfuscate the Django Admin URL in production.

## 12. Interview Questions

**Q1: What are the consequences of a compromised Django `SECRET_KEY`?**  
*Answer:* The `SECRET_KEY` is used for all cryptographic signing in Django:
- **Session Tampering:** Attackers can forge signed session cookies, allowing them to impersonate any user, including administrators.
- **Password Reset Forgery:** Attackers can forge password reset tokens and take over accounts.
- **Data Tampering:** Any signed data (messages, CSRF tokens, signed cookies) can be decrypted and modified.
If compromised, the `SECRET_KEY` must be rotated immediately and all sessions purged.

**Q2: What is the HTTP Host Header attack and how does `ALLOWED_HOSTS` prevent it?**  
*Answer:* In HTTP/1.1, the client sends a `Host` header indicating the target domain. Attackers can inject a malicious domain in this header (e.g. `Host: evil.com`). If Django used this unvalidated header to construct password reset email links (`request.build_absolute_uri()`), the password reset link would point to the attacker's server. `ALLOWED_HOSTS` validates incoming Host headers against a strict whitelist, dropping any spoofed requests with a `SuspiciousOperation` error.

---

## 13. Summary

- `SECRET_KEY` and credentials must come from environment variables.
- `DEBUG` must be `False` in production.
- `check --deploy` automates pre-launch security audits.
