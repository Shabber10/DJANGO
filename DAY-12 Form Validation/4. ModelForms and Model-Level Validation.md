# 4. ModelForms and Model-Level Validation

## 1. Introduction

In data-driven web applications, most forms map directly to database models. Writing a standard `Form` that manually duplicates all fields, validations, and choices already defined in a `Model` violates the DRY principle. Django provides **`ModelForm`** to automatically generate forms directly from Model definitions.

---

## 2. Why Do We Need It?

- **Eliminates Duplication:** You define fields, constraints, nullability, and choices once in `models.py`, and `ModelForm` generates the matching form fields and widgets automatically.
- **Direct Database Persistence:** Calling `form.save()` automatically inserts or updates the database record.

---

## 3. How It Works

A `ModelForm` inspects the specified Model class and:
1. Maps model field types (`models.CharField`, `models.EmailField`) to form field types (`forms.CharField`, `forms.EmailField`).
2. Adopts model constraints (`max_length`, `choices`, `blank=True`).
3. Provides a `.save()` method that instantiates and saves the model instance.

---

## 4. Syntax

```python
# File: store/models.py
from django.db import models

class Product(models.Model):
    name = models.CharField(max_length=200)
    description = models.TextField()
    price = models.DecimalField(max_digits=10, decimal_places=2)
    is_active = models.BooleanField(default=True)

# File: store/forms.py
from django import forms
from .models import Product

class ProductForm(forms.ModelForm):
    class Meta:
        model = Product
        fields = ['name', 'description', 'price', 'is_active']
        # Or: fields = '__all__'
        # Or: exclude = ['is_active']
```

---

## 5. Practical Examples

### Creating and Updating Records with ModelForm
```python
# File: store/views.py
from django.shortcuts import render, redirect, get_object_or_404
from .models import Product
from .forms import ProductForm

# Create View
def product_create(request):
    if request.method == "POST":
        form = ProductForm(request.POST)
        if form.is_valid():
            product = form.save() # Persists directly to database!
            return redirect('store:product_detail', pk=product.pk)
    else:
        form = ProductForm()
    return render(request, 'store/product_form.html', {'form': form})

# Update View (Pass existing instance!)
def product_update(request, pk):
    product = get_object_or_404(Product, pk=pk)
    if request.method == "POST":
        form = ProductForm(request.POST, instance=product)
        if form.is_valid():
            form.save() # Updates existing database record!
            return redirect('store:product_detail', pk=product.pk)
    else:
        form = ProductForm(instance=product) # Pre-populates inputs with current values!
    return render(request, 'store/product_form.html', {'form': form})
```

---

## 6. Code Explanation

- `class Meta`: Configures model form metadata (`model`, `fields`, `exclude`, `widgets`, `labels`).
- `form.save()`: Creates and persists a new model instance.
- `instance=product`: Informs the `ModelForm` that it is operating on an existing database record rather than creating a new one.
- `form.save(commit=False)`: Creates the model instance in memory without saving to the database immediately, allowing you to attach extra data (such as `product.author = request.user`) before saving.

---

## 7. Expected Output

When editing a product, the form renders with all current database values pre-populated inside the inputs. Submitting updates executes an SQL `UPDATE` statement.

---

## 8. Real-World Use Case

CRUD (Create, Read, Update, Delete) interfaces across all web applications: editing user profiles, updating blog posts, creating support tickets.

---

## 9. Common Mistakes

1. **Using `fields = '__all__'` carelessly:** Exposing internal fields (like `is_staff` or `account_balance`) allows malicious users to tamper with sensitive attributes via mass assignment. Explicitly list allowed fields!
2. Forgetting `instance=obj` when writing update views, which causes the form to create a new duplicate record instead of updating the existing one.

---

## 10. Best Practices

- Explicitly list allowed fields: `fields = ['title', 'content']`. Never use `'__all__'` on public forms.
- Use `commit=False` when you need to attach non-form data (like current user) before saving.

## 12. Interview Questions

**Q1: What does `form.save(commit=False)` do and when would you use it?**  
*Answer:* `form.save(commit=False)` constructs and validates the Model instance from cleaned form data without immediately committing the SQL `INSERT` to the database. It is used when you need to attach additional data not present in the form (e.g., `obj.created_by = request.user`) before calling `obj.save()` and `form.save_m2m()`.

**Q2: What is Mass Assignment vulnerability and how does Django `ModelForm` protect against it?**  
*Answer:* Mass assignment occurs when an attacker submits unexpected HTTP POST parameters that automatically overwrite sensitive model attributes. Django protects against this by strictly requiring developers to whitelist allowed fields via `fields = ['name', 'email']` in the `Meta` class, ignoring any unlisted parameters.

---

## 13. Summary

- `ModelForm` generates forms directly from Model definitions.
- `class Meta` declares `model` and `fields`.
- `form.save()` persists records; `instance=obj` handles updates.
