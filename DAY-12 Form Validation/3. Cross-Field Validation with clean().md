# 3. Cross-Field Validation with clean()

## 1. Introduction

Many validation rules depend on the combination of two or more fields—such as verifying that "Password" and "Confirm Password" match, or ensuring that "End Date" occurs after "Start Date". Because single-field cleaners only inspect one field in isolation, Django provides the **`clean()`** method for **Cross-Field Validation**.

---

## 2. Why Do We Need It?

Single-field validation runs independently. When validating a password confirmation, neither `clean_password()` nor `clean_confirm_password()` can guarantee the other field has finished validating without race conditions. Overriding the overall `clean()` method allows you to compare multiple fields after all individual field cleaners have succeeded.

---

## 3. How It Works

1. Django executes all individual field cleaners and populates `cleaned_data`.
2. Django invokes `form.clean()`.
3. Inside `clean()`, call `super().clean()` to retrieve the cleaned data dictionary.
4. Compare multiple fields.
5. If invalid, raise `ValidationError` (for form-wide non-field errors) or use `self.add_error('fieldname', error)` to bind the error to a specific input.
6. Return `cleaned_data`.

---

## 4. Syntax

```python
from django import forms
from django.core.exceptions import ValidationError

class PasswordChangeForm(forms.Form):
    new_password = forms.CharField(widget=forms.PasswordInput)
    confirm_password = forms.CharField(widget=forms.PasswordInput)

    def clean(self):
        cleaned_data = super().clean()
        password = cleaned_data.get('new_password')
        confirm = cleaned_data.get('confirm_password')

        if password and confirm and password != confirm:
            # Bind error directly to the confirm_password field
            self.add_error('confirm_password', "Passwords do not match.")
            
        return cleaned_data
```

## 5. Practical Examples

### Validating Date Ranges in Event Booking
```python
# File: bookings/forms.py
from django import forms
from django.core.exceptions import ValidationError

class RoomReservationForm(forms.Form):
    check_in = forms.DateField(widget=forms.DateInput(attrs={'type': 'date'}))
    check_out = forms.DateField(widget=forms.DateInput(attrs={'type': 'date'}))

    def clean(self):
        cleaned_data = super().clean()
        check_in = cleaned_data.get('check_in')
        check_out = cleaned_data.get('check_out')

        if check_in and check_out:
            if check_out <= check_in:
                raise ValidationError("Check-out date must be strictly after the check-in date.")
                
        return cleaned_data
```

---

## 6. Code Explanation

- `cleaned_data = super().clean()`: Retrieves the dictionary of cleaned values from all preceding individual field validations.
- `if check_in and check_out:`: Critical safety check! If one of the fields had an individual validation error (e.g., malformed date string), it will be `None`. Always check for existence before comparing!
- `self.add_error('fieldname', 'msg')`: Directs the error message to a specific field rather than making it a generic form-wide error.

---

## 7. Expected Output

If the user selects `check_in = Nov 10` and `check_out = Nov 5`:
The form raises a `ValidationError`, rendered in `{{ form.non_field_errors }}`:
```html
<ul class="errorlist nonfield">
    <li>Check-out date must be strictly after the check-in date.</li>
</ul>
```

## 8. Real-World Use Case

Comparing loan amounts against applicant monthly income, verifying password confirmation inputs, and ensuring flight departure dates precede return dates.

---

## 9. Common Mistakes

1. **Comparing fields without checking if they exist:**
   ```python
   # INCORRECT (Crashes if date was invalid):
   if check_out <= check_in: ... # TypeError: '<=' not supported between instances of 'NoneType' and 'NoneType'
   # CORRECT:
   if check_in and check_out: ...
   ```
2. Forgetting to return `cleaned_data` at the end of `clean()`.

---

## 10. Best Practices

- Always call `super().clean()` at the start of `clean()`.
- Use `self.add_error('field_name', 'message')` when the error is primarily the fault of a specific input.
- Always check that values are not `None` before comparing.

## 12. Interview Questions

**Q1: What is the difference between `self.add_error()` and raising `ValidationError` in `clean()`?**  
*Answer:* Raising `ValidationError` inside `clean()` generates a non-field error associated with the form as a whole, rendered via `form.non_field_errors`. Calling `self.add_error('field_name', 'message')` binds the error directly to that specific field, removing that field from `cleaned_data` and rendering the error alongside that input in the UI.

**Q2: What is the execution order of form validation methods in Django?**  
*Answer:*
1. Field's `to_python()` method (type coercion).
2. Field's `validate()` method (built-in field checks).
3. Field's `run_validators()` (callables in `validators=[...]`).
4. Custom method `clean_<fieldname>()`.
5. Form's overall `clean()` method (cross-field validation).

---

## 13. Summary

- `clean()` handles multi-field relationships and comparisons.
- Always check that values exist before comparing.
- Use `self.add_error()` to associate errors with specific fields.
