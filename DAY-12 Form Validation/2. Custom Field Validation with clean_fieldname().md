# 2. Custom Field Validation with clean_fieldname()

## 1. Introduction

While built-in validators cover general cases, business applications often require custom validation rules for individual fields—such as verifying that an email domain belongs to a company, checking that a username isn't reserved, or ensuring a value doesn't already exist in the database. In Django, this is achieved by defining **`clean_<fieldname>()`** methods.

---

## 2. Why Do We Need It?

- Validating business constraints: e.g., corporate emails must end with `@company.com`.
- Normalizing values: e.g., converting all submitted usernames to lowercase before saving.
- Raising targeted errors: Displaying errors directly next to the specific field being validated.

---

## 3. How It Works

When `form.is_valid()` executes:
1. Django runs the standard field cleaner and places the initial value in `self.cleaned_data`.
2. Django checks if the form class defines a method named `clean_<fieldname>()` (e.g. `clean_username()`).
3. If present, Django invokes it with zero arguments.
4. The method retrieves the field value from `self.cleaned_data.get('fieldname')`.
5. If invalid, it raises `forms.ValidationError("Error message")`.
6. If valid, **it MUST return the cleaned/normalized value**!

---

## 4. Syntax

```python
from django import forms
from django.core.exceptions import ValidationError

class RegistrationForm(forms.Form):
    username = forms.CharField(max_length=50)
    email = forms.EmailField()

    def clean_username(self):
        # 1. Retrieve the value
        username = self.cleaned_data.get('username')
        
        # 2. Perform custom business check
        reserved_names = ['admin', 'root', 'superuser', 'support']
        if username.lower() in reserved_names:
            raise ValidationError("This username is reserved by system administration.")
            
        # 3. Return the cleaned (or normalized) value
        return username.lower()
```

## 5. Practical Examples

### Validating Corporate Email Domains
```python
# File: corporate/forms.py
from django import forms
from django.core.exceptions import ValidationError

class EmployeeOnboardingForm(forms.Form):
    full_name = forms.CharField(max_length=100)
    work_email = forms.EmailField()

    def clean_work_email(self):
        email = self.cleaned_data.get('work_email')
        allowed_domain = 'company.com'
        
        if not email.endswith(f"@{allowed_domain}"):
            raise ValidationError(f"Registration restricted to official @{allowed_domain} email addresses.")
            
        return email.lower()
```

---

## 6. Code Explanation

- `clean_work_email(self)`: Named specifically after the field `work_email`.
- `raise ValidationError(...)`: Informs Django that this specific field failed validation. Django attaches the error to `form.errors['work_email']`.
- `return email.lower()`: **CRITICAL!** If you forget the return statement, the field value in `form.cleaned_data` will become `None`!

---

## 7. Expected Output

Submitting `work_email = "alice@gmail.com"`:
The form fails validation and renders:
```html
<ul class="errorlist">
    <li>Registration restricted to official @company.com email addresses.</li>
</ul>
```

---

## 8. Real-World Use Case

Preventing reserved handle takeovers (e.g., blocking users from registering usernames like `api`, `help`, `billing`, or `pricing` on SaaS platforms).

---

## 9. Common Mistakes

1. **Forgetting to return the cleaned value:**
   ```python
   # INCORRECT:
   def clean_email(self):
       email = self.cleaned_data.get('email')
       if not email: raise ValidationError(...)
       # Forgot return statement! Returns None!
   # CORRECT:
   def clean_email(self):
       ...
       return email
   ```

---

## 10. Best Practices

- Always return the value at the end of every `clean_<fieldname>()` method.
- Use `clean_<fieldname>()` to normalize data (e.g. converting to lowercase or stripping whitespace).

## 12. Interview Questions

**Q1: What is the most critical rule when writing a `clean_<fieldname>()` method?**  
*Answer:* You MUST return the cleaned/normalized value at the end of the method. If you do not explicitly return a value, Python returns `None`, which overwrites the valid field data in `form.cleaned_data` with `None`.

**Q2: How does `clean_<fieldname>()` differ from field validators?**  
*Answer:* Field validators (`validators=[...]`) are reusable standalone functions/classes that can be attached across multiple fields and models. `clean_<fieldname>()` is a method on a specific form class, allowing access to the form instance (`self`), other form attributes, or normalization logic tailored to that form.

---

## 13. Summary

- Define `clean_<fieldname>()` for single-field custom validation.
- Raise `forms.ValidationError` on failure.
- Always return the cleaned value.
