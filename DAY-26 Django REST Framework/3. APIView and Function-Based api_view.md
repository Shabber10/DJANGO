# 3. APIView and Function-Based api_view

## 1. Introduction

Django REST Framework provides two primary ways to author custom API endpoints: the **`@api_view`** decorator for Function-Based Views, and the **`APIView`** class for Class-Based Views. Unlike standard Django views that receive `HttpRequest` and return `HttpResponse`, DRF views receive DRF's enhanced **`Request`** object and return DRF's **`Response`** object.

---

## 2. Why Do We Need It?

- DRF's `Request` object automatically parses incoming JSON into `request.data`, regardless of whether the HTTP method is POST, PUT, or PATCH.
- DRF's `Response` object performs automated content negotiation, rendering JSON for API clients and HTML for browsers.
- Handles exceptions automatically, converting unhandled validation errors into structured JSON responses.

---

## 3. How It Works

- **`@api_view(['GET', 'POST'])`:** Wraps a Python function, providing DRF `Request`/`Response` capabilities.
- **`APIView`:** Subclasses Django's `View`. Exposes HTTP handlers (`get()`, `post()`, `put()`, `delete()`) and supports policy attributes (`permission_classes`, `authentication_classes`, `throttle_classes`).

---

## 4. Syntax

```python
# 1. Function-Based with @api_view:
from rest_framework.decorators import api_view
from rest_framework.response import Response
from rest_framework import status

@api_view(['GET', 'POST'])
def item_list(request):
    if request.method == 'GET':
        return Response({"items": ["Pen", "Pencil"]})
    elif request.method == 'POST':
        return Response({"created": request.data}, status=status.HTTP_201_CREATED)

# 2. Class-Based with APIView:
from rest_framework.views import APIView

class ItemListAPIView(APIView):
    def get(self, request):
        return Response({"items": ["Pen", "Pencil"]})

    def post(self, request):
        return Response({"created": request.data}, status=status.HTTP_201_CREATED)
```

## 5. Practical Examples

### Complete CRUD with APIView and Serializers
```python
# File: store/views.py
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from django.shortcuts import get_object_or_404
from .models import Product
from .serializers import ProductSerializer

class ProductListCreateAPIView(APIView):
    def get(self, request):
        products = Product.objects.all()
        serializer = ProductSerializer(products, many=True)
        return Response(serializer.data)

    def post(self, request):
        serializer = ProductSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data, status=status.HTTP_201_CREATED)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

class ProductDetailAPIView(APIView):
    def get(self, request, pk):
        product = get_object_or_404(Product, pk=pk)
        serializer = ProductSerializer(product)
        return Response(serializer.data)

    def put(self, request, pk):
        product = get_object_or_404(Product, pk=pk)
        serializer = ProductSerializer(product, data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data)
        return Response(serializer.errors, status=status.HTTP_400_BAD_REQUEST)

    def delete(self, request, pk):
        product = get_object_or_404(Product, pk=pk)
        product.delete()
        return Response(status=status.HTTP_204_NO_CONTENT)
```

---

## 6. Code Explanation

- `request.data`: Replaces `request.POST` and `json.loads(request.body)`. Parses JSON payloads, form data, and multi-part files transparently!
- `ProductSerializer(products, many=True)`: `many=True` is mandatory when serializing an iterable collection (QuerySet) rather than a single instance.
- `from rest_framework import status`: Provides named constants (`HTTP_200_OK`, `HTTP_201_CREATED`, `HTTP_400_BAD_REQUEST`) instead of magic numbers.

---

## 7. Expected Output

Posting invalid data to `/api/products/`:
```json
HTTP/1.1 400 Bad Request
Content-Type: application/json
{

  "price": ["Price must be strictly positive."]

```

## 8. Real-World Use Case

Custom authentication endpoints, complex multi-model aggregation services, analytics queries, and third-party webhook receivers.

---

## 9. Common Mistakes

1. **Forgetting `many=True` when serializing a QuerySet:** Raises `AttributeError: 'QuerySet' object has no attribute 'fieldname'`.
2. Using standard `HttpResponse` instead of DRF's `Response`.

---

## 10. Best Practices

- Always use `from rest_framework import status` for clean, readable status codes.
- Use `APIView` when you need full control over request handling logic.
- For standard database CRUD, proceed to **Generic Views** to reduce boilerplate.

## 12. Interview Questions

**Q1: How does DRF's `Request` object differ from Django's standard `HttpRequest`?**  
*Answer:* DRF wraps Django's standard `HttpRequest` inside an extended `Request` instance. Key differences include:
- `request.data`: Transparently parses JSON, XML, or form data for all HTTP methods (including PUT and PATCH).
- `request.query_params`: An alias for `request.GET` that uses RESTful terminology.
- `request.user`: Dynamically resolves authentication through configured authentication backends (Token, JWT).

**Q2: What is Content Negotiation in DRF's `Response` object?**  
*Answer:* Content negotiation is the process where DRF inspects the incoming request's `Accept` header and query parameters (e.g. `?format=json`) and matches them against the view's `renderer_classes`. If a browser requests the page, it renders the HTML Browsable API; if an API client requests `application/json`, it serializes and returns raw JSON.

---

## 13. Summary

- `@api_view` handles FBVs; `APIView` handles CBVs.
- `request.data` parses JSON payloads for all methods.
- `Response` handles automated content negotiation.
