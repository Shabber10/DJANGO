# 2. Django Session Framework

## 1. Introduction

To solve the security hazards of storing data directly in browser cookies, Django provides the **Session Framework**. Sessions allow you to store arbitrary, private user data on the server side, while the client's browser only holds a single random, cryptographically signed 32-character string known as the **Session ID** (`sessionid`).

---

## 2. Why Do We Need It?

- **Security:** Sensitive data (cart items, user authentication IDs) resides safely on the server and cannot be viewed or tampered with by the user.
- **Convenience:** The `request.session` object acts like a standard Python dictionary available inside any view.
- **Storage Backends:** Django can store session state in databases, high-speed in-memory caches (Redis), or encrypted files.

---

## 3. How It Works

1. Enabled via `'django.contrib.sessions'` in `INSTALLED_APPS` and `'django.contrib.sessions.middleware.SessionMiddleware'` in `MIDDLEWARE`.
2. When a user visits the site, Django checks for a `sessionid` cookie.
3. If missing, it creates a new session in the `django_session` table and issues a `sessionid` cookie.
4. In views, `request.session['key'] = value` stores data for that specific user.
5. Upon response delivery, Django serializes the session dictionary into the database.

---

## 4. Syntax

```python
# Working with request.session in views:
def add_to_cart(request, product_id):
    # Initialize cart list if not present
    cart = request.session.get('cart', [])
    cart.append(product_id)
    
    # Store back in session
    request.session['cart'] = cart
    
    # Crucial if modifying mutable objects (lists/dicts) in-place:
    request.session.modified = True
    
    return redirect('cart_view')

def cart_view(request):
    cart_items = request.session.get('cart', [])
    return render(request, 'cart.html', {'item_count': len(cart_items)})
```

---

## 5. Practical Examples

### Session Operations Reference
```python
# Setting values
request.session['has_seen_banner'] = True
request.session['preferred_currency'] = 'EUR'

# Reading values (with default fallback)
currency = request.session.get('preferred_currency', 'USD')

# Checking membership
if 'cart' in request.session:
    ...

# Deleting a specific key
del request.session['cart']

# Clearing all session data for user
request.session.flush()

# Setting session expiration (e.g., expires in 1 hour)
request.session.set_expiry(3600)
# Setting session to expire when the browser window closes:
request.session.set_expiry(0)
```

---

## 6. Code Explanation

- `request.session.modified = True`: Tells Django the session data was modified. When you append to a list inside a session in-place (`cart.append(...)`), Django's dictionary tracking doesn't automatically detect the change; setting `modified = True` guarantees the update is saved to the database.
- `request.session.flush()`: Deletes the current session data from both the database AND deletes the session cookie from the user's browser.
- `set_expiry(0)`: Creates a "browser-length" session that terminates as soon as the user closes their browser.

## 8. Real-World Use Case

Guest shopping carts, multi-step registration wizards, temporary OTP verification state, and authenticated login sessions.

---

## 9. Common Mistakes

1. **Modifying a mutable list or dict in session without setting `modified = True`:**
   ```python
   # INCORRECT (Changes may NOT be persisted to DB!):
   request.session['cart'].append(item_id)
   # CORRECT:
   cart = request.session.get('cart', [])
   cart.append(item_id)
   request.session['cart'] = cart
   request.session.modified = True
   ```
2. Storing non-JSON-serializable objects (like open file handles or model instances) in sessions.

---

## 10. Best Practices

- Only store JSON-serializable primitives (strings, numbers, lists, dicts) in `request.session`.
- In high-traffic production, use Redis as the session backend (`django.contrib.sessions.backends.cache`).
- Run `python manage.py clearsessions` periodically to purge expired rows from the database.

## 12. Interview Questions

**Q1: What are the available session backends in Django?**  
*Answer:* Django supports five session backends via `SESSION_ENGINE`:
1. `django.contrib.sessions.backends.db` (Default: stores sessions in SQL database).
2. `django.contrib.sessions.backends.cache` (Fast: stores sessions in Redis/Memcached).
3. `django.contrib.sessions.backends.cached_db` (Hybrid: writes to cache for fast reads, persists to DB for durability).
4. `django.contrib.sessions.backends.file` (Stores sessions in files on the server disk).
5. `django.contrib.sessions.backends.signed_cookies` (Stores cryptographically signed data directly in client cookies).

**Q2: What is the purpose of `request.session.flush()`?**  
*Answer:* `flush()` deletes the current session record from the server-side database/cache storage AND destroys the session cookie in the user's browser, completely resetting the user's session state. It is used during user logout to guarantee that session data cannot be hijacked or reused.

---

## 13. Summary

- Django Sessions store data safely on the server.
- The browser holds only an unguessable `sessionid` cookie.
- Use `request.session` as a dict; set `modified = True` on mutable changes.
