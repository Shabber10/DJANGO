# 2. WSGI, ASGI, Gunicorn, and Uvicorn

## 1. Introduction

Django applications are Python programs, but web servers (like Nginx, Apache, or Caddy) communicate using network protocols like HTTP. **WSGI (Web Server Gateway Interface)** and **ASGI (Asynchronous Server Gateway Interface)** are Python standards that bridge the gap between production web servers and Python web frameworks.

---

## 2. Why Do We Need It?

- High-traffic production websites need to process hundreds of requests concurrently across multiple CPU cores.
- **Gunicorn (Green Unicorn):** The industry-standard WSGI HTTP server for traditional synchronous Django applications.
- **Uvicorn:** A lightning-fast ASGI server powered by `uvloop` for asynchronous Django applications (WebSockets, Channels, async views).
- **Nginx:** Acts as a reverse proxy in front of Gunicorn to handle SSL termination, static file caching, and rate limiting.

---

## 3. How It Works

```text
[ Browser ] ---> HTTPS ---> [ Nginx Reverse Proxy (:443) ]
                                    |
                                    v (Unix Socket or :8000)
                            [ Gunicorn Master Process ]
                                    |
                        +-----------+-----------+
                        |                       |
                 [ Worker 1 (WSGI) ]     [ Worker 2 (WSGI) ]
                        |                       |
                [ Django App ]          [ Django App ]
```
- **Nginx:** Terminates SSL, buffers slow clients, serves static assets, and proxies requests.
- **Gunicorn Master:** Manages worker lifecycles, restarts crashed workers, and distributes incoming requests.
- **Workers:** Independent OS processes executing Python code. Recommended worker count: `(2 x CPU_Cores) + 1`.

---

## 4. Syntax

```bash
# 1. Installing Gunicorn
pip install gunicorn

# 2. Running Gunicorn locally or in container
gunicorn myproject.wsgi:application --bind 0.0.0.0:8000 --workers 3

# 3. Installing Uvicorn for ASGI
pip install uvicorn[standard]

# 4. Running Uvicorn for async Django
uvicorn myproject.asgi:application --host 0.0.0.0 --port 8000 --workers 3
```

## 5. Practical Examples

### 1. Systemd Service File for Gunicorn
```ini
# File: /etc/systemd/system/gunicorn.service
[Unit]
Description=gunicorn daemon for Django EMS
After=network.target

[Service]
User=ubuntu
Group=www-data
WorkingDirectory=/home/ubuntu/django-course-work
ExecStart=/home/ubuntu/venv/bin/gunicorn \
          --access-logfile /var/log/gunicorn/access.log \
          --error-logfile /var/log/gunicorn/error.log \
          --workers 3 \
          --bind unix:/run/gunicorn.sock \
          myproject.wsgi:application

[Install]
WantedBy=multi-user.target
```

### 2. Nginx Reverse Proxy Configuration
```nginx
# File: /etc/nginx/sites-available/ems
server {
    listen 80;
    server_name ems.mycompany.com;

    location /static/ {
        alias /home/ubuntu/django-course-work/staticfiles/;
    }

    location /media/ {
        alias /home/ubuntu/django-course-work/media/;
    }

    location / {
        include proxy_params;
        proxy_pass http://unix:/run/gunicorn.sock;
    }
}
```

---

## 6. Code Explanation

- `unix:/run/gunicorn.sock`: Unix domain sockets are faster than TCP network loopbacks (`127.0.0.1:8000`) because they bypass network routing overhead entirely.
- `--workers 3`: For a 1-core VPS, `(2 * 1) + 1 = 3` workers maximizes CPU utilization without thrashing RAM.
- `proxy_params`: Passes essential client headers (`X-Forwarded-For`, `X-Forwarded-Proto`) so Django knows the real client IP and whether the request was HTTPS.

## 8. Real-World Use Case

**High-Concurrency Enterprise Web Portal:**
Handling 2,000 simultaneous users. Nginx handles SSL negotiation and static assets in C code, while Gunicorn distributes business logic across 8 worker processes, maintaining sub-100ms response times.

---

## 9. Common Mistakes

1. **Setting Too Many Workers:** Setting 30 workers on a 1GB RAM VPS causes out-of-memory (OOM) crashes.
2. **Missing `SECURE_PROXY_SSL_HEADER`:** When Nginx terminates SSL, Django might not realize the original request was HTTPS, creating infinite redirect loops with `SECURE_SSL_REDIRECT`.
3. **Exposing Gunicorn Directly to the Internet:** Gunicorn is not designed to defend against slowloris attacks or handle SSL certificates. Always place Nginx in front.

---

## 10. Best Practices

- Calculate worker count: `(2 * CPU_CORES) + 1`.
- Bind Gunicorn to a Unix socket instead of a TCP port when running on the same server as Nginx.
- Configure `SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')` in `settings.py`.
- Use `systemctl enable gunicorn` so the application restarts automatically upon server reboot.

## 12. Interview Questions

**Q1: Why can't we use `python manage.py runserver` in production?**
*Answer:* `runserver` is an unoptimized development server. It is single-threaded by default, has not undergone security audits for hostile public internet traffic, leaks memory under prolonged load, cannot handle concurrent requests efficiently, and lacks process management capabilities (like auto-restarting workers on crashes or scaling across multi-core processors).

**Q2: What is the purpose of `SECURE_PROXY_SSL_HEADER`?**
*Answer:* When Nginx terminates SSL, it decrypts HTTPS traffic and forwards plain HTTP traffic to Gunicorn over a local socket. If Django checks `request.is_secure()`, it sees HTTP and triggers an SSL redirect, causing an infinite redirect loop. By setting `SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')`, Django trusts the `X-Forwarded-Proto` header set by Nginx to identify whether the end-user's original request was secure.

---

## 13. Summary

- WSGI (Gunicorn) is the synchronous production standard; ASGI (Uvicorn) powers async Django.
- Always run Gunicorn behind an Nginx reverse proxy.
- Use Unix sockets for optimal IPC performance.
- Automate process supervision via systemd services.
