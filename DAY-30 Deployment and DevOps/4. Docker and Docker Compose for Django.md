# 4. Docker and Docker Compose for Django

## 1. Introduction

"It works on my machine" is the oldest excuse in software engineering. Differences in Python versions, OS libraries, database configurations, and environment variables lead to unpredictable bugs. **Docker** packages your Django application, its dependencies, runtime, and system packages into an immutable, lightweight **Container**, ensuring 100% identical execution across development, staging, and production.

---

## 2. Why Do We Need It?

- Instant onboarding: New developers run `docker compose up` and have Django, MySQL, Redis, and Celery running in 60 seconds without manual local installations.
- Isolation: Avoids conflicting Python or database versions on the host machine.
- Cloud native: Docker containers deploy directly to AWS ECS, Google Cloud Run, Kubernetes, or DigitalOcean App Platform.

---

## 3. How It Works

1. **Dockerfile:** Instructions to build the Django application image.
2. **`.dockerignore`:** Excludes temporary files (`.venv`, `__pycache__`, `.git`) from the image.
3. **`docker-compose.yml`:** Orchestrates multiple interconnected services (Django web, MySQL database, Redis cache, Celery worker) on a private container network.

---

## 4. Syntax

### Production Multi-Stage Dockerfile
```dockerfile
# File: Dockerfile
FROM python:3.12-slim-bookworm AS base

# Prevent Python from writing .pyc files and buffer stdout
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

# Install system dependencies
RUN apt-get update && apt-get install -y --no-install-recommends \
    gcc \
    default-libmysqlclient-dev \
    pkg-config \
    curl \
    && rm -rf /var/lib/apt/lists/*

# Install Python dependencies
COPY requirements.txt /app/
RUN pip install --no-cache-dir -r requirements.txt

# Copy project code
COPY . /app/

# Collect static assets
RUN python manage.py collectstatic --noinput

# Run as non-root user for security
RUN useradd -m appuser && chown -R appuser:appuser /app
USER appuser

EXPOSE 8000

CMD ["gunicorn", "myproject.wsgi:application", "--bind", "0.0.0.0:8000", "--workers", "3"]
```

## 5. Practical Examples

### Complete `docker-compose.yml` for Django, MySQL, and Redis
```yaml
# File: docker-compose.yml
version: '3.8'

services:
  db:
    image: mysql:8.0
    restart: always
    environment:
      MYSQL_DATABASE: ems_db
      MYSQL_USER: ems_user
      MYSQL_PASSWORD: StrongPassword2026
      MYSQL_ROOT_PASSWORD: RootPassword2026
    ports:
      - "3306:3306"
    volumes:
      - mysql_data:/var/lib/mysql

  redis:
    image: redis:7-alpine
    restart: always
    ports:
      - "6379:6379"

  web:
    build: .
    restart: always
    command: python manage.py runserver 0.0.0.0:8000
    volumes:
      - .:/app
    ports:
      - "8000:8000"
    environment:
      - DEBUG=True
      - DB_HOST=db
      - DB_NAME=ems_db
      - DB_USER=ems_user
      - DB_PASSWORD=StrongPassword2026
      - REDIS_URL=redis://redis:6379/1
    depends_on:
      - db
      - redis

volumes:
  mysql_data:
```

---

## 6. Code Explanation

- `depends_on`: Ensures `db` and `redis` containers start before the `web` container.
- `volumes: - mysql_data:/var/lib/mysql`: Named persistent volume. Ensures database records survive even when containers are stopped or removed.
- Service discovery: Inside the Docker network, containers communicate using service names as hostnames (e.g., `DB_HOST=db`, `REDIS_URL=redis://redis:6379/1`).
- `USER appuser`: Running containers as `root` is a major security vulnerability; always switch to an unprivileged user in production Dockerfiles.

## 8. Real-World Use Case

**Continuous Integration & Deployment (CI/CD):**
GitHub Actions triggers on every pull request, builds the Docker image, spins up temporary MySQL/Redis test containers, runs `pytest`, and pushes verified images to Amazon Elastic Container Registry (ECR).

---

## 9. Common Mistakes

1. **Forgetting `.dockerignore`:** Copying local `.venv`, `.git`, and `db.sqlite3` into the image bloats image size from 200MB to 2GB!
2. **Database Race Condition on Startup:** Django starts and tries to run migrations before MySQL has finished initializing its socket, causing connection errors. Fix: use a `wait-for-it` script or Docker healthchecks.
3. **Hardcoding Container IPs:** Container IP addresses are ephemeral. Always use Docker Compose service names (`db`, `redis`).

---

## 10. Best Practices

- Use official slim Python base images (`python:3.12-slim`).
- Always run containers as a non-root user (`USER appuser`).
- Use Docker named volumes for database persistence.
- Leverage multi-stage builds to keep production images lightweight.

## 12. Interview Questions

**Q1: Why should you run containers with a non-root user?**
*Answer:* By default, Docker containers run as the `root` user (UID 0). If an attacker finds a remote code execution vulnerability (RCE) inside the Django application and manages to break out of the container isolation (container escape), they gain root privileges on the underlying host operating system. Creating and switching to an unprivileged user (`USER appuser`) significantly reduces the blast radius of any potential exploit.

**Q2: How do containers communicate with each other in Docker Compose?**
*Answer:* Docker Compose automatically creates an isolated bridge network for all services in the compose file. It runs an embedded internal DNS server that maps each service name (such as `db`, `web`, or `redis`) directly to the private container IP address. Applications connect seamlessly using the service name as the hostname (e.g., `mysql://user:pass@db:3306/db`).

---

## 13. Summary

- Docker packages code, system packages, and Python runtime into portable containers.
- Docker Compose orchestrates multi-container stacks (Django, MySQL, Redis, Celery).
- Always use `.dockerignore` and non-root users.
- Service names act as network hostnames for zero-configuration inter-container communication.
