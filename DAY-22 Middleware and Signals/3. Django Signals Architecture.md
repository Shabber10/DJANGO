# 3. Django Signals Architecture

## 1. Introduction

**Django Signals** implement the **Observer Pattern** (Publish-Subscribe). They allow decoupled applications to be notified when specific framework actions occur elsewhere in the project. When an event takes place (e.g. a model is saved, or an HTTP request finishes), a "sender" emits a signal, and all registered "receiver" functions execute automatically.

---

## 2. Why Do We Need It?

In modular monolithic architectures:
- App A (`orders`) should not tightly import and invoke internal functions from App B (`notifications`) and App C (`analytics`).
- Signals allow `orders` to simply announce: *"An order was placed!"*, allowing notifications, email senders, and analytics trackers to react independently without tightly coupling the codebases.

---

## 3. How It Works

The signal framework consists of:
1. **Signal:** The event dispatcher instance (e.g. `post_save`, `pre_delete`).
2. **Sender:** The entity triggering the event (typically a Model class).
3. **Receiver:** The Python callback function that executes when the signal fires.
4. **Connecting:** Linking the receiver to the signal using the `@receiver` decorator.

---

## 4. Syntax

```python
from django.db.models.signals import post_save
from django.dispatch import receiver
from django.contrib.auth.models import User

# Receiver function connected via decorator
@receiver(post_save, sender=User)
def user_created_notification(sender, instance, created, **kwargs):
    if created:
        print(f"New user registered: {instance.username}")
    else:
        print(f"User updated: {instance.username}")
```

---

## 5. Practical Examples

### Connecting Signals Safely via `apps.py`
To ensure signals are connected when Django starts up, connect them inside your application's `AppConfig.ready()` method:

```python
# File: accounts/apps.py
from django.apps import AppConfig

class AccountsConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'accounts'

    def ready(self):
        # Import signals here to avoid circular imports on startup!
        import accounts.signals
```

---

## 6. Code Explanation

- `sender=User`: Restricts the receiver to trigger ONLY when `User` instances are saved. If omitted, the receiver triggers for EVERY model saved in the entire project!
- `created`: Boolean flag. `True` if a new row was inserted; `False` if an existing row was updated.
- `instance`: The actual model instance that was saved.
- `**kwargs`: Necessary to ensure forward compatibility with any additional arguments Django's signal dispatcher might pass.

---

## 7. Expected Output

Creating a user in `python manage.py shell`:
```python
>>> User.objects.create_user(username="arjun", password="password")
New user registered: arjun
```

---

## 8. Real-World Use Case

Sending welcome emails when new accounts are created, invalidating cache entries when database records change, and logging audit trails.

---

## 9. Common Mistakes

1. **Importing signals at the top of `models.py`:** Causes circular import crashes during Django application startup. Always connect signals inside `apps.py` `ready()` method!
2. Forgetting `**kwargs` in receiver function signatures.

---

## 10. Best Practices

- Always specify `sender=ModelClass` to avoid catching unintended signals.
- Place signal receivers in a dedicated `signals.py` file inside your app.
- Import `signals` inside `AppConfig.ready()`.

## 12. Interview Questions

**Q1: What are the risks of overusing signals in a Django codebase?**  
*Answer:* Overusing signals can make code execution flow implicit, mysterious, and difficult to trace ("spooky action at a distance"). It can cause unexpected side effects during tests or bulk data operations, trigger recursive save loops, and create subtle performance bottlenecks. For direct domain logic, explicit service functions or model method overrides are often preferable to signals.

**Q2: What is the purpose of the `dispatch_uid` argument in `@receiver`?**  
*Answer:* `dispatch_uid` is a unique identifier (string) that prevents duplicate signal registrations. In environments where code might be imported multiple times (e.g. reloaders or certain test runners), `dispatch_uid` guarantees that the receiver function is registered only once, preventing the receiver from running multiple times for a single event.

## 13. Summary

- Signals implement publish-subscribe decoupling.
- Standard signals: `post_save`, `pre_save`, `post_delete`, `pre_delete`.
- Connect receivers in `apps.py` `ready()` method.
