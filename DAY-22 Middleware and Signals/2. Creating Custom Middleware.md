# 2. Creating Custom Middleware

## 1. Introduction

While Django's built-in middleware handles standard framework operations, custom business and operational requirements frequently demand authoring **Custom Middleware**. Whether blocking suspicious IP addresses, enabling maintenance mode, or enforcing domain redirection, custom middleware gives you total control over the request-response lifecycle.

---

## 2. Why Do We Need It?

If you need to enforce a policy site-wide:
- Manually adding an IP check or maintenance check to 100 views is error-prone.
- Custom middleware enforces rules at the perimeter, rejecting unauthorized or blocked traffic before views or database queries are ever executed.

---

## 3. How It Works

1. Create a Python module (e.g. `core/middleware.py`).
2. Write a class with `__init__(self, get_response)` and `__call__(self, request)`.
3. Add the Python import string to the `MIDDLEWARE` list in `settings.py`.
4. To short-circuit a request, return an `HttpResponse` directly (e.g., `HttpResponseForbidden()`) without calling `self.get_response(request)`.

---

## 4. Syntax

```python
# File: core/middleware.py
from django.http import HttpResponseForbidden

class IPBlocklistMiddleware:
    BLOCKED_IPS = ['192.168.1.100', '10.0.0.99']

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        client_ip = request.META.get('REMOTE_ADDR')
        
        # Short-circuit if client IP is blocked!
        if client_ip in self.BLOCKED_IPS:
            return HttpResponseForbidden("Access Denied: Your IP has been blocked.")

        return self.get_response(request)
```

---

## 5. Practical Examples

### Site-Wide Maintenance Mode Middleware
```python
# File: core/middleware.py
from django.conf import settings
from django.shortcuts import render

class MaintenanceModeMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        # Check maintenance setting (could be dynamically read from Redis or DB)
        is_maintenance = getattr(settings, 'MAINTENANCE_MODE', False)

        # Allow admin portal access during maintenance
        if is_maintenance and not request.path.startswith('/admin/'):
            return render(request, 'maintenance.html', status=503)

        return self.get_response(request)
```

In `config/settings.py`:
```python
MIDDLEWARE = [
    'core.middleware.MaintenanceModeMiddleware', # First line!
    'django.middleware.security.SecurityMiddleware',
    ...
]

MAINTENANCE_MODE = False # Toggle to True to put site in maintenance!
```

---

## 6. Code Explanation

- Placing `MaintenanceModeMiddleware` at the very top of `MIDDLEWARE` ensures that during maintenance, requests are immediately halted before session or database middleware runs, conserving server resources.
- Returning an explicit HTTP 503 status code informs search engine crawlers that downtime is temporary.

---

## 7. Expected Output

When `MAINTENANCE_MODE = True`:
Visiting `/` or `/store/` returns:
```text
HTTP/1.1 503 Service Unavailable
Content-Type: text/html; charset=utf-8
(Renders maintenance.html)
```
Admin users can still access `/admin/` to perform updates!

---

## 8. Real-World Use Case

Scheduled database migrations requiring temporary site-wide read-only or maintenance screens; geo-blocking compliance; multi-tenant subdomain tenant resolution.

---

## 9. Common Mistakes

1. **Returning `None` instead of `response` from `__call__`:**
   Every middleware must return an `HttpResponse` object. Forgetting `return response` causes `ValueError: The view ... didn't return an HttpResponse object.`

---

## 10. Best Practices

- Position custom middleware carefully based on what dependencies it needs (e.g., place after `AuthenticationMiddleware` if it inspects `request.user`).
- Return semantic HTTP status codes (403 for blocked IPs, 503 for maintenance).

## 12. Interview Questions

**Q1: How can custom middleware short-circuit the Django request lifecycle?**  
*Answer:* By returning an `HttpResponse` directly from `__call__()` without calling `self.get_response(request)`. When this happens, Django skips all subsequent middleware, skips the URL routing dispatcher, and skips the view function, immediately sending the returned response back up the response chain.

**Q2: What is the significance of middleware order in `settings.MIDDLEWARE`?**  
*Answer:* Middleware runs sequentially top-to-bottom on requests and in reverse bottom-to-top on responses. If Middleware B depends on attributes attached by Middleware A (for example, `AuthenticationMiddleware` needs `request.session` attached by `SessionMiddleware`), Middleware A must precede Middleware B in the list.

---

## 13. Summary

- Custom middleware intercepts requests before and after views.
- Registered in `settings.MIDDLEWARE`.
- Can short-circuit requests by returning early responses.
