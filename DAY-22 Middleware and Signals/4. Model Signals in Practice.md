# 4. Model Signals in Practice

## 1. Introduction

The most widely used signals in Django are **Model Signals** (`pre_save`, `post_save`, `pre_delete`, `post_delete`). They provide lifecycle hooks that execute before or after database persistence, enabling automated slug generation, profile creation, and file cleanup.

---

## 2. Why Do We Need It?

Certain business workflows naturally attach to the database lifecycle:
- Generating an SEO slug automatically before an article is inserted (`pre_save`).
- Creating a matching `UserProfile` table row whenever a `User` is created (`post_save`).
- Deleting an image file from disk when its corresponding model row is deleted (`post_delete`).

---

## 3. How It Works

- **`pre_save`:** Fires right before `model.save()` issues the SQL `INSERT` or `UPDATE`. Ideal for modifying instance fields (slugs, timestamps, calculations).
- **`post_save`:** Fires immediately after the database write succeeds. Ideal for creating related records or sending emails.
- **`pre_delete` / `post_delete`:** Fires before/after SQL `DELETE`. Ideal for deleting uploaded binary files from disk.

---

## 4. Syntax

```python
from django.db.models.signals import pre_save, post_save, post_delete
from django.dispatch import receiver
from django.utils.text import slugify
from .models import Article

# 1. Automated Slug Generation on pre_save
@receiver(pre_save, sender=Article)
def auto_generate_slug(sender, instance, **kwargs):
    if not instance.slug:
        instance.slug = slugify(instance.title)

# 2. File Cleanup on post_delete
@receiver(post_delete, sender=Article)
def delete_article_image_on_delete(sender, instance, **kwargs):
    if instance.cover_image:
        # Delete file from disk!
        instance.cover_image.delete(save=False)
```

---

## 5. Practical Examples

### The UserProfile Creation Pattern
```python
# File: accounts/signals.py
from django.db.models.signals import post_save
from django.dispatch import receiver
from django.contrib.auth import get_user_model
from .models import UserProfile

User = get_user_model()

@receiver(post_save, sender=User)
def manage_user_profile(sender, instance, created, **kwargs):
    if created:
        # User was just registered: Create matching profile
        UserProfile.objects.create(user=instance)
    else:
        # User was updated: Ensure profile is saved
        if hasattr(instance, 'profile'):
            instance.profile.save()
```

---

## 6. Code Explanation

- `pre_save`: You can modify `instance.slug = ...` directly without calling `instance.save()`. Django writes the modified instance to the database in the upcoming save!
- `post_delete`: Django does NOT automatically delete uploaded files from disk when a model row is deleted. The `post_delete` signal ensures no orphaned files accumulate in `media/`.
- `instance.cover_image.delete(save=False)`: Removes the binary file from disk without triggering another model save.

## 9. Common Mistakes

1. **Calling `instance.save()` inside a `post_save` receiver without conditions:** Calling `instance.save()` inside `post_save` triggers another `post_save` signal, resulting in an **infinite recursion loop** and a `RecursionError` crash!
2. Expecting bulk operations like `Product.objects.bulk_create()` to trigger signals. Bulk operations do NOT call `save()`, so signals do NOT fire!

---

## 10. Best Practices

- Never call `instance.save()` unconditionally inside `post_save`.
- Remember that `bulk_create()` and `QuerySet.update()` do NOT fire signals.
- Use `post_delete` to clean up media files from disk.

## 12. Interview Questions

**Q1: Why do `bulk_create()` and `QuerySet.update()` NOT fire `pre_save` and `post_save` signals?**  
*Answer:* `bulk_create()` and `QuerySet.update()` execute batch SQL statements (`INSERT INTO ... VALUES (...), (...)` and `UPDATE ... SET ... WHERE ...`) directly at the database engine level in a single round-trip for performance. They do not instantiate individual Python model objects or call `model.save()`, so Django model lifecycle signals are intentionally bypassed.

**Q2: How do you avoid infinite recursion loops in `post_save` signals?**  
*Answer:* Avoid calling `instance.save()` on the same instance inside `post_save`. If you must update a field on the instance, use `Model.objects.filter(pk=instance.pk).update(...)` (which bypasses signals) or wrap the save with a flag or disconnected signal.

---

## 13. Summary

- `pre_save` modifies fields before persistence (slugs).
- `post_save` reacts to creation/updates (profiles, emails).
- `post_delete` cleans up files from disk.
- Bulk ORM operations bypass signals.
