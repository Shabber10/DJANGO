# 1. Django Middleware Architecture

## 1. Introduction

**Middleware** is a lightweight, low-level plugin system for globally altering Django's input or output. Each middleware component acts as a layer of an onion surrounding your views, capable of inspecting, modifying, or short-circuiting HTTP requests on their way in, and HTTP responses on their way out.

---

## 2. Why Do We Need It?

Many application concerns apply globally to every single request:
- Checking session validity and populating `request.user`.
- Validating CSRF tokens.
- Setting security headers (`X-Frame-Options`, `Content-Security-Policy`).
- Measuring request latency and profiling performance.
Without middleware, you would have to duplicate these checks manually in every single view function.

---

## 3. How It Works

### The Onion Model:
```
[ Incoming HTTP Request ]
          │
          ▼
    [ SecurityMiddleware ]
          │
          ▼
    [ SessionMiddleware ]
          │
          ▼
    [ AuthenticationMiddleware ]
          │
          ▼
    [ URL Dispatcher & View ]
          │
          ▼ (Outgoing Response)
    [ AuthenticationMiddleware ]
          │
          ▼
    [ SessionMiddleware ]
          │
          ▼
    [ SecurityMiddleware ]
          │
          ▼
[ Outgoing HTTP Response ]
```
Middleware executes **top-to-bottom** during the request phase, and **bottom-to-top** (reverse order) during the response phase!

---

## 4. Syntax

```python
# Standard Modern Middleware Class Structure (Callable):
class SimpleMiddleware:
    def __init__(self, get_response):
        # One-time configuration and initialization
        self.get_response = get_response

    def __call__(self, request):
        # Code executed for each request BEFORE the view (and later middleware) are called.

        response = self.get_response(request) # Delegates to view/next middleware

        # Code executed for each request AFTER the view is called.
        return response
```

---

## 5. Practical Examples

### Request Latency Timing Middleware
```python
# File: core/middleware.py
import time

class PerformanceTimerMiddleware:
    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        start_time = time.time()

        # Pass request down the chain to the view
        response = self.get_response(request)

        # Calculate duration
        duration = time.time() - start_time
        # Attach custom diagnostic header
        response['X-Process-Time-Ms'] = f"{duration * 1000:.2f}"
        
        return response
```

---

## 6. Code Explanation

- `self.get_response`: The next middleware in the chain (or the final view).
- `__call__(self, request)`: Called on every request.
- `response['X-Process-Time-Ms']`: Injects an HTTP header measuring execution duration in milliseconds.

---

## 7. Expected Output

Inspecting response headers in cURL or DevTools:
```text
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
X-Process-Time-Ms: 14.28
```

---

## 8. Real-World Use Case

Application performance monitoring (APM), rate limiting by client IP, maintenance mode toggles, and multi-tenant domain routing.

---

## 9. Common Mistakes

1. **Misordering middleware in `settings.py`:** For example, placing `AuthenticationMiddleware` *before* `SessionMiddleware`. Authentication relies on sessions, so it will fail with `AttributeError: 'HttpRequest' object has no attribute 'session'`.

---

## 10. Best Practices

- Keep middleware lean; heavy blocking database queries in middleware slow down EVERY request across the site.
- Respect middleware ordering dependencies in `settings.MIDDLEWARE`.

## 12. Interview Questions

**Q1: Explain the lifecycle of a request through Django Middleware.**  
*Answer:* An incoming request enters the middleware pipeline defined in `settings.MIDDLEWARE` in top-to-bottom order. Each middleware can inspect or modify `request`, or return an early `HttpResponse` (short-circuiting the rest of the chain). If not short-circuited, the URL dispatcher matches the route and executes the view. The resulting `HttpResponse` then bubbles back up through the middleware pipeline in bottom-to-top (reverse) order, allowing each middleware to modify headers, cookies, or content before sending it to the client.

**Q2: What is the purpose of `process_exception(request, exception)` in middleware?**  
*Answer:* `process_exception()` is an optional middleware hook called when a view raises an unhandled Python exception. It allows middleware to catch specific errors globally (e.g. logging to Sentry, sending email alerts, or converting custom domain exceptions into clean JSON error responses) without cluttering individual view functions with `try...except` blocks.

---

## 13. Summary

- Middleware wraps view execution globally.
- Evaluates top-to-bottom on requests; bottom-to-top on responses.
- Essential for cross-cutting concerns (auth, security, telemetry).
