# 1. DRF Authentication Schemes

## 1. Introduction

Unlike browser-based web applications that rely primarily on session cookies, REST APIs are consumed by diverse clients: native mobile apps, Single Page Applications (React, Vue), microservices, and external developer scripts. Django REST Framework provides multiple pluggable **Authentication Schemes** to verify client identity.

---

## 2. Why Do We Need It?

- Mobile applications cannot easily manage session cookies or CSRF tokens.
- Cross-origin Single Page Applications often run on separate domains (`app.company.com` vs `api.company.com`), where cookies face cross-origin restrictions.
- Third-party integrations require long-lived API tokens.

---

## 3. How It Works

DRF authenticates requests by running the classes listed in `DEFAULT_AUTHENTICATION_CLASSES`:
1. **`SessionAuthentication`:** Uses Django's standard session cookies (best for Browsable API and same-origin frontends).
2. **`BasicAuthentication`:** Reads `Authorization: Basic <base64(user:pass)>` (useful for quick testing; insecure without HTTPS).
3. **`TokenAuthentication`:** Uses static cryptographic tokens stored in the database (`Authorization: Token <key>`).
4. **`JWT (JSON Web Token)`:** Stateless, signed cryptographic tokens (via `SimpleJWT`).

---

## 4. Syntax

### Setting Up Built-in Token Authentication:
In `settings.py`:
```python
INSTALLED_APPS = [
    ...,
    'rest_framework',
    'rest_framework.authtoken', # Dedicated token table!
]

REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework.authentication.TokenAuthentication',
        'rest_framework.authentication.SessionAuthentication',
    ],
}
```

Run migrations to create the token table:
```bash
python manage.py migrate
```

Exposing the Token Obtain Endpoint in `urls.py`:
```python
from rest_framework.authtoken.views import obtain_auth_token
from django.urls import path

urlpatterns = [
    path('api/api-token-auth/', obtain_auth_token, name='api_token_auth'),
]
```

---

## 5. Practical Examples

### Requesting and Using a Token
1. **Obtain Token via POST:**
```bash
curl -X POST http://127.0.0.1:8000/api/api-token-auth/ \
     -H "Content-Type: application/json" \
     -d '{"username": "shabber", "password": "securepassword123"}'
```
Response:
```json
{
  "token": "9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b"
}
```

2. **Accessing Protected Endpoints using Token:**
```bash
curl http://127.0.0.1:8000/api/profile/ \
     -H "Authorization: Token 9944b09199c62bcf9418ad846dd0e4bbdfc6ee4b"
```

---

## 6. Code Explanation

- `rest_framework.authtoken`: Creates an `authtoken_token` table mapping each user to a 40-character hexadecimal key.
- `Authorization: Token <key>`: The standard HTTP header parsed by `TokenAuthentication`.
- If the token is valid, DRF sets `request.user` to that user; if invalid, it returns `401 Unauthorized`.

---

## 7. Expected Output

Sending a request without a token to a protected view:
```json
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Token
Content-Type: application/json
{
  "detail": "Authentication credentials were not provided."
}
```

---

## 8. Real-World Use Case

Supplying API keys to external developers (e.g. GitHub personal access tokens, Stripe secret API keys).

---

## 9. Common Mistakes

1. **Misspelling the Header Prefix:** DRF's built-in TokenAuthentication expects `Authorization: Token <key>`, NOT `Bearer <key>`! (JWT uses `Bearer`).
2. Forgetting to run `migrate` after adding `rest_framework.authtoken`.

---

## 10. Best Practices

- Always enforce HTTPS in production when using tokens.
- Use `TokenAuthentication` for simple microservices; use **JWT** for distributed mobile and web applications.

## 12. Interview Questions

**Q1: How does DRF's built-in TokenAuthentication work under the hood?**  
*Answer:* When `rest_framework.authtoken` is installed, it creates a database table (`authtoken_token`) with a 1-to-1 relationship to the User model, storing a 40-character random key. When an HTTP request arrives with `Authorization: Token <key>`, DRF queries the database for that key. If found, it populates `request.user` with the associated user object; if not found, it raises an `AuthenticationFailed` exception.

**Q2: What is the main architectural drawback of DRF's built-in `TokenAuthentication` compared to JWT?**  
*Answer:* Built-in TokenAuthentication is stateful: every incoming API request requires a database lookup to query the `authtoken_token` table to resolve the user. In high-throughput distributed systems with thousands of requests per second, this creates a database bottleneck. JWT is stateless: the token itself contains signed claims, allowing servers to verify identity cryptographically without touching the database.

---

## 13. Summary

- DRF supports Session, Basic, Token, and JWT authentication.
- Built-in token auth stores keys in the database.
- Clients authenticate via the `Authorization: Token <key>` header.
