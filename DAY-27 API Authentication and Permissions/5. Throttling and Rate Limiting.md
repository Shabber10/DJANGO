# 5. Throttling and Rate Limiting

## 1. Introduction

To protect web APIs from abuse, aggressive scraping, brute-force attacks, and **Denial of Service (DoS)**, backends enforce **Throttling (Rate Limiting)**. Django REST Framework provides an integrated throttling engine that restricts the number of requests clients can make within specific time windows.

---

## 2. Why Do We Need It?

Without rate limiting:
- A malicious bot can submit 10,000 login attempts per minute to crack passwords.
- Aggressive scrapers can drain server CPU and database connections.
- External API integrations can overwhelm internal infrastructure.
Throttling ensures fair resource distribution and system stability.

---

## 3. How It Works

DRF tracks request timestamps in the application cache (typically Redis or Memcached):
- **`AnonRateThrottle`:** Tracks unauthenticated clients by their IP address (`request.META['REMOTE_ADDR']`).
- **`UserRateThrottle`:** Tracks authenticated users by their user ID (`user.pk`).
- **`ScopedRateThrottle`:** Applies distinct limits to specific sensitive endpoints (e.g. login, payment checkout).
When limits are exceeded, DRF halts execution and returns **`HTTP 429 Too Many Requests`**.

---

## 4. Syntax

```python
# File: config/settings.py
REST_FRAMEWORK = {
    'DEFAULT_THROTTLE_CLASSES': [
        'rest_framework.throttling.AnonRateThrottle',
        'rest_framework.throttling.UserRateThrottle',
    ],
    'DEFAULT_THROTTLE_RATES': {
        'anon': '100/day',     # Guests: 100 requests per day
        'user': '1000/hour',   # Logged-in: 1,000 requests per hour
        'login': '5/minute',   # Custom scope for login attempts
    }
}
```

---

## 5. Practical Examples

### Applying Scoped Throttling to Sensitive Views
```python
# File: accounts/views.py
from rest_framework.views import APIView
from rest_framework.throttling import ScopedRateThrottle
from rest_framework.response import Response

class SensitiveLoginAPIView(APIView):
    # Enforces the 'login' rate limit (5 requests per minute!)
    throttle_classes = [ScopedRateThrottle]
    throttle_scope = 'login'

    def post(self, request):
        # Authenticate user...
        return Response({"status": "authenticated"})
```

---

## 6. Code Explanation

- `'5/minute'`: Rate format can be specified in `s` (second), `m` (minute), `h` (hour), or `d` (day).
- `ScopedRateThrottle`: Uses `throttle_scope = 'name'` to look up the rate from `DEFAULT_THROTTLE_RATES`.
- When a client is blocked, DRF sets the `Retry-After: 48` header, informing the client exactly how many seconds to wait before retrying!

---

## 7. Expected Output

When a client sends a 6th request within 1 minute:
```json
HTTP/1.1 429 Too Many Requests
Retry-After: 42
Content-Type: application/json
{
  "detail": "Request was throttled. Expected available in 42 seconds."
}
```

---

## 8. Real-World Use Case

Protecting password-reset endpoints, OTP SMS verification triggers, payment authorizations, and public weather/currency APIs.

---

## 9. Common Mistakes

1. **Running throttling with the default in-memory cache in multi-process production:**
   Default `LocMemCache` keeps rate limits in memory per Python process. In multi-worker production (Gunicorn with 4 workers), each worker maintains a separate counter! Always configure Redis (`django-redis`) for shared throttling across workers.

---

## 10. Best Practices

- Back throttling with **Redis** in production.
- Use aggressive limits for unauthenticated endpoints (login, password reset).
- Supply clear `Retry-After` headers to assist legitimate API consumers.

## 12. Interview Questions

**Q1: How does DRF calculate rate limits and what caching mechanism does it rely on?**  
*Answer:* DRF calculates rates using a sliding-window or fixed-window timestamp algorithm stored in Django's cache framework (`django.core.cache`). For each request, it checks the number of timestamps recorded for that client's cache key (IP or user ID). If the count exceeds the allowed limit for that time window, it calculates the remaining seconds and raises `Throttled`. In production, this requires a shared cache (such as Redis) so all web workers share a unified counter.

**Q2: What is the purpose of `ScopedRateThrottle` in DRF?**  
*Answer:* `ScopedRateThrottle` allows applying different rate limits to different endpoints rather than a single site-wide limit. By defining `throttle_scope = 'burst'` or `throttle_scope = 'login'` on individual views and configuring distinct rates in `DEFAULT_THROTTLE_RATES`, developers can enforce strict limits on sensitive endpoints (e.g. 5/min on login) while allowing generous limits on catalog endpoints (e.g. 1000/hour on products).

---

## 13. Summary

- Throttling prevents API abuse and brute-force attacks.
- Returns HTTP 429 Too Many Requests with `Retry-After` header.
- Redis provides shared cache tracking in production.
