# 3. Permissions and Custom Permission Classes

## 1. Introduction

Authentication verifies identity; **Permissions** determine authorization. DRF provides a flexible, modular permission system with built-in permission classes (`AllowAny`, `IsAuthenticated`, `IsAdminUser`) and a clean base class (`BasePermission`) for authoring **Custom Object-Level Permissions**.

---

## 2. Why Do We Need It?

Different API endpoints require different security rules:
- Public catalog: Anyone can view (`AllowAny`).
- Member dashboard: Only logged-in users can view (`IsAuthenticated`).
- Blog articles: Anyone can read, but only the original author can edit or delete their article (**Object-Level Permission**).

---

## 3. How It Works

DRF evaluates permissions in two phases:
1. **View-Level Permissions (`has_permission(self, request, view)`):** Executed at the start of the request before any database record is retrieved. Returns `True` or `False`.
2. **Object-Level Permissions (`has_object_permission(self, request, view, obj)`):** Executed when `get_object()` is called. Verifies whether the user is permitted to interact with that specific instance `obj`.

---

## 4. Syntax

```python
# File: core/permissions.py
from rest_framework import permissions

class IsOwnerOrReadOnly(permissions.BasePermission):
    # Custom permission: Only the author of an object can edit/delete it.
    # Guests and other users have read-only permissions (GET, HEAD, OPTIONS).
    def has_object_permission(self, request, view, obj):
        # Read-only methods are safe
        if request.method in permissions.SAFE_METHODS:
            return True

        # Write permissions are only allowed to the author
        return obj.author == request.user
```

---

## 5. Practical Examples

### Applying Permissions to Views and ViewSets
```python
# File: blog/views.py
from rest_framework import viewsets, permissions
from .models import Article
from .serializers import ArticleSerializer
from core.permissions import IsOwnerOrReadOnly

class ArticleViewSet(viewsets.ModelViewSet):
    queryset = Article.objects.all()
    serializer_class = ArticleSerializer
    
    # Layered permissions: Must be logged in, AND must be the owner to edit!
    permission_classes = [
        permissions.IsAuthenticatedOrReadOnly,
        IsOwnerOrReadOnly
    ]
```

---

## 6. Code Explanation

- `permissions.SAFE_METHODS`: A tuple containing `('GET', 'HEAD', 'OPTIONS')`—HTTP methods that do not modify database state.
- `permission_classes`: An iterable of permission classes. ALL classes in the list must return `True` for access to be granted!
- If permissions fail, DRF returns `401 Unauthorized` (if user is unauthenticated) or `403 Forbidden` (if user is authenticated but lacking permission).

---

## 7. Expected Output

If User Bob attempts to execute `DELETE /api/articles/12/` (authored by Alice):
```json
HTTP/1.1 403 Forbidden
Content-Type: application/json
{
  "detail": "You do not have permission to perform this action."
}
```

---

## 8. Real-World Use Case

Multi-tenant platforms ensuring members cannot read or tamper with another organization's records; social networks ensuring users can only delete their own comments.

---

## 9. Common Mistakes

1. **Expecting `has_object_permission` to execute in custom `APIView` without calling `self.check_object_permissions(request, obj)`:** In standard `APIView`, you must explicitly call `self.check_object_permissions(request, obj)` after fetching the object. (Generic views and ViewSets handle this automatically!).

---

## 10. Best Practices

- Check `request.method in permissions.SAFE_METHODS` when building read-write permission splits.
- Always implement object-level permissions to prevent Insecure Direct Object References (IDOR).
- Combine built-in classes (`IsAuthenticatedOrReadOnly`) with custom domain classes.

## 12. Interview Questions

**Q1: What is the difference between `has_permission` and `has_object_permission` in DRF?**  
*Answer:* `has_permission(self, request, view)` runs before the view executes or any database lookup occurs; it checks general access rights (e.g., is the user authenticated or an admin?). `has_object_permission(self, request, view, obj)` runs after `get_object()` retrieves a specific database record; it checks object-level rights (e.g., is the current user the creator of this specific comment?).

**Q2: What is an Insecure Direct Object Reference (IDOR / BOLA) and how do DRF permissions solve it?**  
*Answer:* IDOR occurs when an application exposes a direct database reference (e.g. `/api/invoices/105/`) without verifying that the requesting user owns that object. An attacker can simply change the ID in the URL to view other users' sensitive invoices. DRF object-level permissions (`IsOwnerOrReadOnly` or `has_object_permission`) verify ownership before returning the record, preventing unauthorized data access.

---

## 13. Summary

- Permissions enforce authorization rules on API views.
- Built-in classes: `AllowAny`, `IsAuthenticated`, `IsAdminUser`.
- Subclass `BasePermission` to build custom object-level access controls.
