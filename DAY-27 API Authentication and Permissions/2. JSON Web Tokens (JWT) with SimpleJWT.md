# 2. JSON Web Tokens (JWT) with SimpleJWT

## 1. Introduction

**JSON Web Tokens (JWT)** are an open, industry-standard (RFC 7519) method for representing claims securely between two parties. Unlike traditional tokens that require querying a database table on every request, JWTs are **stateless and self-contained**—the token itself carries signed user data. In Django REST Framework, the official recommended implementation is **`djangorestframework-simplejwt`**.

---

## 2. Why Do We Need It?

- **Stateless Scalability:** Servers do not store active tokens in a database. A server verifies the token signature mathematically using its secret key, completely eliminating database auth lookups!
- **Dual Token Architecture:** Uses short-lived **Access Tokens** (5-15 mins) for API access and long-lived **Refresh Tokens** (7-30 days) to securely obtain new access tokens without prompting re-login.

---

## 3. How It Works

A JWT consists of three parts separated by dots (`.`):
`Header.Payload.Signature`
- **Header:** Algorithm & token type (e.g. `{"alg": "HS256", "typ": "JWT"}`).
- **Payload:** User claims (e.g. `{"user_id": 42, "exp": 1730380800}`).
- **Signature:** Cryptographic hash: `HMACSHA256(base64Url(Header) + "." + base64Url(Payload), SECRET_KEY)`.

---

## 4. Syntax

### Installing SimpleJWT:
```bash
pip install djangorestframework-simplejwt
```

In `config/settings.py`:
```python
from datetime import timedelta

REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework_simplejwt.authentication.JWTAuthentication',
    ],
}

SIMPLE_JWT = {
    'ACCESS_TOKEN_LIFETIME': timedelta(minutes=15),
    'REFRESH_TOKEN_LIFETIME': timedelta(days=7),
    'ROTATE_REFRESH_TOKENS': True,
    'BLACKLIST_AFTER_ROTATION': True,
    'AUTH_HEADER_TYPES': ('Bearer',), # Authorization: Bearer <token>
}
```

In `config/urls.py`:
```python
from django.urls import path
from rest_framework_simplejwt.views import (
    TokenObtainPairView,
    TokenRefreshView,
)

urlpatterns = [
    path('api/token/', TokenObtainPairView.as_view(), name='token_obtain_pair'),
    path('api/token/refresh/', TokenRefreshView.as_view(), name='token_refresh'),
]
```

## 5. Practical Examples

### Complete JWT Auth Flow
1. **Obtain Tokens (Login):**
```bash
curl -X POST http://127.0.0.1:8000/api/token/ \
     -H "Content-Type: application/json" \
     -d '{"username": "shabber", "password": "mypassword"}'
```
Response:
```json
{
  "access": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
  "refresh": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

2. **Access Protected API with Access Token:**
```bash
curl http://127.0.0.1:8000/api/orders/ \
     -H "Authorization: Bearer <access_token>"
```

3. **Refresh Expired Access Token:**
When the access token expires (after 15 minutes), send the refresh token to get a new access token:
```bash
curl -X POST http://127.0.0.1:8000/api/token/refresh/ \
     -H "Content-Type: application/json" \
     -d '{"refresh": "<refresh_token>"}'
```

---

## 6. Code Explanation

- `TokenObtainPairView`: Exposes the login endpoint that verifies username/password and issues the `(access, refresh)` token pair.
- `TokenRefreshView`: Exposes the endpoint that validates a refresh token and generates a fresh access token without requiring re-entry of credentials.
- `Authorization: Bearer <token>`: Standard OAuth 2.0 / JWT header prefix.

---

## 7. Expected Output

If an expired or tampered access token is submitted:
```json
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token"
{
  "detail": "Given token not valid for any token type",
  "code": "token_not_valid"
}
```

## 8. Real-World Use Case

Modern Single Page Applications (Next.js, React) and mobile apps (iOS, Android, Flutter) communicating with scalable cloud microservices.

---

## 9. Common Mistakes

1. **Storing sensitive secrets in JWT payloads:** JWT payloads are only Base64-encoded, NOT encrypted! Anyone who intercepts the token can decode and read the payload. Never store passwords or social security numbers in JWT claims.
2. Setting access token lifespans too long (e.g. 30 days), making it impossible to revoke access if a token is compromised.

---

## 10. Best Practices

- Keep access token lifetimes short (5 to 15 minutes).
- Enable `ROTATE_REFRESH_TOKENS = True` and token blacklisting for secure logouts.
- Always transmit JWTs over HTTPS.

## 12. Interview Questions

**Q1: How does stateless JWT verification eliminate database bottlenecks in microservices?**  
*Answer:* A JWT contains the user ID and expiration timestamp in its payload, sealed by a cryptographic signature computed with the server's `SECRET_KEY`. When a request arrives, the server mathematically validates the signature using the secret key and checks the expiration time. If the signature is valid, the claims are trusted and `request.user` is populated without needing an SQL database query, allowing APIs to scale horizontally with zero auth database load.

**Q2: What is Token Blacklisting in SimpleJWT?**  
*Answer:* Because JWTs are stateless, a valid token remains usable until it naturally expires. When a user logs out, their refresh token should be revoked. SimpleJWT's `rest_framework_simplejwt.token_blacklist` app maintains a database table of revoked refresh tokens. When `ROTATE_REFRESH_TOKENS` is enabled, used or logged-out refresh tokens are blacklisted, preventing reuse.

---

## 13. Summary

- JWT provides stateless, cryptographically signed authentication.
- Access tokens expire quickly; refresh tokens grant new access tokens.
- Implemented in DRF via `djangorestframework-simplejwt`.
