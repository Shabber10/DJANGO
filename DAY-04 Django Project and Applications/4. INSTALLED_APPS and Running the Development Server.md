# 4. INSTALLED_APPS and Running the Development Server

## 1. Introduction

Creating an application folder is not enough; Django must be explicitly informed that the app exists. This is done through the **`INSTALLED_APPS`** setting. Once registered, you can verify your project by launching Django's built-in development web server.

---

## 2. Why Do We Need It?

`INSTALLED_APPS` acts as Django's registry. Django scans `INSTALLED_APPS` to:
- Discover database models for migrations (`makemigrations`).
- Locate templates inside app-level `templates/` folders.
- Discover static files inside app-level `static/` folders.
- Register admin classes in `admin.py`.
- Load custom management commands and template tags.

---

## 3. How It Works

When `python manage.py runserver` is invoked:
1. Django validates all settings and checks `INSTALLED_APPS`.
2. It runs the system check framework to detect syntax and configuration errors.
3. It outputs unapplied database migration warnings.
4. It launches an HTTP server listening on `127.0.0.1:8000` with **autoreload** enabled (watching Python files for changes and automatically restarting).

---

## 4. Syntax

### Registering an App in `settings.py`:
```python
# File: config/settings.py

INSTALLED_APPS = [
    # Core Django apps
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',

    # Custom apps (Either by app name or AppConfig path)
    'blog',
    # OR: 'blog.apps.BlogConfig',
]
```

### Launching the Development Server:
```bash
# Default port 8000 on localhost
python manage.py runserver

# Custom port
python manage.py runserver 8080

# Binding to all network interfaces (e.g. for Docker or mobile testing)
python manage.py runserver 0.0.0.0:8000
```

---

## 5. Practical Examples

### Complete Step-by-Step App Verification
```bash
# 1. Create app
python manage.py startapp blog

# 2. Add 'blog' to INSTALLED_APPS in config/settings.py

# 3. Perform system check
python manage.py check

# 4. Start the server
python manage.py runserver
```

---

## 6. Code Explanation

- `'blog.apps.BlogConfig'`: The recommended verbose syntax for registering apps. It points directly to the `AppConfig` class in `blog/apps.py`, enabling custom app initialization logic.
- `python manage.py runserver`: Starts the development web server. It is multi-threaded by default and restarts whenever a `.py` file is saved.

## 8. Real-World Use Case

During everyday software development, developers keep `runserver` active in a background terminal tab. Every time you save a view, template, or model, Django's `StatReloader` immediately reloads the code.

---

## 9. Common Mistakes

1. Leaving trailing commas off in the `INSTALLED_APPS` list.
2. Attempting to use `runserver` in production. It is not designed for security or high concurrency.

---

## 10. Best Practices

- Group `INSTALLED_APPS` into three sections: Built-in Django apps, Third-Party apps (e.g. `rest_framework`), and Local domain apps.
- Always run `python manage.py check` before launching the server.

## 12. Interview Questions

**Q1: What happens if an app is not added to `INSTALLED_APPS`?**  
*Answer:* Django will not discover any database models defined in the app (so `makemigrations` ignores them), will not look for templates in the app's `templates/` directory, will not discover static files in the app's `static/` directory, and will not register admin classes or management commands.

**Q2: Why should `runserver` never be used in production?**  
*Answer:* `runserver` has not undergone security audits, lacks process management, does not handle high concurrency, cannot serve static/media files efficiently, and cannot scale across multiple CPU cores like production WSGI/ASGI servers (Gunicorn, uWSGI).

---

## 13. Summary

- All apps must be declared in `INSTALLED_APPS` in `settings.py`.
- `runserver` provides an instant local server with auto-reloading.
- The system check framework catches configuration errors automatically.
