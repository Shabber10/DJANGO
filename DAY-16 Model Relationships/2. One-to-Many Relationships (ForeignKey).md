# 2. One-to-Many Relationships (ForeignKey)

## 1. Introduction

The **One-to-Many Relationship** (represented by **`models.ForeignKey`**) is the most common relationship in relational databases. It signifies that one parent record (e.g. a Department) can be associated with multiple child records (e.g. Employees), but each child record belongs to exactly one parent.

---

## 2. Why Do We Need It?

- Normalization: Prevents duplicating company or department details inside every employee row.
- Integrity: Ensures that an order cannot point to a non-existent customer.
- Deletion Policies: Enforces business rules when parent records are deleted.

---

## 3. How It Works

### The `on_delete` Strategies:
- **`models.CASCADE`:** Deletes all child records when the parent is deleted. (e.g. deleting a Blog Post deletes all its Comments).
- **`models.PROTECT`:** Prevents deletion of the parent by raising `ProtectedError` if any children reference it. (e.g. cannot delete a Department that still has active Employees).
- **`models.SET_NULL`:** Sets the foreign key column to `NULL` when the parent is deleted. (Requires `null=True`).
- **`models.SET_DEFAULT`:** Resets the foreign key to its defined `default` value.
- **`models.DO_NOTHING`:** Does nothing; leaves foreign key handling entirely to the underlying database.

---

## 4. Syntax

```python
# File: company/models.py
from django.db import models

class Department(models.Model):
    name = models.CharField(max_length=100)
    code = models.CharField(max_length=10, unique=True)

    def __str__(self):
        return self.name

class Employee(models.Model):
    department = models.ForeignKey(
        Department,
        on_delete=models.PROTECT,          # Protects department from accidental deletion!
        related_name='employees'           # Reverse manager: dept.employees.all()
    )
    first_name = models.CharField(max_length=50)
    email = models.EmailField(unique=True)

    def __str__(self):
        return f"{self.first_name} ({self.department.name})"
```

---

## 5. Practical Examples

### Forward and Reverse Lookups in Practice
```python
# Create parent
dept = Department.objects.create(name="Engineering", code="ENG")

# Create child referencing parent
emp = Employee.objects.create(department=dept, first_name="Amina", email="amina@example.com")

# Forward traversal:
print(emp.department.code) # "ENG"

# Reverse traversal:
eng_employees = dept.employees.filter(first_name__startswith="A")
print(eng_employees.count()) # 1
```

---

## 6. Code Explanation

- `department_id`: In the database, Django appends `_id` to the field name, creating a column named `department_id` containing the integer primary key of the Department row.
- `emp.department`: Returns the full `Department` model instance.
- `emp.department_id`: Returns the raw foreign key integer without executing an extra query!

---

## 7. Expected Output

Attempting to delete a department with active employees under `on_delete=models.PROTECT`:
```python
>>> dept.delete()
django.db.models.deletion.ProtectedError: ("Cannot delete some instances of model 'Department' because they are referenced through protected foreign keys: 'Employee.department'", {<Employee: Amina (Engineering)>})
```
Referential integrity protected your company data from accidental deletion!

---

## 8. Real-World Use Case

E-commerce stores linking products to categories, hospitals linking doctors to departments, and financial systems linking transactions to bank accounts.

---

## 9. Common Mistakes

1. **Using `models.CASCADE` on critical business entities:** Accidentally deleting a `Customer` and having all historical invoices and payments cascade-deleted! Use `models.PROTECT` or `models.SET_NULL` for financial records.
2. Forgetting `null=True` when specifying `on_delete=models.SET_NULL`.

---

## 10. Best Practices

- Use `models.PROTECT` on master records (customers, departments, categories) to prevent catastrophic data loss.
- Use `models.CASCADE` for strictly owned child records (order line items, blog comments).
- Access `obj.foreign_key_id` when you only need the ID, avoiding unnecessary database queries.

## 12. Interview Questions

**Q1: What is the difference between `obj.department` and `obj.department_id`?**  
*Answer:* `obj.department` triggers a database query (unless cached or joined via `select_related`) to instantiate and return the full `Department` model instance. `obj.department_id` accesses the raw foreign key integer value stored directly in the current model's table row without making any additional database queries.

**Q2: What is `ProtectedError` in Django?**  
*Answer:* `ProtectedError` is a subclass of `IntegrityError` raised when you attempt to delete a parent model instance that is referenced by child records through a foreign key configured with `on_delete=models.PROTECT`.

---

## 13. Summary

- `ForeignKey` implements One-to-Many relationships.
- `on_delete` governs deletion behaviors (`CASCADE`, `PROTECT`, `SET_NULL`).
- Reverse queries are accessed via `related_name`.
