# 2. Migration Commands and Workflow

## 1. Introduction

Managing migrations across branches, resolving schema conflicts, and rolling back unintended changes are standard tasks in professional Django engineering. Understanding advanced migration commands and safe migration workflows ensures smooth database operations.

---

## 2. Why Do We Need It?

- **Adding Non-Nullable Fields:** Adding a `null=False` field to a table with existing rows requires defining a default value.
- **Rolling Back Migrations:** Reverting a broken migration without losing unrelated table data.
- **Squashing Migrations:** Merging hundreds of historical migration files into a single clean initial file.

---

## 3. How It Works

- **Default Prompts:** If you add a non-nullable field without a default, `makemigrations` halts and asks you to provide a one-off default value.
- **Rollback:** Running `migrate <app_name> <migration_number>` rolls back all migrations in that app applied *after* that number.
- **Zero Migration:** Running `migrate <app_name> zero` rolls back and unapplies ALL migrations for that app!

---

## 4. Syntax

```bash
# Adding a non-nullable field:
# Django prompts:
# 1) Provide a one-off default now (will be set on all existing rows)
# 2) Quit and let me add a default in models.py

# Roll back an app to migration 0002:
python manage.py migrate blog 0002

# Unapply all migrations for an app (Drops tables!):
python manage.py migrate blog zero

# Fake a migration (marks as applied without running SQL):
python manage.py migrate blog 0003 --fake

# Squash historical migrations:
python manage.py squashmigrations blog 0005
```

---

## 5. Practical Examples

### Safe Workflow for Adding Fields
Suppose you add `phone` to an existing `Employee` model:
```python
# Option A: Allow null/blank (Safest for existing data!)
phone = models.CharField(max_length=20, blank=True, default='')

# Option B: Provide explicit default
tier = models.IntegerField(default=1)
```
Because a default or blank is specified, `makemigrations` runs non-interactively without halting CI/CD builds!

---

## 6. Code Explanation

- `--fake`: Updates the `django_migrations` table as if the migration ran, without executing any SQL statements. Useful when retrofitting Django onto existing legacy database schemas.
- `migrate blog zero`: Executes the `reverse_code` or `drop_table` operations for all migrations in `blog`, effectively resetting the app's database footprint.

---

## 7. Expected Output

Rolling back:
```text
Applying blog.0003_delete_comment... UNAPPLYING
Applying blog.0002_add_likes... UNAPPLYING
OK
```

---

## 8. Real-World Use Case

Squashing 80+ legacy migration files into a single initial migration in mature enterprise codebases to reduce unit test suite startup times.

---

## 9. Common Mistakes

1. Adding a `unique=True` non-nullable field to a table that already contains multiple rows without providing unique values (causes database integrity constraint crashes).
2. Modifying already-committed and deployed migration files. Once a migration has been applied in production, NEVER edit it; create a new migration instead!

---

## 10. Best Practices

- Never edit a migration file that has already been pushed and applied to production.
- Always provide a `default` value when adding new non-nullable fields.
- Squash historical migrations periodically when test suites become slow.

## 12. Interview Questions

**Q1: How do you handle migration conflicts when merging Git branches?**  
*Answer:* When two branches create migrations with the same sequence number (e.g., both create `0003_...`), running `makemigrations --merge` instructs Django to inspect both migration branches and create a new merge migration file that lists both conflicting migrations in its `dependencies`, resolving the branch divergence cleanly.

**Q2: What is the `--fake-initial` option in `migrate`?**  
*Answer:* `--fake-initial` tells Django to check if the database tables for an app's initial migration (`0001_initial`) already exist. If the tables exist, Django marks `0001_initial` as applied in `django_migrations` without executing the `CREATE TABLE` statements, preventing `Table already exists` errors when connecting to pre-existing databases.

---

## 13. Summary

- Always provide defaults when adding non-nullable fields.
- Rollbacks are executed by targeting earlier migration numbers.
- `makemigrations --merge` resolves branch migration conflicts.
