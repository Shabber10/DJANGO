# 1. Understanding Django Migrations

## 1. Introduction

**Migrations** are Django's way of propagating changes you make to your models (adding a field, deleting a model, altering constraints) into your database schema. They act as a version control system for your database tables, capturing every structural evolution in human-readable Python files.

---

## 2. Why Do We Need It?

In team environments and production deployments:
- Modifying database schemas manually with raw SQL scripts leads to drift, missing columns, and broken environments across teammates.
- Migrations version your schema in Git: when you pull a teammate's branch, running one command brings your local database schema into exact alignment.
- Migrations allow both forward schema upgrades and safe backward rollbacks.

---

## 3. How It Works

Django's migration cycle consists of two primary steps:
1. **`python manage.py makemigrations`:** Django compares your current `models.py` definitions against your existing migration files and writes out new migration files (e.g., `0001_initial.py`, `0002_add_phone.py`) in each app's `migrations/` folder.
2. **`python manage.py migrate`:** Django inspects the `django_migrations` table in your database to see which migration files haven't executed yet, and runs their generated SQL in order.

---

## 4. Syntax

```bash
# 1. Detect model changes and create migration files
python manage.py makemigrations

# Target a specific app
python manage.py makemigrations accounts

# 2. Apply pending migrations to the database
python manage.py migrate

# 3. View status of all migrations ([X] applied, [ ] unapplied)
python manage.py showmigrations

# 4. Preview the exact SQL that a migration will execute
python manage.py sqlmigrate accounts 0001
```

---

## 5. Practical Examples

### Inspecting an Auto-Generated Migration File
Look inside `academy/migrations/0001_initial.py`:
```python
from django.db import migrations, models

class Migration(migrations.Migration):
    initial = True
    dependencies = []

    operations = [
        migrations.CreateModel(
            name='Student',
            fields=[
                ('id', models.BigAutoField(auto_created=True, primary_key=True, serialize=False, verbose_name='ID')),
                ('first_name', models.CharField(max_length=50)),
                ('email', models.EmailField(max_length=254, unique=True)),
            ],
        ),
    ]
```

---

## 6. Code Explanation

- `dependencies`: Lists migrations that must execute before this one (enforcing proper foreign key creation order).
- `operations`: A list of operation objects (`CreateModel`, `AddField`, `AlterField`, `DeleteModel`) that Django translates into SQL statements.
- `django_migrations`: A database table maintained by Django that records the app name, migration name, and application timestamp for every applied migration.

---

## 7. Expected Output

Running `python manage.py showmigrations`:
```text
admin
 [X] 0001_initial
 [X] 0002_logentry_remove_auto_add
 [X] 0003_logentry_add_action_flag_choices
academy
 [X] 0001_initial
 [ ] 0002_student_phone  <-- Pending, unapplied migration!
```

---

## 8. Real-World Use Case

Deploying database schema changes safely in zero-downtime CI/CD production pipelines on Kubernetes or cloud databases (AWS RDS, PostgreSQL).

---

## 9. Common Mistakes

1. **Deleting migration files manually from disk:** Deleting migration files causes the database's `django_migrations` tracking table to fall out of sync with your filesystem, resulting in `NodeNotFoundError`.
2. Forgetting to commit migration files to Git. Migration files MUST be committed!

---

## 10. Best Practices

- Always commit migration files to version control along with the model changes that created them.
- Run `showmigrations` to inspect unapplied changes before running `migrate`.
- Use `sqlmigrate` to review the generated SQL before applying migrations to production.

## 12. Interview Questions

**Q1: How does Django's migration engine track applied migrations?**  
*Answer:* Django creates a dedicated table named `django_migrations` inside the database. When `python manage.py migrate` is run, Django queries this table, compares the recorded list of applied `(app, name)` pairs against the migration files on disk, and executes only the unapplied migrations in topological dependency order.

**Q2: What is the purpose of `sqlmigrate`?**  
*Answer:* `sqlmigrate` displays the exact raw SQL statements that Django would execute for a given migration without actually applying them. This is critical for Database Administrators (DBAs) to review schema modifications and indexes before deploying to production.

---

## 13. Summary

- Migrations version-control your database schema in Python code.
- `makemigrations` creates migration files; `migrate` executes SQL.
- Migration files must always be committed to Git.
