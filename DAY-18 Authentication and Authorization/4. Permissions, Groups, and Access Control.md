# 4. Permissions, Groups, and Access Control

## 1. Introduction

Once a user is authenticated, the application must enforce **Authorization**. Django provides a granular permission system coupled with **Groups** to implement Role-Based Access Control (RBAC).

---

## 2. Why Do We Need It?

Different users have different operational roles:
- A "Customer Support" representative should view accounts but not delete them.
- An "Editor" can publish blog articles, but cannot modify billing settings.
- Hardcoding user checks like `if request.user.username == "admin":` is fragile and unmaintainable. Django's permission engine decouples roles from individual identities.

---

## 3. How It Works

For every model registered in `INSTALLED_APPS`, Django automatically creates four permissions in the format:
`<app_label>.<action>_<model_name>`:
- `add_article`: Can create articles.
- `change_article`: Can edit articles.
- `delete_article`: Can delete articles.
- `view_article`: Can view articles.

Permissions can be assigned:
1. Directly to individual users (`user.user_permissions.add(perm)`).
2. To Groups (`group.permissions.add(perm)`), where assigning a user to a Group automatically inherits all group permissions!

---

## 4. Syntax

```python
# In Views: Using @permission_required decorator
from django.contrib.auth.decorators import permission_required
from django.shortcuts import render

@permission_required('blog.delete_article', raise_exception=True)
def delete_article_view(request, pk):
    # Only users with blog.delete_article permission can execute this!
    ...
```

```html
<!-- In Templates: Using perms context variable -->
{% if perms.blog.change_article %}
    <a href="{% url 'blog:edit' article.pk %}">Edit Article</a>
{% endif %}
```

## 5. Practical Examples

### Programmatic Group and Permission Management
```python
from django.contrib.auth.models import Group, Permission
from django.contrib.contenttypes.models import ContentType
from blog.models import Article

# 1. Create a "Content Editors" group
editors_group, created = Group.objects.get_or_create(name='Content Editors')

# 2. Retrieve permissions for the Article model
content_type = ContentType.objects.get_for_model(Article)
article_perms = Permission.objects.filter(content_type=content_type, codename__in=['add_article', 'change_article'])

# 3. Assign permissions to the group
editors_group.permissions.set(article_perms)

# 4. Add a user to the group
user.groups.add(editors_group)

# 5. Check permission (returns True via group inheritance!)
print(user.has_perm('blog.change_article')) # True
```

---

## 6. Code Explanation

- `@permission_required('blog.delete_article', raise_exception=True)`: If the user lacks the permission, Django immediately raises `PermissionDenied`, rendering an HTTP 403 Forbidden page.
- `user.has_perm('app.action_model')`: Checks user-specific permissions AND all permissions inherited from the user's groups.

---

## 7. Expected Output

If an unauthorized user visits a protected view:
```text
HTTP/1.1 403 Forbidden
403 Forbidden: You do not have permission to access this resource.
```

---

## 8. Real-World Use Case

Enterprise RBAC: assigning doctors, nurses, and billing specialists to their respective groups in a Hospital Information System.

---

## 9. Common Mistakes

1. **Omiting `raise_exception=True` on `@permission_required`:** By default, if omitted, Django redirects users to the login screen, which confuses already-authenticated users! Setting `raise_exception=True` properly returns a 403 Forbidden error.

---

## 10. Best Practices

- Assign permissions to Groups rather than individual users.
- Always use `raise_exception=True` on `@permission_required` for authenticated endpoints.
- Define custom model permissions in `class Meta` for domain-specific actions (e.g. `can_publish`, `can_export`).

## 12. Interview Questions

**Q1: How do you define custom permissions on a Django model?**  
*Answer:* Inside the model's `class Meta`, define the `permissions` tuple containing 2-tuples of `(codename, human_readable_description)`:
```python
class Meta:
    permissions = [
        ("can_publish", "Can publish articles directly to live site"),
        ("can_view_analytics", "Can view article readership metrics"),
    ]
```
After migrating, these custom permissions are registered in the database and can be checked via `user.has_perm('blog.can_publish')`.

**Q2: What is the benefit of managing permissions via Groups rather than directly on Users?**  
*Answer:* Groups implement Role-Based Access Control (RBAC). As employees join, leave, or change roles, administrators simply add or remove users from groups (e.g. "Managers", "Auditors") rather than manually managing dozens of individual permissions on every user account, minimizing administrative overhead and security errors.

---

## 13. Summary

- Django auto-generates `add`, `change`, `delete`, and `view` permissions per model.
- Groups bundle permissions into operational roles.
- Use `@permission_required` in views and `perms` in templates.
