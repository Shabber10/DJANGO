# 5. Custom User Models (AbstractUser)

## 1. Introduction

By default, Django provides an authentication user model with `username`, `first_name`, `last_name`, `email`, and `password`. However, modern applications almost universally prefer **logging in with an email address** rather than a username, or require custom fields (e.g., `phone_number`, `date_of_birth`, `user_type`) directly on the User model. Django allows creating a **Custom User Model** by subclassing **`AbstractUser`**.

---

## 2. Why Do We Need It?

The official Django documentation issues a critical recommendation:
> **"It is highly recommended to set up a custom user model when starting a project, even if the default User model is sufficient for now."**
Switching to a custom user model *after* creating database migrations in production is notoriously complex and painful because foreign keys throughout migrations point to `auth.User`. Setting it up on Day 1 gives you lifelong architectural flexibility.

---

## 3. How It Works

- Subclass `django.contrib.auth.models.AbstractUser`.
- Set `USERNAME_FIELD = 'email'` to make email the primary login credential.
- Configure `AUTH_USER_MODEL = 'accounts.CustomUser'` in `settings.py`.
- Update `admin.py` to register the custom user model using `UserAdmin`.

---

## 4. Syntax

```python
# File: accounts/models.py
from django.contrib.auth.models import AbstractUser
from django.db import models

class CustomUser(AbstractUser):
    # Make email unique and mandatory
    email = models.EmailField(unique=True)
    
    # Custom domain attributes
    phone_number = models.CharField(max_length=20, blank=True)
    is_employee = models.BooleanField(default=False)
    is_employer = models.BooleanField(default=False)

    # Use email instead of username for login
    USERNAME_FIELD = 'email'
    REQUIRED_FIELDS = ['username'] # Fields prompted during createsuperuser

    def __str__(self):
        return self.email
```

In `config/settings.py`:
```python
# Tell Django to use CustomUser across the entire project
AUTH_USER_MODEL = 'accounts.CustomUser'
```

---

## 5. Practical Examples

### Updating Django Admin for CustomUser
```python
# File: accounts/admin.py
from django.contrib import admin
from django.contrib.auth.admin import UserAdmin
from .models import CustomUser

@admin.register(CustomUser)
class CustomUserAdmin(UserAdmin):
    # Add custom fields to admin edit forms
    fieldsets = UserAdmin.fieldsets + (
        ('Custom Profile Info', {'fields': ('phone_number', 'is_employee', 'is_employer')}),
    )
    # Add custom fields to user creation form
    add_fieldsets = UserAdmin.add_fieldsets + (
        ('Custom Profile Info', {'fields': ('email', 'phone_number', 'is_employee', 'is_employer')}),
    )
    list_display = ('email', 'username', 'is_employee', 'is_employer', 'is_staff')
```

---

## 6. Code Explanation

- `AbstractUser`: Keeps all existing Django authentication infrastructure (passwords, permissions, groups, admin integration), while allowing you to add fields or change `USERNAME_FIELD`.
- `AUTH_USER_MODEL`: Tells Django that wherever foreign keys reference users, they should point to `accounts.CustomUser`.
- `settings.AUTH_USER_MODEL`: When creating foreign keys to users in other models, always use `models.ForeignKey(settings.AUTH_USER_MODEL, ...)`!

## 9. Common Mistakes

1. **Importing User directly instead of using `get_user_model()`:**
   ```python
   # INCORRECT:
   from django.contrib.auth.models import User # Breaks if custom user model is configured!
   # CORRECT:
   from django.contrib.auth import get_user_model
   User = get_user_model()
   ```
2. Hardcoding foreign keys: `models.ForeignKey(User, ...)` instead of `models.ForeignKey(settings.AUTH_USER_MODEL, ...)`.

---

## 10. Best Practices

- Set up a custom user model at the very start of every new Django project.
- Always use `get_user_model()` in views, forms, and tests.
- Always use `settings.AUTH_USER_MODEL` in model foreign keys.

## 12. Interview Questions

**Q1: What is the difference between `AbstractUser` and `AbstractBaseUser` in Django?**  
*Answer:*
- `AbstractUser`: Provides the full existing implementation of Django's User model (including `username`, `first_name`, `last_name`, `email`, permissions, groups, and admin compatibility), allowing you to add extra fields or modify `USERNAME_FIELD`.
- `AbstractBaseUser`: Provides only the core password hashing and session token logic (`password`, `last_login`, `is_active`). You must define all user fields, permissions, and managers from scratch, suitable for highly specialized authentication requirements.

**Q2: Why must `get_user_model()` be used instead of importing the user model directly?**  
*Answer:* Because projects can customize `AUTH_USER_MODEL`. Calling `from django.contrib.auth import get_user_model; User = get_user_model()` dynamically references whichever user model is currently active in `settings.AUTH_USER_MODEL`, ensuring reusable apps and view logic remain decoupled and portable.

---

## 13. Summary

- Always configure a custom user model at project initialization.
- Subclass `AbstractUser` to add fields and customize `USERNAME_FIELD`.
- Reference user model via `get_user_model()` and `settings.AUTH_USER_MODEL`.
