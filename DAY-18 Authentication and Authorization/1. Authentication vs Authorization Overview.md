# 1. Authentication vs Authorization Overview

## 1. Introduction

Security in web applications hinges on two interrelated yet distinct concepts: **Authentication (AuthN)** and **Authorization (AuthZ)**. Django provides a battle-tested, built-in security subsystem (`django.contrib.auth`) that handles user identity verification and access permissions out of the box.

---

## 2. Why Do We Need It?

- **Authentication answers:** *"Who are you?"* (Verifying credentials like username and password).
- **Authorization answers:** *"What are you allowed to do?"* (Determining whether an authenticated user has permission to edit an article, delete an account, or view a financial ledger).
Conflating these two concepts results in critical security flaws such as Broken Object Level Authorization (BOLA).

---

## 3. How It Works

The `django.contrib.auth` framework consists of four core building blocks:
1. **User Model:** Stores usernames, emails, hashed passwords, flags (`is_active`, `is_staff`, `is_superuser`).
2. **Permissions:** Granular binary flags (`add_article`, `change_article`, `delete_article`, `view_article`) automatically created for every registered model.
3. **Groups:** Collections of permissions that can be assigned to multiple users (e.g. "Editors", "Managers").
4. **Authentication Backends:** Pluggable classes that verify credentials (default: username/password against SQL database).

---

## 4. Syntax

```python
# Accessing user and permissions in views:
def sensitive_view(request):
    # 1. Authentication Check
    if not request.user.is_authenticated:
        return redirect('accounts:login')
        
    # 2. Authorization Check
    if not request.user.has_perm('blog.change_article'):
        return HttpResponseForbidden("You do not have permission to edit articles.")
        
    return HttpResponse("Access Granted")
```

## 5. Practical Examples

### Checking Authentication in Templates
```html
<nav>
    {% if user.is_authenticated %}
        <span>Welcome, {{ user.get_short_name|default:user.username }}!</span>
        {% if perms.store.add_product %}
            <a href="{% url 'store:product_create' %}">+ New Product</a>
        {% endif %}
        <form action="{% url 'logout' %}" method="post" style="display:inline;">
            {% csrf_token %}
            <button type="submit">Log Out</button>
        </form>
    {% else %}
        <a href="{% url 'login' %}">Log In</a>
        <a href="{% url 'register' %}">Sign Up</a>
    {% endif %}
</nav>
```

---

## 6. Code Explanation

- `request.user`: Injected into every request by `AuthenticationMiddleware`. If unauthenticated, it is an instance of `AnonymousUser`.
- `user.is_authenticated`: Boolean returning `True` for logged-in users, `False` for anonymous visitors.
- `perms.app_label.permission_name`: Template helper to inspect user permissions directly in HTML.

---

## 7. Expected Output

- Logged-in user sees personalized navigation and authorized action buttons.
- Anonymous visitor sees "Log In" and "Sign Up" links.

---

## 8. Real-World Use Case

Role-Based Access Control (RBAC) in enterprise portals: standard users can create support tickets, support agents can respond to tickets, and managers can delete tickets or reassign agents.

---

## 9. Common Mistakes

1. **Calling `is_authenticated()` as a method:**
   In modern Django, `is_authenticated` is an attribute, not a callable method:
   `if user.is_authenticated:` (No parentheses!).
2. Checking authentication but forgetting to check authorization, allowing any logged-in user to access other users' private records.

---

## 10. Best Practices

- Always verify both AuthN (logged in?) and AuthZ (has permission to this specific object?).
- Use Django's built-in decorators (`@login_required`, `@permission_required`).
- Use Groups to manage permissions for roles rather than assigning permissions user-by-user.

## 12. Interview Questions

**Q1: What is the difference between `is_staff`, `is_superuser`, and `is_active` in Django's User model?**  
*Answer:*
- `is_active`: Designates whether the user account is enabled. Setting it to `False` disables the account without deleting database rows (soft deactivation).
- `is_staff`: Controls whether the user is permitted to log in to the Django Admin interface.
- `is_superuser`: Grants all permissions automatically without needing explicit group or permission assignments.

**Q2: What is `AnonymousUser` in Django?**  
*Answer:* `AnonymousUser` is a dummy class implementing the `User` interface for unauthenticated visitors. It has `is_authenticated = False`, `is_anonymous = True`, `id = None`, and returns `False` for any `has_perm()` check, allowing view code to treat `request.user` consistently without checking for `None`.

---

## 13. Summary

- Authentication identifies users; Authorization grants permissions.
- `django.contrib.auth` provides built-in models, middleware, and permissions.
- `request.user` represents the current user or `AnonymousUser`.
