# 4. Environment Variables and Production Settings

## 1. Introduction

In modern software engineering, code and configuration must be strictly decoupled per the **Twelve-Factor App** methodology. Sensitive secrets—such as database passwords, API credentials, and the Django `SECRET_KEY`—should never be committed into Git repositories. Instead, they must be supplied via **Environment Variables**.

---

## 2. Why Do We Need It?

- **Security:** Publicly pushing a `SECRET_KEY` or database password to GitHub allows attackers to compromise servers and hijack sessions.
- **Portability:** The exact same codebase can run on development, staging, and production servers simply by providing different `.env` files.

---

## 3. How It Works

Using packages like `python-dotenv` or `python-decouple`:
1. Secrets are stored in a local `.env` file (which is added to `.gitignore`).
2. Upon startup, Django reads the `.env` file into process environment variables (`os.environ`).
3. `settings.py` reads configuration values dynamically.

---

## 4. Syntax

### Installing python-dotenv:
```bash
pip install python-dotenv
```

### Creating `.env` file (in project root):
```text
SECRET_KEY=django-insecure-your-super-secret-key-here
DEBUG=True
ALLOWED_HOSTS=127.0.0.1,localhost
DATABASE_URL=sqlite:///db.sqlite3
```

### Loading in `settings.py`:
```python
# File: config/settings.py
import os
from pathlib import Path
from dotenv import load_dotenv

BASE_DIR = Path(__file__).resolve().parent.parent

# Load .env file
load_dotenv(BASE_DIR / '.env')

SECRET_KEY = os.getenv('SECRET_KEY')
DEBUG = os.getenv('DEBUG', 'False') == 'True'
ALLOWED_HOSTS = os.getenv('ALLOWED_HOSTS', '').split(',')
```

---

## 5. Practical Examples

### Production vs Development Settings Architecture
Enterprise projects often split settings into separate modules:
```text
config/
├── settings/
│   ├── __init__.py
│   ├── base.py         <-- Common settings (INSTALLED_APPS, MIDDLEWARE)
│   ├── development.py  <-- DEBUG=True, SQLite, console email backend
│   └── production.py   <-- DEBUG=False, PostgreSQL, AWS S3, WhiteNoise
```

In `manage.py`:
```python
# Default to development settings locally
os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'config.settings.development')
```

---

## 6. Code Explanation

- `os.getenv('KEY', default)`: Retrieves the environment variable, returning `default` if the key is not found in the environment.
- `load_dotenv()`: Parses the key-value pairs from a `.env` file and injects them into `os.environ`.
- `os.getenv('DEBUG') == 'True'`: Environment variables are always loaded as strings, so boolean conversion requires string comparison.

---

## 7. Expected Output

Running `python manage.py check`:
Django starts normally, reading secrets transparently from the `.env` file.

---

## 8. Real-World Use Case

Cloud hosting platforms (Render, Railway, AWS ECS, Heroku, Kubernetes) inject secrets directly through platform environment variable dashboards without any `.env` files on disk.

---

## 9. Common Mistakes

1. Accidentally committing `.env` to GitHub. (Always add `.env` to `.gitignore`!).
2. Forgetting to provide a fallback or raising an error when a mandatory secret is missing in production.

---

## 10. Best Practices

- Provide a `.env.example` file containing dummy variable names so new developers know what variables are required.
- Always add `.env` and `*.env` to `.gitignore`.
- Use `python-decouple` or `environ` for typed environment variable parsing.

## 12. Interview Questions

**Q1: How do you handle configuration differences between local development and production environments in Django?**  
*Answer:* By following the 12-Factor App methodology: extracting all environment-dependent settings (SECRET_KEY, DEBUG, DATABASES, ALLOWED_HOSTS, EMAIL credentials) into environment variables loaded via `.env` or system environment, or by splitting settings into `base.py`, `local.py`, and `production.py`.

**Q2: What should you do immediately if a production `SECRET_KEY` is accidentally leaked to a public Git repository?**  
*Answer:* Immediately rotate the `SECRET_KEY` in production, invalidate all active user sessions and password reset tokens, remove the commit from Git history (using `git filter-repo` or BFG Repo-Cleaner), and push the scrubbed history.

---

## 13. Summary

- Decouple code from configuration using environment variables.
- Keep secrets in `.env` and add it to `.gitignore`.
- Production requires `DEBUG=False` and isolated secrets management.
