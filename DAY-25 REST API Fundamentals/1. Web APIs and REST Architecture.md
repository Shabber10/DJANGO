# 1. Web APIs and REST Architecture

## 1. Introduction

An **Application Programming Interface (API)** allows different software systems to communicate and exchange data. In web development, **REST (Representational State Transfer)** is the architectural style that governs how distributed web services interact over HTTP. Understanding REST principles is essential before working with tools like Django REST Framework.

---

## 2. Why Do We Need It?

Modern web architectures have shifted from server-rendered HTML monoliths to decoupled architectures:
- Backends provide JSON data endpoints.
- Frontends (React, Vue, Next.js, mobile apps for iOS/Android, IoT devices) consume those endpoints independently.
- A single REST API backend can power web applications, native mobile apps, and third-party integrations simultaneously.

---

## 3. How It Works

### The 6 Guiding Principles of REST (Roy Fielding):
1. **Client-Server Architecture:** Separation of user interface concerns from data storage concerns.
2. **Statelessness:** Every request from client to server must contain all necessary information; the server stores no client session context between requests.
3. **Cacheability:** Responses must define themselves as cacheable or non-cacheable to optimize network traffic.
4. **Uniform Interface:** Standardized resource identification (URIs), resource manipulation through representations (JSON), and self-descriptive messages.
5. **Layered System:** Clients cannot tell whether they are connected directly to the end server or an intermediary (CDN, proxy, API gateway).
6. **Code on Demand (Optional):** Servers can temporarily extend client functionality by transferring executable code (e.g. JavaScript).

---

## 4. Syntax

### Standard RESTful URI Resource Patterns:
- `GET /api/v1/articles/`: Retrieve list of articles.
- `POST /api/v1/articles/`: Create a new article.
- `GET /api/v1/articles/42/`: Retrieve article #42.
- `PUT /api/v1/articles/42/`: Replace entire article #42.
- `PATCH /api/v1/articles/42/`: Partially update fields on article #42.
- `DELETE /api/v1/articles/42/`: Delete article #42.

---

## 5. Practical Examples

### Non-RESTful vs RESTful Design Comparison

**INCORRECT (Non-RESTful / RPC-style URIs):**
```text
POST /api/getArticles/          <-- Verb in URI!
POST /api/createArticle/        <-- Verb in URI!
GET  /api/deleteArticle?id=42   <-- Deleting via GET with query string!
POST /api/updateArticlePrice/   <-- Verb in URI!
```

**CORRECT (RESTful Resource-Oriented URIs):**
```text
GET    /api/articles/           <-- HTTP GET defines action; noun defines resource
POST   /api/articles/           <-- HTTP POST defines creation
DELETE /api/articles/42/        <-- HTTP DELETE targets specific resource
PATCH  /api/articles/42/        <-- HTTP PATCH modifies specific fields
```

---

## 6. Code Explanation

- **Nouns, not Verbs:** URIs represent resources (nouns like `articles`, `users`, `orders`), while HTTP methods represent verbs (`GET`, `POST`, `DELETE`).
- **Plural naming:** Collections should use plural nouns (`/products/`, not `/product/`).

---

## 7. Expected Output

Querying a RESTful endpoint via HTTP client:
```text
GET /api/v1/books/1/ HTTP/1.1
Host: api.example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
{
  "id": 1,
  "title": "Django for APIs",
  "author": "William S."
}
```

---

## 8. Real-World Use Case

Stripe API, GitHub REST API, Twitter/X API, and Shopify Admin API all strictly adhere to RESTful resource-oriented architectural design.

---

## 9. Common Mistakes

1. **Putting verbs in URL endpoints:** e.g. `/api/delete_user/5/`. In REST, the HTTP verb (`DELETE /api/users/5/`) communicates the action.
2. Ignoring HTTP status codes and always returning `200 OK` with `{"error": "Unauthorized"}` in the body.

---

## 10. Best Practices

- Use plural nouns for resources (`/orders/`, `/customers/`).
- Version your API routes from Day 1 (`/api/v1/...`).
- Use proper HTTP verbs: GET for read, POST for create, PUT/PATCH for update, DELETE for remove.

## 12. Interview Questions

**Q1: What are the primary constraints of REST architecture?**  
*Answer:* The six core architectural constraints defined by Roy Fielding are: Client-Server separation, Statelessness, Cacheability, Uniform Interface, Layered System, and Code on Demand (optional).

**Q2: Why is API versioning critical in RESTful design and how is it implemented?**  
*Answer:* As mobile apps and third-party integrations consume an API, breaking changes (removing fields, altering response schemas) cannot be deployed without breaking older client versions. Versioning allows running multiple schema versions simultaneously. Common strategies include URI path versioning (`/api/v1/users/`), query parameters (`?version=1`), or custom headers (`Accept: application/vnd.company.v1+json`).

---

## 13. Summary

- REST is an architectural style for building scalable web services.
- URIs represent resources as nouns; HTTP methods define the actions.
- Client and server are decoupled via stateless JSON exchanges.
