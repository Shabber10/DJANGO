# 2. HTTP Methods, Status Codes, and JSON

## 1. Introduction

In REST APIs, **JSON (JavaScript Object Notation)** is the universal data interchange format, and HTTP methods and status codes constitute the operational vocabulary. A well-designed REST API communicates precision through semantic HTTP status codes and consistent JSON payload schemas.

---

## 2. Why Do We Need It?

Without standardized status codes:
- Client applications cannot programmatically determine whether a request succeeded or failed without parsing arbitrary human-readable error messages.
- Standardized codes (201 Created, 400 Bad Request, 401 Unauthorized, 404 Not Found) allow mobile and frontend apps to trigger appropriate UI states (modals, toasts, redirects).

---

## 3. How It Works

### Status Code Semantic Mapping in REST:
- **`200 OK`:** Successful GET, PUT, or PATCH.
- **`201 Created`:** Successful POST (resource created); often includes `Location` header.
- **`204 No Content`:** Successful DELETE; indicates success with no response body.
- **`400 Bad Request`:** Client sent invalid JSON syntax or failed payload validation.
- **`401 Unauthorized`:** Missing or invalid authentication token.
- **`403 Forbidden`:** Authenticated, but lacks permission to access resource.
- **`404 Not Found`:** Resource identifier does not exist.
- **`405 Method Not Allowed`:** HTTP method not supported on endpoint.
- **`429 Too Many Requests`:** Rate limit exceeded.
- **`500 Internal Server Error`:** Unhandled server exception.

---

## 4. Syntax

```json
// Standard Success Payload:
{
  "status": "success",
  "data": {
    "id": 105,
    "name": "Mechanical Keyboard",
    "price": 129.99
  }
}

// Standard Error Payload:
{
  "status": "error",
  "code": "validation_failed",
  "message": "Invalid input payload",
  "errors": {
    "price": ["Ensure this value is greater than 0."]
  }
}
```

---

## 5. Practical Examples

### Returning Semantic Status Codes in Django
```python
# File: api/views.py
from django.http import JsonResponse

def product_api(request, pk=None):
    if request.method == "GET":
        if pk:
            # Return single item (200 OK)
            return JsonResponse({"id": pk, "name": "Keyboard"})
        # Return collection (200 OK)
        return JsonResponse([{"id": 1}, {"id": 2}], safe=False)

    elif request.method == "POST":
        # Create item (201 Created)
        return JsonResponse({"message": "Product created", "id": 101}, status=201)

    elif request.method == "DELETE":
        # Deleted item (204 No Content)
        return JsonResponse({}, status=204)

    return JsonResponse({"error": "Method not allowed"}, status=405)
```

---

## 6. Code Explanation

- `status=201`: Informs the client that the database record was persisted.
- `status=204`: Returns an empty body with status 204, confirming deletion without wasting network bandwidth on redundant text.
- `status=405`: Informs the client that an unsupported method was attempted.

## 8. Real-World Use Case

Payment gateways (Stripe, Razorpay) returning `201 Created` upon charge authorization, or `400 Bad Request` with structured error codes (`insufficient_funds`, `expired_card`).

---

## 9. Common Mistakes

1. **Returning `200 OK` when an error occurred:**
   ```json
   // ANTI-PATTERN:
   HTTP/1.1 200 OK
   {"error": true, "message": "Record not found"} // Should be HTTP 404!
   ```

---

## 10. Best Practices

- Never return 200 OK for error responses.
- Return structured error dictionaries with field-level breakdowns.
- Use 201 for creations and 204 for deletions.

## 12. Interview Questions

**Q1: Why is returning `200 OK` with an error message in the JSON body considered an anti-pattern?**  
*Answer:* It violates HTTP semantics. HTTP clients, API gateways, load balancers, and monitoring tools inspect the HTTP status line to monitor health and route responses. Returning 200 causes client libraries (like Axios or Fetch) to enter their success branches (`.then()`) rather than error branches (`.catch()`), requiring frontend developers to write redundant boilerplate to inspect every response body for error flags.

**Q2: What is the idempotency property of HTTP PUT vs POST?**  
*Answer:* PUT is idempotent: executing `PUT /api/users/5/` five consecutive times with identical data results in the exact same database state as executing it once. POST is non-idempotent: executing `POST /api/orders/` five times creates five distinct orders in the database.

---

## 13. Summary

- JSON is the lingua franca of REST APIs.
- HTTP status codes provide machine-readable response metadata.
- Semantic codes (200, 201, 204, 400, 401, 403, 404) are mandatory.
