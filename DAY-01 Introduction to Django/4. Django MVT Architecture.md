# 4. Django MVT Architecture

## 1. Introduction

Django implements a variation of the classical **Model-View-Controller (MVC)** architectural pattern, officially known as **Model-View-Template (MVT)**. In Django's MVT architecture, the framework itself acts as the Controller, orchestrating the interaction between database Models, business logic Views, and user presentation Templates.

---

## 2. Why Do We Need It?

Without architectural separation of concerns, web code quickly degenerates into spaghetti code—where SQL queries, HTML strings, validation logic, and HTTP handling are jumbled into single files. The MVT pattern enforces clean boundaries:
- **Separation of Concerns:** Database schemas exist independently of user interfaces.
- **Maintainability:** Front-end designers can modify HTML templates without touching Python backend code.
- **Testability:** Views and models can be unit-tested without rendering browsers.

---

## 3. How It Works

### The MVT Breakdown:
1. **Model (`models.py`):** Represents the data layer, maps to database tables, and encapsulates data rules.
2. **View (`views.py`):** Represents business logic. Receives requests, queries Models, and renders Templates with context dictionaries (corresponds to Controller in MVC).
3. **Template (`templates/*.html`):** Represents the presentation layer. Generates HTML using dynamic context data (corresponds to View in MVC).

The framework's URL dispatcher and request handler act as the controller directing traffic.

---

## 4. Syntax

```python
# Model (models.py)
from django.db import models
class Article(models.Model):
    title = models.CharField(max_length=200)
    content = models.TextField()

# View (views.py)
from django.shortcuts import render
from .models import Article
def article_list(request):
    articles = Article.objects.all()
    return render(request, 'articles/list.html', {'articles': articles})
```

---

## 5. Practical Examples

### Complete Template Integration
```html
<!-- templates/articles/list.html -->
<!DOCTYPE html>
<html>
<head><title>Article Portal</title></head>
<body>
    <h1>All Articles</h1>
    <ul>
    {% for article in articles %}
        <li><strong>{{ article.title }}</strong>: {{ article.content|truncatewords:20 }}</li>
    {% empty %}
        <li>No articles available.</li>
    {% endfor %}
    </ul>
</body>
</html>
```

---

## 6. Code Explanation

- `Article.objects.all()`: Queries records via the Model layer.
- `render(request, template_name, context)`: Merges data into the Template and returns an `HttpResponse`.
- `{{ article.title }}`: Injects dynamic data safely with automatic HTML escaping.

---

## 7. Expected Output

Navigating to `/articles/` renders the HTML output with all database articles populated into list items.

---

## 8. Real-World Use Case

Any data-driven application (banking portal, e-commerce catalogue, corporate intranet) relies on MVT to cleanly decouple data storage from business rules and UI design.

---

## 9. Common Mistakes

1. Executing complex database queries directly inside templates.
2. Building raw HTML strings inside view functions.

---

## 10. Best Practices

- Keep Models fat (domain logic belongs in models/services).
- Keep Views thin (views coordinate requests, queries, and responses).
- Keep Templates dumb (templates handle presentation only).

## 12. Interview Questions

**Q1: How does Django's MVT differ from traditional MVC?**  
*Answer:* In Django, the Model is the data layer, the View is the controller containing business logic, and the Template is the presentation view. Django itself acts as the overarching controller.

**Q2: What is the Context dictionary in Django MVT?**  
*Answer:* The Context is a dictionary passed from the View to the Template that provides access to dynamic Python objects during rendering.

---

## 13. Summary

- MVT separates data (Model), business logic (View), and presentation (Template).
- Django coordinates the workflow as the central controller.
- This pattern promotes clean code, reusability, and maintainability.
