# 4. Database Transactions and atomic

## 1. Introduction

In web applications, complex operations often require multiple database writes. For example, transferring money involves deducting funds from Account A and adding funds to Account B. If the server crashes between step 1 and step 2, money disappears! **Database Transactions** ensure that a group of SQL operations execute as an indivisible unit: either **all operations succeed**, or **all operations are rolled back**.

---

## 2. Why Do We Need It?

Transactions guarantee the **ACID** properties of database operations:
- **Atomicity:** All changes succeed together or roll back completely ("All-or-Nothing").
- **Consistency:** Database transitions from one valid state to another, respecting all constraints.
- **Isolation:** Concurrent transactions execute without interfering with one another.
- **Durability:** Committed transactions persist even in the event of power loss or crash.

---

## 3. How It Works

Django provides the `transaction.atomic()` function, which can be used as both:
1. **A Context Manager:** Wrapping specific critical blocks of code (`with transaction.atomic():`).
2. **A Decorator:** Wrapping an entire view or function (`@transaction.atomic`).

If an uncaught exception is raised inside an `atomic` block, Django issues an SQL `ROLLBACK`. If the block completes without exception, Django issues an SQL `COMMIT`.

---

## 4. Syntax

```python
from django.db import transaction

# Approach 1: Context Manager (Recommended for precision)
def transfer_funds(sender_account, receiver_account, amount):
    with transaction.atomic():
        sender_account.balance -= amount
        sender_account.save()
        
        # If an error happens here, the sender deduction is rolled back!
        receiver_account.balance += amount
        receiver_account.save()

# Approach 2: View Decorator
@transaction.atomic
def create_order_view(request):
    # Entire view is wrapped in a transaction
    order = Order.objects.create(...)
    OrderItem.objects.bulk_create(...)
    return HttpResponse("Order placed")
```

## 5. Practical Examples

### Pessimistic Locking with `select_for_update()`
```python
# File: banking/services.py
from django.db import transaction
from django.core.exceptions import ValidationError
from .models import BankAccount

def secure_withdrawal(account_id, amount):
    with transaction.atomic():
        # select_for_update() acquires an SQL row-level lock (SELECT ... FOR UPDATE)
        # Prevents concurrent requests from reading or modifying this row until committed!
        account = BankAccount.objects.select_for_update().get(id=account_id)
        
        if account.balance < amount:
            raise ValidationError("Insufficient balance.")
            
        account.balance -= amount
        account.save()
        
        return account.balance
```

---

## 6. Code Explanation

- `transaction.atomic()`: Opens a transaction. Nested `atomic()` blocks create **savepoints**, allowing partial rollbacks.
- `select_for_update()`: Locks the selected database row until the surrounding transaction commits. Essential for preventing **race conditions** in inventory decrements, seat bookings, and wallet deductions.
- `transaction.on_commit(callback)`: Registers a callback function (such as sending an email or Celery task) to execute **only after** the transaction has successfully committed to the database.

---

## 7. Expected Output

```python
# Simulating a failed transfer inside atomic block:
>>> transfer_funds(sender, receiver, 500)
# Exception raised: ValueError("Network error to payment gateway")
# Database state:
>>> sender.refresh_from_db(); sender.balance
1000  # Automatically restored! Money was NOT deducted!
```

## 8. Real-World Use Case

**E-Commerce Checkout & Flash Sales:**
During a flash sale, 100 users try to buy the last 2 items in stock. `select_for_update()` inside `transaction.atomic()` ensures requests are queued sequentially at the database row level, preventing inventory from going negative.

---

## 9. Common Mistakes

1. **Executing Slow Network Calls Inside Transactions:** Making external HTTP requests or sending emails inside `with transaction.atomic():` keeps database locks open for seconds, causing connection pool exhaustion! Use `transaction.on_commit()`.
2. **Catching Exceptions Inside `atomic` Without Re-raising:** Catching exceptions inside the atomic block without letting Django see the exception causes Django to commit the partial transaction!
3. **Overusing `@transaction.atomic` on Entire Views:** Wrapping whole views in transactions holds locks longer than necessary and can degrade overall concurrency.

---

## 10. Best Practices

- Keep atomic transaction blocks as short and fast as possible.
- Use `transaction.on_commit(lambda: my_task.delay())` to trigger Celery tasks only after successful commit.
- Use `select_for_update()` to prevent race conditions on mutable financial/inventory balances.

## 12. Interview Questions

**Q1: What problem does `transaction.on_commit()` solve?**
*Answer:* If you dispatch an asynchronous Celery task or send an email inside a transaction block before it commits, the worker might process the task before the database has finalized the commit. The worker queries the database, fails to find the newly created record, and raises an `ObjectDoesNotExist` error. `transaction.on_commit(callback)` ensures the task or side effect is triggered only after the transaction has successfully committed to disk.

**Q2: What is the difference between Optimistic Concurrency Control and Pessimistic Concurrency Control?**
*Answer:* **Pessimistic locking** (`select_for_update()`) locks the database row immediately upon reading it, blocking all other transactions until the lock is released. **Optimistic locking** does not lock the row; instead, it checks a version column or timestamp upon saving (`UPDATE table SET balance=..., version=version+1 WHERE id=... AND version=old_version`). If the version changed, the transaction aborts and retries.

---

## 13. Summary

- `transaction.atomic()` guarantees all-or-nothing database execution.
- Unhandled exceptions automatically trigger SQL `ROLLBACK`.
- Use `select_for_update()` to lock rows and prevent race conditions.
- Always use `transaction.on_commit()` to trigger external side-effects like Celery tasks.
