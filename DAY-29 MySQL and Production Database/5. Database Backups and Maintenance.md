# 5. Database Backups and Maintenance

## 1. Introduction

Data is the most valuable asset of any web application. Hardware failures, ransomware attacks, accidental drops, or corrupted migrations can wipe out an entire company overnight. A disciplined **Database Backup and Maintenance** strategy ensures minimal downtime and zero data loss.

---

## 2. Why Do We Need It?

- Hardware crashes and cloud region outages happen without warning.
- Human error: Developers accidentally run `DELETE` without a `WHERE` clause on production.
- RTO (Recovery Time Objective): How quickly can your service be restored?
- RPO (Recovery Point Objective): How much data can your business afford to lose (e.g., 5 minutes vs 24 hours)?

---

## 3. How It Works

Database backups fall into two main categories:
1. **Logical Backups:** SQL dumps or JSON exports containing table structures and `INSERT` statements (`mysqldump`, Django `dumpdata`).
2. **Physical / Binary Backups:** Raw database storage copies, point-in-time recovery logs (MySQL Binlogs, AWS RDS automated snapshots).

---

## 4. Syntax

```bash
# 1. Native MySQL Logical Backup with mysqldump
mysqldump -u ems_user -p --single-transaction --quick --databases ems_db > backup_ems_$(date +%F).sql

# 2. Restoring MySQL Backup
mysql -u ems_user -p ems_db < backup_ems_2026-10-31.sql

# 3. Django Built-in Fixture Backup (dumpdata)
python manage.py dumpdata employees --indent 2 > employees_backup.json

# 4. Restoring Django Fixture (loaddata)
python manage.py loaddata employees_backup.json
```

---

## 5. Practical Examples

### Automated Backup Script with Compression and S3 Upload
```bash
#!/bin/bash
# File: scripts/backup_db.sh
set -e

DB_NAME="ems_db"
DB_USER="ems_user"
TIMESTAMP=$(date +"%Y%m%d_%H%M%S")
BACKUP_DIR="/var/backups/mysql"
BACKUP_FILE="${BACKUP_DIR}/${DB_NAME}_${TIMESTAMP}.sql.gz"

mkdir -p ${BACKUP_DIR}

echo "Starting backup for ${DB_NAME}..."
# Dump and compress on the fly
mysqldump -u ${DB_USER} -p"${DB_PASSWORD}" --single-transaction --quick ${DB_NAME} | gzip > ${BACKUP_FILE}

echo "Backup created at ${BACKUP_FILE}"

# Upload to Amazon S3 bucket for offsite disaster recovery
aws s3 cp ${BACKUP_FILE} s3://my-company-db-backups/daily/

# Keep only last 7 days locally
find ${BACKUP_DIR} -type f -name "*.sql.gz" -mtime +7 -delete
echo "Backup process completed successfully."
```

---

## 6. Code Explanation

- `--single-transaction`: Dumps InnoDB tables in a consistent transaction state without locking tables or interrupting active users!
- `--quick`: Forces `mysqldump` to retrieve rows from the server row-by-row rather than buffering all rows in memory (essential for large multi-gigabyte tables).
- `gzip`: Compresses the SQL text dump, reducing backup file size by 70-85%.
- Offsite backup (S3): Backups must never reside solely on the same server as the live database.

## 8. Real-World Use Case

**Disaster Recovery in Production:**
A flawed migration script accidentally drops the `leave_requests` table during an update. Within 15 minutes, DevOps uses the automated 02:00 AM snapshot and binlogs to restore the database to the exact minute prior to the failed migration.

---

## 9. Common Mistakes

1. **Never Testing Restores:** Having backups that you have never practiced restoring. Untested backups are not backups!
2. **Storing Backups on the Same Drive:** If the server disk crashes, both the database and the backups are lost.
3. **Running `mysqldump` Without `--single-transaction`:** Locks tables and blocks production users while the dump runs.

---

## 10. Best Practices

- Follow the **3-2-1 Backup Rule**: 3 copies of data, 2 different media types, 1 offsite location (e.g., S3 / GCS).
- Schedule automated daily dumps via cron or use cloud automated snapshots.
- Periodically perform drill restorations on staging environments to verify data integrity.
- Encrypt backup files at rest and during transit.

## 12. Interview Questions

**Q1: What is the 3-2-1 backup rule and how does it apply to cloud web applications?**
*Answer:* The 3-2-1 rule states that you should maintain:
- **3** total copies of your data (1 live production database + 2 backups).
- **2** different storage media/types (e.g., live SSD disk storage and compressed object storage archives).
- **1** copy stored offsite (e.g., in an isolated cloud region or separate cloud provider like Amazon S3 or Google Cloud Storage).

**Q2: What are the limitations of Django's `dumpdata` for enterprise database backups?**
*Answer:* `dumpdata` serializes records into JSON or XML through the Django ORM layer. For large databases, this is extremely slow, consumes massive RAM, does not preserve database-specific schema objects (stored procedures, triggers, indexes, specific constraints), and can cause foreign key dependency errors during `loaddata`. Native tools like `mysqldump` or `pg_dump` operate directly on the storage engine and are hundreds of times faster.

---

## 13. Summary

- Regular database backups protect against hardware failure, human error, and corruption.
- Use `mysqldump --single-transaction --quick` for consistent non-blocking MySQL backups.
- Store backups offsite (Amazon S3 / Google Cloud Storage) adhering to the 3-2-1 backup rule.
- Regularly practice and verify database restoration drills.
