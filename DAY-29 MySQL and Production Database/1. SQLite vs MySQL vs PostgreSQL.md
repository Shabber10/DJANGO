# 1. SQLite vs MySQL vs PostgreSQL

## 1. Introduction

Django ships with SQLite as the default out-of-the-box database engine. While SQLite is fantastic for zero-configuration local development and rapid prototyping, production applications handling concurrent users and mission-critical transactions require a dedicated client-server Relational Database Management System (RDBMS) like **MySQL** or **PostgreSQL**.

---

## 2. Why Do We Need It?

- **Database-Level File Locking:** SQLite locks the entire database file during write operations. If two users submit forms simultaneously, one gets a `database is locked` error.
- **Client-Server Architecture:** Production databases run on dedicated hardware with connection pooling, multi-threading, and distributed backups.
- **Data Integrity & Concurrency:** MySQL and Postgres handle thousands of concurrent read/write queries with row-level locking and ACID compliance.

---

## 3. How It Works

### Database Comparison Matrix

| Feature | SQLite | MySQL | PostgreSQL |
|---|---|---|---|
| **Architecture** | Serverless / Single File | Client-Server RDBMS | Client-Server Object-Relational |
| **Concurrency** | Low (Table/File-level locking) | High (Row-level locking via InnoDB) | Very High (MVCC) |
| **Best Used For** | Prototyping, Tests, CLI Tools | Web applications, E-Commerce, CMS | Complex analytics, GeoDjango, JSONB |
| **Setup Overhead** | Zero (Built into Python) | Requires MySQL Server / MariaDB | Requires PostgreSQL Server |
| **Django Engine** | `django.db.backends.sqlite3` | `django.db.backends.mysql` | `django.db.backends.postgresql` |
| **Driver** | Built-in `sqlite3` | `mysqlclient` | `psycopg` (v3) |

## 4. Syntax

```python
# Comparing DATABASES configuration in settings.py

# 1. Development (SQLite)

    'default': {
        'ENGINE': 'django.db.backends.sqlite3',

# 2. Production (MySQL)

    'default': {

        'USER': 'ems_user',
        'PASSWORD': 'SecurePassword123!',

            'charset': 'utf8mb4',
            'init_command': "SET sql_mode='STRICT_TRANS_TABLES'",
        },
    }
}
```

## 5. Practical Examples

### Environment-Driven Database Switching
```python
# File: settings.py
import os
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

DB_ENGINE = os.environ.get('DB_ENGINE', 'sqlite')

if DB_ENGINE == 'mysql':
    DATABASES = {
        'default': {
            'ENGINE': 'django.db.backends.mysql',
            'NAME': os.environ.get('DB_NAME', 'prod_db'),
            'USER': os.environ.get('DB_USER', 'root'),
            'PASSWORD': os.environ.get('DB_PASSWORD', ''),
            'HOST': os.environ.get('DB_HOST', 'localhost'),
            'PORT': os.environ.get('DB_PORT', '3306'),
            'OPTIONS': {
                'charset': 'utf8mb4',
            }
        }
    }
else:
    DATABASES = {
        'default': {
            'ENGINE': 'django.db.backends.sqlite3',
            'NAME': BASE_DIR / 'db.sqlite3',
        }
    }
```

---

## 6. Code Explanation

- `utf8mb4`: Crucial MySQL character set configuration! Standard MySQL `utf8` only supports 3-byte characters, crashing when users input 4-byte characters like emojis. `utf8mb4` provides full Unicode support.
- `STRICT_TRANS_TABLES`: Ensures MySQL throws errors on invalid or truncated data rather than silently converting values.
- Dynamic switching via environment variables allows local development on SQLite while staging and production automatically run MySQL.

## 8. Real-World Use Case

**Scaling from Prototype to 100k Users:**
A startup launches an e-learning portal using SQLite. As concurrent test submissions increase, users encounter `sqlite3.OperationalError: database is locked`. Migrating to MySQL with InnoDB storage engine immediately resolves concurrency bottlenecks.

---

## 9. Common Mistakes

1. **Using Default MySQL `utf8`:** Results in `Incorrect string value` errors whenever users enter emojis. Always use `utf8mb4`.
2. **Deploying SQLite to Production:** SQLite cannot handle high-write production web traffic.
3. **Hardcoding DB Credentials in `settings.py`:** Always load database passwords from environment variables or secrets managers.

---

## 10. Best Practices

- Use MySQL or PostgreSQL in staging and production environments.
- Ensure the MySQL database collation is set to `utf8mb4_unicode_ci`.
- Keep database credentials in `.env` files never committed to Git.

## 12. Interview Questions

**Q1: What causes the `database is locked` error in SQLite under web traffic?**
*Answer:* SQLite handles transactions using file-level or database-level locks. While multiple readers can access the database concurrently, only one writer can hold a write lock at any given instant. Under concurrent web traffic, multiple requests attempting to write simultaneously will block; if a request waits longer than the busy timeout, it raises `OperationalError: database is locked`.

**Q2: What is InnoDB and why is it mandatory for Django with MySQL?**
*Answer:* InnoDB is MySQL's default ACID-compliant storage engine that supports row-level locking, foreign key constraints, and multi-version concurrency control (MVCC). Older engines like MyISAM lacked transaction support and foreign key enforcement, making InnoDB mandatory for reliable Django ORM operations.

---

## 13. Summary

- SQLite is ideal for local dev, but production requires client-server RDBMS (MySQL / PostgreSQL).
- MySQL InnoDB provides row-level locking and full ACID transaction support.
- Always use `utf8mb4` charset for complete Unicode and emoji support.
- Manage credentials securely via environment variables.
