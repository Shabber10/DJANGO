# 3. Migrations, Indexes, and Database Constraints

## 1. Introduction

A well-designed database guarantees speed and data integrity at the storage layer. While Django validators check constraints at the application level, **Database Constraints** (Unique, Check) enforce rules at the database engine level, and **Database Indexes** accelerate query lookup speeds from $O(N)$ full table scans down to $O(\log N)$ B-Tree lookups.

---

## 2. Why Do We Need It?

- Application-level validation is subject to race conditions (two users submitting the same username at the same millisecond bypass Python validation).
- Without indexes, searching for an employee by email in a table with 1,000,000 rows requires scanning all 1,000,000 rows on disk!
- With a B-Tree index on `email`, the database locates the record in just 3 to 5 disk page lookups.

---

## 3. How It Works

Django models configure indexes and constraints inside the `Meta` class:
1. `indexes`: List of `models.Index` instances. Generates SQL `CREATE INDEX`.
2. `UniqueConstraint`: Enforces unique combinations across one or more fields.
3. `CheckConstraint`: Enforces SQL `CHECK (condition)` expressions.
4. `sqlmigrate`: Command to inspect the raw SQL generated by Django migrations.

---

## 4. Syntax

```python
# File: employees/models.py
from django.db import models
from django.db.models import Q, F

class Employee(models.Model):
    first_name = models.CharField(max_length=100)
    last_name = models.CharField(max_length=100)
    email = models.EmailField(unique=True)
    salary = models.DecimalField(max_digits=10, decimal_places=2)
    hire_date = models.DateField()
    is_active = models.BooleanField(default=True)

    class Meta:
        indexes = [
            # Composite index for filtering active employees by hire date
            models.Index(fields=['is_active', 'hire_date'], name='idx_emp_active_hire'),
            # Functional index (case-insensitive last name search)
            models.Index(fields=['last_name'], name='idx_emp_last_name'),
        ]
        constraints = [
            # Check constraint: Salary must be greater than zero
            models.CheckConstraint(
                check=Q(salary__gt=0),
                name='chk_emp_salary_positive'
            ),
        ]
```

---

## 5. Practical Examples

### Inspecting Generated SQL with `sqlmigrate`
```bash
# Check the exact SQL Django will execute on MySQL
$ python manage.py sqlmigrate employees 0002_add_indexes_and_constraints
```
Generated MySQL Output:
```sql
-- Create Index
CREATE INDEX `idx_emp_active_hire` ON `employees_employee` (`is_active`, `hire_date`);

-- Create Check Constraint
ALTER TABLE `employees_employee` 
ADD CONSTRAINT `chk_emp_salary_positive` CHECK (`salary` > 0);
```

---

## 6. Code Explanation

- `models.Index(fields=[...])`: Creates a composite B-Tree index. Order of fields matters! An index on `(is_active, hire_date)` accelerates queries filtering by `is_active` or by both fields, but not queries filtering by `hire_date` alone.
- `CheckConstraint(check=Q(salary__gt=0))`: Emits a native MySQL `CHECK` constraint. If any code attempts to insert a negative salary, the database immediately aborts the transaction with an integrity error.
- `sqlmigrate`: Always inspect migration SQL before applying migrations to production databases.

---

## 7. Expected Output

```python
# Violating Check Constraint in Django Shell
>>> Employee.objects.create(first_name="John", last_name="Doe", email="j@example.com", salary=-500, hire_date="2026-01-01")
django.db.utils.IntegrityError: (3819, "Check constraint 'chk_emp_salary_positive' is violated.")
```

## 8. Real-World Use Case

**Preventing Double Bookings in Hotel Reservations:**
A room cannot be booked twice for overlapping dates. Using a `UniqueConstraint` with conditional expressions ensures the database physically rejects duplicate reservations even under high-concurrency race conditions.

---

## 9. Common Mistakes

1. **Over-Indexing:** Adding indexes to every single column slows down `INSERT`, `UPDATE`, and `DELETE` operations because every index must be rewritten on every write.
2. **Ignoring Index Column Order:** In composite indexes `(A, B)`, filtering only on `B` cannot utilize the index efficiently.
3. **Relying Only on Form Validation:** Skipping database constraints leaves APIs and background scripts able to insert invalid or corrupt data.

---

## 10. Best Practices

- Index fields frequently used in `filter()`, `order_by()`, and `join` conditions.
- Primary keys and `unique=True` fields are indexed automatically by Django.
- Always use `UniqueConstraint` and `CheckConstraint` in `Meta.constraints` instead of older deprecated options (`unique_together`).
- Always run `python manage.py sqlmigrate` to review changes before migrating production.

## 12. Interview Questions

**Q1: Why should you prefer `UniqueConstraint` in `Meta.constraints` over `unique_together`?**
*Answer:* `unique_together` is legacy Django syntax that only supports simple combinations of fields. `UniqueConstraint` supports advanced features: conditional unique constraints (using `condition=Q(...)`), functional expressions (e.g., lowercasing strings with `Lower()`), custom violation error messages, and deferrable constraints.

**Q2: What is a Covering Index?**
*Answer:* A covering index is an index that contains all the columns required to satisfy a query (both the `WHERE` filter columns and the `SELECT` projected columns). When a query is covered, the database engine retrieves the data entirely from the index tree without needing to perform a secondary lookup into the main table heap, resulting in maximum query velocity.

---

## 13. Summary

- Indexes dramatically accelerate read queries from $O(N)$ to $O(\log N)$.
- Don't over-index: indexes consume disk space and slow down write operations.
- Enforce business integrity at the database layer using `UniqueConstraint` and `CheckConstraint`.
- Inspect generated SQL using `python manage.py sqlmigrate`.
