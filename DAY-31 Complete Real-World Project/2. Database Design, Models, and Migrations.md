# 2. Database Design, Models, and Migrations

## 1. Introduction

The foundation of any enterprise application is its data model. In this lesson, we will design and implement the relational schema for our Employee Management System using Django ORM, incorporating custom user models, foreign keys, constraints, and audit timestamps.

---

## 2. Why Do We Need It?

- Poor database design causes data redundancy, orphaned records, and slow query bottlenecks.
- Relational integrity ensures that employees belong to valid departments, salaries cannot be negative, and leave dates make logical sense.
- Abstract base classes enforce consistent `created_at` and `updated_at` audit trails across all tables.

---

## 3. How It Works

### Entity-Relationship Diagram (ERD) Overview
- **`User` (Custom AbstractUser):** Base auth model with role flags (`is_hr`, `is_employee`).
- **`Department`:** Holds department name, code, budget, and one-to-one manager reference.
- **`Employee`:** One-to-one with `User`, foreign key to `Department`, designation, salary, hire date.
- **`Attendance`:** Foreign key to `Employee`, date, clock-in, clock-out, total hours.
- **`LeaveRequest`:** Foreign key to `Employee`, leave type, start date, end date, status, reason.

## 4. Syntax

```python
# File: apps/core/models.py
from django.db import models

class TimeStampedModel(models.Model):
    # Abstract base class providing self-updating timestamps
    created_at = models.DateTimeField(auto_now_add=True)
    updated_at = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True
```

## 5. Practical Examples

### 1. Custom User Model (`apps/accounts/models.py`)
```python
# File: apps/accounts/models.py
from django.contrib.auth.models import AbstractUser
from django.db import models

class User(AbstractUser):
    ROLE_CHOICES = [
        ('ADMIN', 'Administrator'),
        ('HR', 'HR Manager'),
        ('EMPLOYEE', 'Employee'),
    ]
    role = models.CharField(max_length=10, choices=ROLE_CHOICES, default='EMPLOYEE')
    phone = models.CharField(max_length=20, blank=True)

    @property
    def is_hr(self):
        return self.role == 'HR' or self.is_superuser

    @property
    def is_emp(self):
        return self.role == 'EMPLOYEE'
```

### 2. Department and Employee Models
```python
# File: apps/employees/models.py
from django.db import models
from django.conf import settings
from django.db.models import Q
from apps.core.models import TimeStampedModel

class Department(TimeStampedModel):
    name = models.CharField(max_length=100, unique=True)
    code = models.CharField(max_length=10, unique=True)
    description = models.TextField(blank=True)
    
    def __str__(self):
        return f"{self.name} ({self.code})"

class Employee(TimeStampedModel):
    STATUS_CHOICES = [
        ('ACTIVE', 'Active'),
        ('ON_LEAVE', 'On Leave'),
        ('TERMINATED', 'Terminated'),
    ]
    user = models.OneToOneField(settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name='employee_profile')
    department = models.ForeignKey(Department, on_delete=models.PROTECT, related_name='employees')
    employee_id = models.CharField(max_length=20, unique=True)
    designation = models.CharField(max_length=100)
    salary = models.DecimalField(max_digits=10, decimal_places=2)
    hire_date = models.DateField()
    status = models.CharField(max_length=15, choices=STATUS_CHOICES, default='ACTIVE')

    class Meta:
        indexes = [
            models.Index(fields=['employee_id'], name='idx_emp_id'),
            models.Index(fields=['status', 'department'], name='idx_emp_stat_dept'),
        ]
        constraints = [
            models.CheckConstraint(check=Q(salary__gt=0), name='chk_emp_salary_gt_zero')
        ]

    def __str__(self):
        return f"{self.user.get_full_name()} ({self.employee_id})"
```

---

## 6. Code Explanation

- `on_delete=models.PROTECT`: Prevents a department from being accidentally deleted if it still contains active employees.
- `OneToOneField(..., related_name='employee_profile')`: Links the authentication `User` directly to their operational `Employee` data.
- `CheckConstraint(check=Q(salary__gt=0))`: Enforces non-negative salaries at the database engine level.
- `indexes`: Composite index on `status` and `department` accelerates HR queries filtering active employees by department.

## 8. Real-World Use Case

**Relational Integrity During Reorganizations:**
When a corporate department changes names or leadership, `PROTECT` ensures child employee records are never accidentally orphaned or deleted during bulk administrative operations.

---

## 9. Common Mistakes

1. **Using `CASCADE` on Departments:** Deleting a department would automatically delete all employees in that department! Always use `PROTECT` for parent departmental records.
2. **Missing `settings.AUTH_USER_MODEL`:** Hardcoding `from django.contrib.auth.models import User` breaks custom user models. Always reference `settings.AUTH_USER_MODEL`.
3. **No Unique Employee ID:** Relying solely on auto-incrementing database IDs rather than formal corporate badge/employee numbers.

---

## 10. Best Practices

- Inherit all business models from an abstract `TimeStampedModel`.
- Always specify explicit `related_name` on foreign keys.
- Enforce business rules via database constraints (`CheckConstraint`).

## 12. Interview Questions

**Q1: What is the difference between `auto_now` and `auto_now_add` in Django DateTimeField?**
*Answer:* `auto_now_add=True` automatically sets the field value to the current timestamp when the model instance is first created and never updates it again (ideal for `created_at`). `auto_now=True` automatically updates the timestamp to the current time whenever `save()` is called on the instance (ideal for `updated_at`). Both fields are automatically made non-editable in Django Admin and forms.

**Q2: Why should you use `settings.AUTH_USER_MODEL` instead of `get_user_model()` in model definitions?**
*Answer:* In model field definitions (`models.py`), foreign keys to the user model are evaluated when models are first imported during application initialization. Calling `get_user_model()` at module import time can cause circular imports or runtime errors if the user app has not finished loading. Referencing `settings.AUTH_USER_MODEL` passes a lazy string (e.g., `'accounts.User'`), which Django resolves safely after all apps are loaded.

---

## 13. Summary

- Abstract base classes provide universal audit timestamps (`created_at`, `updated_at`).
- Link operational employee records to auth users with `OneToOneField`.
- Protect departments from cascade deletion with `models.PROTECT`.
- Enforce schema constraints and indexes in model `Meta`.
