# 5. Attendance and Leave Management Workflow

## 1. Introduction

Human resource systems require robust tracking of daily presence and time-off requests. In this lesson, we implement two interconnected operational workflows: a daily **Attendance Clock-In/Clock-Out System** that calculates working hours, and a complete **Leave Management Workflow** with leave balance validation and manager approval/rejection pipelines.

---

## 2. Why Do We Need It?

- Clocking in/out prevents time theft and provides verifiable records for payroll calculations.
- Leave requests require business rule enforcement: an employee cannot request leaves if their balance is exhausted, and end dates must be on or after start dates.
- Managers need a dedicated inbox to review, approve, or reject pending leave applications with explanatory notes.

---

## 3. How It Works

1. **Attendance Tracking:**
   - Single clock-in per calendar day per employee (`UniqueConstraint`).
   - Clock-out calculates `total_hours = (clock_out - clock_in).total_seconds() / 3600`.
2. **Leave Request Workflow:**
   - Status transitions: `PENDING` -> `APPROVED` or `REJECTED`.
   - On approval: Leave days are deducted from the employee's `LeaveBalance`.

---

## 4. Syntax

```python
# File: apps/attendance/models.py
from django.db import models
from django.utils import timezone
from apps.employees.models import Employee

class Attendance(models.Model):
    employee = models.ForeignKey(Employee, on_delete=models.CASCADE, related_name='attendances')
    date = models.DateField(default=timezone.now)
    clock_in = models.TimeField()
    clock_out = models.TimeField(null=True, blank=True)
    total_hours = models.DecimalField(max_digits=4, decimal_places=2, default=0.00)

    class Meta:
        # Prevent multiple attendance records for the same employee on the same date!
        constraints = [
            models.UniqueConstraint(fields=['employee', 'date'], name='unique_emp_daily_attendance')
        ]
```

## 5. Practical Examples

### 1. Leave Request Model and Approval Workflow
```python
# File: apps/leaves/models.py
from django.db import models
from django.core.exceptions import ValidationError
from django.utils import timezone
from apps.employees.models import Employee

class LeaveRequest(models.Model):
    STATUS_CHOICES = [
        ('PENDING', 'Pending Approval'),
        ('APPROVED', 'Approved'),
        ('REJECTED', 'Rejected'),
    ]
    LEAVE_TYPES = [
        ('SICK', 'Sick Leave'),
        ('CASUAL', 'Casual Leave'),
        ('ANNUAL', 'Annual Paid Leave'),
    ]
    employee = models.ForeignKey(Employee, on_delete=models.CASCADE, related_name='leave_requests')
    leave_type = models.CharField(max_length=10, choices=LEAVE_TYPES)
    start_date = models.DateField()
    end_date = models.DateField()
    reason = models.TextField()
    status = models.CharField(max_length=10, choices=STATUS_CHOICES, default='PENDING')
    rejection_reason = models.TextField(blank=True)
    applied_at = models.DateTimeField(auto_now_add=True)

    def clean(self):
        if self.end_date < self.start_date:
            raise ValidationError("End date cannot be earlier than start date.")
        if self.start_date < timezone.now().date():
            raise ValidationError("Cannot apply for leaves in the past.")

    @property
    def duration_days(self):
        return (self.end_date - self.start_date).days + 1
```

### 2. Manager Leave Approval View
```python
# File: apps/leaves/views.py
from django.shortcuts import get_object_or_404, redirect
from django.contrib import messages
from apps.accounts.decorators import hr_required
from .models import LeaveRequest

@hr_required
def approve_leave(request, pk):
    leave_req = get_object_or_404(LeaveRequest, pk=pk)
    if leave_req.status != 'PENDING':
        messages.warning(request, "This leave request has already been processed.")
        return redirect('leaves:pending_list')

    action = request.POST.get('action')
    if action == 'approve':
        leave_req.status = 'APPROVED'
        leave_req.save()
        messages.success(request, f"Leave approved for {leave_req.employee}.")
    elif action == 'reject':
        leave_req.status = 'REJECTED'
        leave_req.rejection_reason = request.POST.get('rejection_reason', 'Business requirements.')
        leave_req.save()
        messages.info(request, f"Leave rejected for {leave_req.employee}.")

    return redirect('leaves:pending_list')
```

---

## 6. Code Explanation

- `UniqueConstraint(fields=['employee', 'date'])`: Guarantees at the database level that an employee cannot create multiple attendance entries for the same day.
- `clean()`: Performs cross-field validation, preventing impossible date spans (e.g., end date before start date).
- `duration_days`: Dynamic property computing the total inclusive calendar days of requested leave.
- `@hr_required`: Guarantees that only authorized managers or HR staff can approve or reject leave requests.

## 9. Common Mistakes

1. **Allowing Past Date Submissions:** Not validating that `start_date >= timezone.now().date()`, allowing employees to apply for retroactive leaves without approval.
2. **Missing Database-Level Attendance Constraint:** Relying solely on Python checks allows concurrent requests to clock in twice.
3. **Not Calculating Work Hours on Clock-Out:** Forgetting to convert `clock_out` and `clock_in` difference into a decimal representation of hours.

---

## 10. Best Practices

- Enforce one-clock-in-per-day constraints using `UniqueConstraint`.
- Validate date spans inside the model's `clean()` method.
- Wrap leave approval and balance deduction inside `transaction.atomic()`.

## 12. Interview Questions

**Q1: Where should business validation logic be placed: forms, models, or views?**
*Answer:* **Models (`clean()`)** are the best place for core domain validation rules (e.g., end date cannot precede start date) because model validation applies everywhere—in web forms, the Django Admin, REST APIs, and background tasks. **Forms** should handle HTTP-specific formatting and user input cleaning. **Views** should orchestrate flow and permissions, remaining lean without containing deep business rules.

**Q2: How do you prevent race conditions when deducting leave balances?**
*Answer:* Wrap the leave approval and balance deduction in `transaction.atomic()` and use `select_for_update()` to lock the employee's `LeaveBalance` row:
```python
with transaction.atomic():
    balance = LeaveBalance.objects.select_for_update().get(employee=emp)
    if balance.remaining_days < requested_days:
        raise ValidationError("Insufficient balance.")
    balance.remaining_days -= requested_days
    balance.save()
    leave_req.status = 'APPROVED'
    leave_req.save()
```

---

## 13. Summary

- Attendance systems rely on `UniqueConstraint(fields=['employee', 'date'])`.
- Validate date integrity inside model `clean()` methods.
- Manage leave status transitions (`PENDING`, `APPROVED`, `REJECTED`) via authorized views.
- Ensure state changes and balance deductions are atomic.
