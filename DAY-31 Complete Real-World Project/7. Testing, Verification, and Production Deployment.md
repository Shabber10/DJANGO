# 7. Testing, Verification, and Production Deployment

## 1. Introduction

We have architected the data model, secured authentication and permissions, implemented full CRUD operations, and built a secured REST API. The final step is rigorous **Testing, Verification, and Production Deployment**. In this lesson, we write comprehensive unit and integration tests, verify database constraints, and deploy the completed Employee Management System to a production-ready environment.

---

## 2. Why Do We Need It?

- Untested code is broken code. Automated tests prevent regressions when refactoring business logic.
- Production deployment must be automated, repeatable, and verified against security vulnerabilities.
- Writing test suites proves that the system meets enterprise software standards.

---

## 3. How It Works

1. **Model Tests:** Verify `CheckConstraint`, `UniqueConstraint`, and calculation methods.
2. **View & Authorization Tests:** Verify that employees receive `403 Forbidden` on HR routes.
3. **REST API Tests:** Test JWT authentication, token generation, and JSON payloads with `APITestCase`.
4. **CI/CD & Deployment:** Package application into Docker containers and run production pre-flight checks.

---

## 4. Syntax

```python
# File: apps/employees/tests/test_models.py
from django.test import TestCase
from django.contrib.auth import get_user_model
from django.db.utils import IntegrityError
from apps.employees.models import Department, Employee

User = get_user_model()

class EmployeeModelTest(TestCase):
    def setUp(self):
        self.dept = Department.objects.create(name="Engineering", code="ENG")
        self.user = User.objects.create_user(username="testuser", password="password123")

    def test_employee_creation_success(self):
        emp = Employee.objects.create(
            user=self.user,
            department=self.dept,
            employee_id="EMP-001",
            designation="Developer",
            salary=80000.00,
            hire_date="2026-01-01"
        )
        self.assertEqual(str(emp), " (EMP-001)")
        self.assertEqual(emp.status, "ACTIVE")

    def test_negative_salary_constraint(self):
        # Database constraint chk_emp_salary_gt_zero must block negative salary!
        with self.assertRaises(IntegrityError):
            Employee.objects.create(
                user=self.user,
                department=self.dept,
                employee_id="EMP-002",
                designation="Developer",
                salary=-5000.00,
                hire_date="2026-01-01"
            )
```

## 5. Practical Examples

### 1. Integration and Authorization Test (`apps/employees/tests/test_views.py`)
```python
from django.test import TestCase, Client
from django.urls import reverse
from django.contrib.auth import get_user_model

User = get_user_model()

class EmployeeAccessControlTest(TestCase):
    def setUp(self):
        self.client = Client()
        self.hr_user = User.objects.create_user(username="hr_user", password="pass", role="HR")
        self.emp_user = User.objects.create_user(username="emp_user", password="pass", role="EMPLOYEE")
        self.list_url = reverse('employees:list')

    def test_anonymous_redirected_to_login(self):
        response = self.client.get(self.list_url)
        self.assertEqual(response.status_code, 302)
        self.assertIn('/accounts/login/', response.url)

    def test_regular_employee_forbidden(self):
        self.client.login(username="emp_user", password="pass")
        response = self.client.get(self.list_url)
        self.assertEqual(response.status_code, 403)

    def test_hr_user_granted_access(self):
        self.client.login(username="hr_user", password="pass")
        response = self.client.get(self.list_url)
        self.assertEqual(response.status_code, 200)
```

### 2. REST API Test with `APITestCase`
```python
# File: apps/api/tests/test_api.py
from rest_framework.test import APITestCase
from rest_framework import status
from django.urls import reverse
from django.contrib.auth import get_user_model

User = get_user_model()

class EmployeeAPITest(APITestCase):
    def setUp(self):
        self.user = User.objects.create_user(username="api_hr", password="pass", role="HR")
        # Obtain JWT Token
        token_url = reverse('token_obtain_pair')
        res = self.client.post(token_url, {'username': 'api_hr', 'password': 'pass'})
        self.token = res.data['access']
        # Set Bearer token on client credentials
        self.client.credentials(HTTP_AUTHORIZATION='Bearer ' + self.token)

    def test_get_employees_authenticated(self):
        url = reverse('api-employee-list')
        response = self.client.get(url)
        self.assertEqual(response.status_code, status.HTTP_200_OK)
```

---

## 6. Code Explanation

- `self.assertRaises(IntegrityError)`: Verifies that our database `CheckConstraint` physically rejects invalid salaries at the database engine level.
- `self.client.credentials(HTTP_AUTHORIZATION='Bearer ' + self.token)`: Configures DRF's test client to authenticate subsequent requests using JWT Bearer headers.
- Multi-Role Testing: Validates that unauthenticated users get `302 Redirect`, regular employees get `403 Forbidden`, and HR managers get `200 OK`.

## 8. Real-World Use Case

**Continuous Integration (CI) Verification:**
Every time a pull request is submitted on GitHub, a GitHub Actions workflow boots a clean Ubuntu runner, spins up MySQL and Redis, executes the entire test suite, and runs `python manage.py check --deploy`. Pull requests cannot be merged if any test fails!

---

## 9. Common Mistakes

1. **Testing Against SQLite When Deploying to MySQL:** Differences in constraint enforcement or regex lookups can cause tests to pass locally on SQLite but crash in production MySQL.
2. **Hardcoding IDs in Tests:** Relying on `id=1` instead of referencing model variables (`self.dept.id`) causes brittle tests that break upon setup changes.
3. **Skipping Pre-Deployment Checks:** Forgetting to run `python manage.py check --deploy` before pushing to cloud servers.

---

## 10. Best Practices

- Target >80% test coverage across models, views, forms, and API endpoints.
- Test negative paths (unauthorized access, invalid inputs) as thoroughly as happy paths.
- Automate test runs in CI/CD before triggering production releases.

## 12. Interview Questions

**Q1: Why does Django create a separate test database when running `python manage.py test`?**
*Answer:* Django creates a dedicated, isolated test database (typically prefixed with `test_`) to ensure tests run in a pristine sandbox without altering, corrupting, or wiping live development or production data. Each test method is executed inside an atomic transaction that is rolled back upon completion, ensuring total isolation between individual tests. When all tests complete, Django tears down and destroys the test database.

**Q2: What are the key milestones in building and shipping a production Django application?**
*Answer:* A production-grade Django application requires:
1. **Architecture & Modeling:** Clean app boundaries, custom user model, relational schema with constraints and indexes.
2. **Business Logic & Permissions:** Robust views, ModelForms, RBAC decorators, and atomic transactions.
3. **Dual Interface:** Responsive HTML templates and secured REST APIs (DRF + JWT).
4. **Optimization:** Caching (Redis), async workers (Celery), and query optimization (`select_related` / `prefetch_related`).
5. **Testing & QA:** Comprehensive unit and integration test suites.
6. **Production DevOps:** Containerization (Docker), WSGI/ASGI servers (Gunicorn/Nginx), static asset serving (WhiteNoise), environment separation, and pre-flight security audits (`check --deploy`).
